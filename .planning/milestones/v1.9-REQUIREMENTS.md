# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-21
**Milestone:** v1.9 Cloud Server Templates And Runtime Profiles
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.9 Requirements

Requirements for the next CR-0001 implementation milestone after v1.8. The milestone intentionally skips live UAT and live evidence closure until the whole change request is otherwise implemented.

### Cloud Templates

- [x] **TPL-01**: Administrator can create, update, disable, and inspect versioned cloud server templates for supported game type, provider, server type, location, storage, ports, runtime defaults, and override limits.
- [x] **TPL-02**: Authorized user can select an active cloud server template during `/servers` cloud planning and see defaulted provider, port, storage, runtime, and cost assumptions before dry-run review.
- [x] **TPL-03**: Dry-run review and provider provisioning snapshot the selected template id and version, reject stale or disabled templates, and block user inputs that violate template bounds before provider mutation.
- [x] **TPL-04**: Template create, update, disable, selection, and provisioning-use events are authorization-sensitive, audited, and projected without provider tokens, Steam credentials, worker credentials, authorization headers, bearer tokens, cookies, or raw secret-bearing payloads.

### Runtime Profiles

- [x] **RUN-01**: Administrator can define reusable Arma 3 runtime profiles for mod-pack revision, mission reference, server configuration preset, BattlEye/profile/log directory assumptions, port policy, and runtime options.
- [x] **RUN-02**: Authorized user can select a permitted runtime profile or mission reference during cloud planning and review the resulting Arma 3 runtime configuration before provisioning.
- [x] **RUN-03**: Worker-facing job snapshots include only allowlisted runtime-profile fields needed for install, configure, start, stop, and log collection, with no provider, Steam, worker, bearer, cookie, or raw secret-bearing payload data.

### Guided Workflow And Guardrails

- [x] **UI-01**: WebApp admin and `/servers` creation surfaces consume template and runtime-profile APIs through generated clients and repository facades without introducing raw browser HTTP bridges or binding Razor directly to generated transport DTOs.
- [x] **SAFE-01**: Existing one-server-per-worker, Hetzner-only, required billing owner, provider-teardown-as-cost-stop, spending-policy, reconciliation, stale-plan, and redaction gates remain enforced when templates and runtime profiles are used.

## Future Requirements

Deferred to later milestones. Tracked but not in the current roadmap.

### Live UAT And Evidence

- **LIVE-01**: Operator can run the full authenticated browser, live Hetzner, Steam/Arma runtime, teardown, redaction, and final billable-resource evidence pass after the rest of CR-0001 is implemented.
- **LIVE-02**: Operator can classify Phase 30 as passed, failed, or blocked only after final provider-side billable resource count is `0` and evidence redaction passes.

### Advanced Runtime And Cloud Shape

- **RUN-04**: Worker can report dynamic cloud capacity and capabilities for placement.
- **RUN-05**: Cloud workers can optionally support Arma 3 headless clients.
- **RUN-06**: Multiple game sessions can safely run on one worker when billing, ports, storage, and cleanup are proven.
- **RUN-07**: Arma 3 runtime can be packaged with Docker or Compose where networking and BattlEye constraints allow it.
- **RUN-08**: User can resize, snapshot, restore, or back up cloud server resources after ownership, policy, and cost semantics are defined.

### Billing Extensions

- **COST-24**: System can ingest provider billing data through a direct Hetzner billing API adapter if an official supported endpoint becomes available.
- **COST-25**: Administrator can export adjusted internal attribution summaries for treasurer or reporting workflows.

## Out of Scope

Explicitly excluded from v1.9.

| Feature | Reason |
|---------|--------|
| Live UAT, live Hetzner mutation for evidence, live Steam/Arma proof, authenticated browser evidence closure, or Phase 30 pass/fail classification | Operator direction is to skip UAT until the whole CR is implemented. |
| Marking live Hetzner, Steam, Arma, browser, teardown, or cleanup evidence as passed without captured evidence | Planning must not infer live success from implementation tests. |
| Payment processing, payment-provider billing, customer invoicing, taxes, checkout, or legal invoice generation | CR-0001 defines billing as internal attribution, not payment collection. |
| Multi-provider orchestration | Hetzner remains the first real cloud target until runtime and cleanup behavior are proven. |
| Multi-session cloud workers | One server per worker remains the safe billing, firewall, port, storage, and cleanup model. |
| Headless clients, resource resize, snapshots, backups, marketplace templates, or broad template marketplace behavior | This milestone adds first-party templates and runtime profiles only. |
| Manual SSH or provider-console workflows as the normal path | Provider interaction remains mediated by the control plane and worker model. |
| Treating runtime stop or runtime cleanup as provider cost stop | Hetzner resources remain billable until provider teardown/deletion succeeds. |
| Persisting raw provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, bearer tokens, cookies, OAuth codes, or raw secret-bearing payloads | Security constraints require redaction and allowlisted projections. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud orchestration is validated. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
