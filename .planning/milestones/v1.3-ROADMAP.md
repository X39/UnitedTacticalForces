### Phase 13: Cloud Worker Dispatch And Agent Foundation

**Goal:** Add the worker-facing job protocol and cloud worker agent foundation so a registered cloud worker can safely claim only its own jobs and report progress without direct database access.

**Requirements:** WORK-11, WORK-12, WORK-13, WORK-14, RELY-12

**Success Criteria:**

1. Cloud worker agent can start from bootstrap configuration, register or resume, and persist its worker credential with restrictive local access.
2. Worker-facing API endpoints authenticate with worker credentials and return bounded lifecycle job execution snapshots.
3. Cloud worker claim queries are constrained to the worker's cloud session and game server while local worker behavior remains compatible.
4. Worker heartbeat, progress, log, success, retry, and failure reports update durable job state and audit/log records.
5. DTOs, logs, audits, job errors, and generated client models do not expose Steam, provider, bootstrap, worker, hash, bearer, or secret-bearing command material.

### Phase 14: Arma 3 Install And Configuration Execution

**Goal:** Implement worker-side Arma 3 install/update and configuration rendering using Steam tooling and API-provided execution snapshots.

**Requirements:** RUN-05, RUN-06, RUN-07

**Success Criteria:**

1. Cloud worker validates SteamCMD, DepotDownloader, install paths, permissions, branch, and runtime prerequisites before file mutations.
2. Cloud worker installs or updates Arma 3 dedicated server app `233780` for the assigned game server.
3. Cloud worker downloads selected workshop/mod-pack content for Arma 3 app `107410` and preserves Linux case/symlink behavior needed by the existing controller path.
4. Cloud worker renders server, basic, BattlEye, profile, mission, mod, and launch configuration from an immutable API execution snapshot.
5. Install/update/configuration progress and sanitized tool output are persisted as server logs.

### Phase 15: Arma 3 Process Lifecycle And Runtime Recovery

**Goal:** Let the cloud worker start, stop, restart, observe, and recover the native Linux Arma 3 process while durable API state remains authoritative.

**Requirements:** RUN-08, RUN-09, RELY-10, RELY-11

**Success Criteria:**

1. Cloud worker starts `arma3server_x64` with the generated configuration, selected mods, profiles, BattlEye path, and assigned ports.
2. Cloud worker can gracefully stop and restart the owned Arma 3 process and record terminal exit status.
3. Arma process output, tool output, and post-exit logs are uploaded as persisted game-server logs and update-stream-visible events.
4. API restart preserves cloud runtime job state, progress, logs, lifecycle status, audit records, and owner attribution.
5. Worker restart can recover or report running process, partial install, active job, and cleanup-needed state.

### Phase 16: Runtime Visibility, Cleanup, And Verification

**Goal:** Complete the v1.3 runtime loop with safe admin/server-owner visibility, cleanup semantics, retry gating, and focused verification.

**Requirements:** HETZ-07, CLN-03, VIS-10, VIS-11, RELY-13

**Success Criteria:**

1. Admin and server-owner views show cloud runtime readiness, current job, progress, endpoint, logs, last heartbeat, and last sanitized failure for the allowed scope.
2. Runtime retry and cleanup actions are visible only when persisted state says the action is safe and applicable.
3. Runtime cleanup stops any owned Arma process and removes or marks runtime files without treating runtime stop as provider cost stop.
4. End-to-end cloud runtime behavior covers install, configure, start, update, stop, log, and cleanup through durable lifecycle jobs.
5. Tests cover worker authentication, session-scoped claiming, local compatibility, lifecycle transitions, restart recovery, cleanup state, authorization boundaries, and redaction.
