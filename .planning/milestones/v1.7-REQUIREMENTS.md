# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-18
**Milestone:** v1.7 Operational UAT And Evidence Hardening
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.7 Requirements

Requirements for the operational UAT and evidence-hardening milestone. Each requirement maps to exactly one roadmap phase.

### Operational UAT

- [ ] **OPS-02**: Operator can complete authenticated Aspire/API browser UAT covering live cloud provisioning, metadata sync, plan selection, server-admin navigation, runtime install/start/stop, cleanup, and final provider billable resource count `0`. **Deferred:** UAT remains deferred until the whole change request is implemented across all milestones.
- [ ] **OPS-03**: Operator can record an approval checklist before live provider mutation with approver, token reference, approved project, budget ceiling, resource shape, cleanup window, game server, billing account, and dry-run plan identifiers without storing raw secrets. **Skipped/deferred:** the template exists, but the operator skipped the UAT checks on 2026-06-19 and required fields remain pending.
- [ ] **OPS-04**: Operator can execute or explicitly block live Steam/Arma runtime UAT with documented credentials, environment preconditions, runtime commands, worker registration, logs, lifecycle outcomes, and cleanup evidence. **Deferred:** live Steam/Arma evidence remains operator-gated.

### Evidence And Redaction

- [ ] **EVID-01**: UAT evidence captures provider status, metadata freshness, dry-run plan details, provisioned provider resource identifiers, worker bootstrap/heartbeat, runtime lifecycle, cost visibility, policy status, reconciliation findings, billing owner, audit records, teardown, and cleanup outcome. **Deferred:** requires Phase 30 live execution.
- [ ] **EVID-02**: UAT evidence preserves enough timestamps, IDs, state transitions, and screenshots or command excerpts to independently review the live flow while redacting provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, bearer tokens, and raw secret-bearing provider payloads. **Deferred:** requires Phase 30 live/browser/provider evidence review.
- [ ] **EVID-03**: Cleanup evidence records automated teardown results, any manual cleanup steps, provider-side deletion confirmation, remaining billable resource count, and the final provider billable resource count `0` before OPS-02 can pass. **Deferred:** requires Phase 30 teardown evidence.

### Operational Hardening

- [x] **RELY-24**: UAT-discovered blockers are triaged, fixed when they directly block v1.7 evidence or cleanup safety, or explicitly deferred with rationale and cost/secret-safety impact.

## Out of Scope

Explicitly excluded from v1.7.

| Feature | Reason |
|---------|--------|
| Payment processing, payment-provider billing, customer invoicing, taxes, or legal invoice generation | CR-0001 defines billing as internal attribution, not payment collection. |
| Direct Hetzner billing API integration | v1.7 is operational evidence hardening; v1.6 already supports invoice/export reconciliation. |
| Multi-session cloud workers | One server per worker remains the safe billing, firewall, port, storage, and cleanup model. |
| Multi-provider orchestration | Hetzner remains the first real cloud target until runtime and cleanup behavior are proven. |
| New cloud templates, generic product redesign, or broad frontend wizard redesign | v1.7 fixes evidence blockers only; product expansion should be a separate milestone. |
| Claiming authenticated browser, live Hetzner, or live Steam/Arma UAT as passed without operator evidence | These checks require credentials, provider approval, budget, cleanup window, and final provider-side billable resource verification. |
| Persisting raw provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, or bearer tokens in evidence | Security constraints require all operational evidence and logs to be redacted. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud orchestration is validated. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
