# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-15
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1 Requirements

Requirements for the first milestone: persistent local worker and billing attribution foundation. Each maps to exactly one roadmap phase.

### Lifecycle

- [x] **LIFE-01**: Operator can request configure, install, start, stop, restart, update, collect logs, and delete operations as durable lifecycle jobs.
- [x] **LIFE-02**: Operator receives a job identifier and current job state instead of a stale success snapshot for long-running lifecycle operations.
- [x] **LIFE-03**: Operator can inspect each lifecycle job's state, attempt count, assigned worker, timestamps, and failure reason.
- [x] **LIFE-04**: Operator can see persisted game-server lifecycle state after the API process restarts.

### Worker

- [x] **WORK-01**: Administrator can see a local worker registered with heartbeat, health, and stale/active status.
- [x] **WORK-02**: Worker can claim eligible lifecycle jobs with a lease so duplicate execution is prevented.
- [x] **WORK-03**: Worker can execute existing local Arma 3 controller operations through job handlers without breaking current local hosting behavior.
- [x] **WORK-04**: Operator can recover, retry, or fail jobs abandoned by stale workers according to persisted recovery rules.

### Billing

- [x] **BILL-01**: Administrator can define billing accounts with user ownership as the first supported owner type and an extensible owner kind for future teams, events, or organizations.
- [x] **BILL-02**: Operator must choose or confirm exactly one active billing owner before creating or operating a managed game server.
- [x] **BILL-03**: User can see the active billing owner for a managed game server and its lifecycle jobs.
- [x] **BILL-04**: Administrator can preserve historical billing assignment intervals when ownership changes, a server stops, a server is deleted, or cleanup fails.

### Audit

- [x] **AUDT-01**: Administrator can audit who requested each lifecycle job, when it was requested, and how it completed.
- [x] **AUDT-02**: Administrator can audit billing assignment changes with actor, previous owner, new owner, reason, and timestamp.
- [x] **AUDT-03**: Administrator can audit cleanup failures or abandoned jobs without losing the billing owner responsible for the affected server.

### Visibility

- [x] **VIS-01**: User can see queued, running, succeeded, failed, cancelled, and retrying lifecycle operations in the frontend.
- [x] **VIS-02**: User can open a server details view and see lifecycle state, current job progress, active billing owner, relevant logs, and failure messages.
- [x] **VIS-03**: Administrator can identify stale workers, stuck jobs, and servers requiring manual cleanup from API or frontend surfaces.

### Reliability And Security

- [x] **RELY-01**: API restart does not lose queued, running, failed, or completed lifecycle job truth.
- [x] **RELY-02**: Worker restart does not permanently lose claimed jobs or observed game-server state.
- [x] **RELY-03**: Existing game-server authorization checks are preserved when lifecycle actions become jobs.
- [x] **RELY-04**: Secret values used for Steam, worker execution, and future provider operations are not exposed through frontend DTOs, job errors, or persisted logs.

## v2 Requirements

Deferred to later milestones. Tracked but not in the current roadmap.

### Cloud Provider

- **CLD-01**: Administrator can configure Hetzner project credentials without exposing provider tokens to frontend clients.
- **CLD-02**: User can preview Hetzner server type, region, firewall, IP, and storage assumptions before provisioning.
- **CLD-03**: System can provision and destroy one Arma 3 cloud worker per game server through a provider abstraction.
- **CLD-04**: Administrator can reconcile known resources against Hetzner resources and identify orphans.

### Cost

- **COST-01**: User can see estimated hourly and monthly cost before provisioning or resizing.
- **COST-02**: User can see running cost snapshots while resources exist.
- **COST-03**: Administrator can reconcile internal usage records against provider billing data.
- **COST-04**: UI labels costs as estimated, reconciled, or adjusted.

### Policy

- **POL-01**: Administrator can define spending limits and approval thresholds.
- **POL-02**: System can automatically stop or flag resources that exceed policy.
- **POL-03**: Administrator can configure allowed Hetzner regions and size limits.

### Advanced Runtime

- **RUN-01**: Worker can report dynamic capacity and capabilities for placement.
- **RUN-02**: Cloud workers can optionally support headless clients.
- **RUN-03**: Multiple game sessions can safely run on one worker when billing, ports, storage, and cleanup are proven.
- **RUN-04**: Arma 3 runtime can be packaged with Docker/Compose where networking and BattlEye constraints allow it.

## Out of Scope

Explicitly excluded from the first milestone.

| Feature | Reason |
|---------|--------|
| Hetzner VM provisioning | Durable local worker jobs and billing attribution must be proven before creating real cloud cost. |
| Cloud worker bootstrap and teardown | Depends on provider resource inventory and cleanup semantics from a later milestone. |
| Provider billing reconciliation | Requires cloud resources and provider billing source decisions. |
| Payment processing | CR-0001 defines billing as cost attribution, not payment collection. |
| Spending limits and approvals | Policy enforcement depends on active owner assignment and cost records. |
| Automatic shutdown rules | Requires policy and provider/resource lifecycle integration. |
| Multi-session cloud workers | One server per worker keeps initial billing, ports, firewalling, and cleanup straightforward. |
| Kubernetes or a generic cluster platform | Explicitly excluded as a first target in CR-0001. |
| Removing all local-process support | Migration must keep existing local Arma 3 hosting usable. |
