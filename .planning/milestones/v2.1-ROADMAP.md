## Overview

v2.1 reimagines the React server operations UI (`sources/ReactApp` only) so any member can start a new server or change
an existing one quickly, with clear state, cost, and next steps. It is game-agnostic: Arma 3 and Minecraft are examples,
and the UI is driven by server capabilities. Phases 61-63 lay the foundations and rebuild the fleet and the workspace
shell. Phases 64-65 deliver the two member journeys (start a new server, change an existing one). Phases 66-68 add the
three explicitly requested backend-backed capabilities (accrued cost and cost alerts, worker metrics, auto-stop and
schedules), each as a vertical slice through the control plane, the worker where needed, and its React surface. Phase 69
closes the milestone with the consistency pass and verification.

**Goal**: Members can reach the server section and trust what it shows and asks of them: one shared status model, one cost confirmation for every cost-bearing action, English and German text owned by the React app, and the design tokens and parity checklist the rest of the milestone builds on.
**Depends on**: Nothing (first phase)

  1. A member holding only the `sv` or `sv:view` claim can open the server section and sees exactly the servers they may view, confirmed end to end including the API response.
  2. The same server shows the same status on the fleet, the workspace header, and notifications, and a server that may still incur cost is never labelled off or stopped.
  3. Starting or cost-stopping a server from any current entry point, including an `?action=` deep link, opens one confirmation showing estimated cost, cost owner, and how to stop; an action the member cannot perform is shown disabled with the reason, and a deep link to an unavailable action explains why.

### Phase 66: Accrued Cost & Cost Alerts

**Requirements**: CST-03, CST-04, CST-05, CST-06

### Phase 67: Server Metrics

**Goal**: A user sees how a running server is doing (uptime, players, machine load, and a short history) and sees "unavailable" instead of an invented number when a metric cannot be measured. The worker reports metrics through the worker protocol; the API never samples the game process.
**Depends on**: Phase 63 (fills the Overview metrics area)
**Requirements**: MET-01, MET-02, MET-03, MET-04, MET-05
**Success Criteria** (what must be TRUE):
  1. A running server shows its uptime (running since) in the workspace.
  2. A user sees the current player count where the game exposes it, and an explicit "unavailable" where it does not.
  3. A user sees CPU and memory usage of the server machine.
  4. A user sees a short retained history of these metrics as charts, still present after a page reload.
  5. A stopped server, an offline worker, or a game without player data shows metrics as unavailable, never as zero or a fake value, and metrics reach the control plane only through the worker protocol.

## Cross-Phase Constraints

These apply to every phase in the milestone and are enforced per phase. Their formal requirement closure sits in Phase 69
(FND-06, L10N-03, VER-01..03), so regressions must be caught as each phase lands, not only at the end.

- **React only**: UI changes live in `sources/ReactApp`. `sources/WebApp` and generated Kiota output are never edited.
- **Routes and URLs**: URLs are not a stable contract. Routes, pathnames, and query parameters (`?tab=`, `?action=`,
  `?path=`) may change when a better design needs it; update `sources/Common/Ui/routes.json` and the route tests with
  any change and keep them green.
- **Reuse**: shared components under `sources/ReactApp/src/components`; no raw `<input>` or `<button>` posing as a control.
- **Localization**: every new user-facing string lives in the React-owned English and German JSON (after Phase 61).
- **Parity**: each UI phase updates the Phase 61 parity matrix for the capabilities it touches.
- **Accessibility and mobile**: each UI phase keeps keyboard operation and 320px usability for the screens it touches.
- **Backend phases (66-68)**: follow AGENTS.md. The control plane owns accrued cost, alerts, schedules, and timers; the
  worker reports metrics only through the worker protocol in `sources/HostingContracts`; no game execution in the API;
  Aspire stays a development harness. EF migrations are scaffolded with `dotnet ef migrations add`. Enums use the `E`
  prefix, every type and member has XML documentation, and each top-level type has its own file. Provider tokens, SMTP
  credentials, recipient addresses, and worker credentials never reach frontend clients or unredacted logs. Add focused
  tests for authorization-sensitive actions, job transitions, persistence, and restart recovery.
- **API contract refresh**: backend changes in 66-68 refresh the ReactApp OpenAPI snapshot and generated types. Whether
  that touches generated Kiota output (which is not to be edited by hand) must be verified at plan time.
