# Requirements: United Tactical Forces - Server UX Rework And Generic Game Hosting

**Defined:** 2026-07-03
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.12 Requirements

### Generic Hosting Model

- [x] **GEN-01**: Administrator can inspect every supported game controller as a game-hosting capability with display name, supported hosting modes, configurable runtime fields, lifecycle actions, and cloud compatibility.
- [x] **GEN-02**: User can create a server for any currently supported game through generic server creation contracts without calling Arma-3-named cloud entry, dry-run, review, or repository methods.
- [x] **GEN-03**: User can select generic runtime/profile/template choices whose labels, validation, snapshots, and worker-facing data are scoped by selected game type instead of hard-coded `arma3` filters.
- [x] **GEN-04**: Existing Arma 3 behavior remains available through the generic model without losing mod pack, mission, template, profile, cost, policy, worker, or audit data.

### Guided Creation

- [x] **CREATE-01**: User can start from one server creation entry point and choose game, hosting mode, billing owner, runtime options, and provider template in a clear sequence.
- [x] **CREATE-02**: User can understand the difference between local record, local managed install, cloud planning, dry-run review, provisioning, and running state through task-oriented labels and next steps.
- [x] **CREATE-03**: User can complete a cloud-capable server creation path without manually discovering a separate "cloud plan" concept or jumping between unrelated command pages.
- [x] **CREATE-04**: User receives immediate validation for missing owner, unsupported game/hosting mode, unavailable provider metadata, stale plan, policy gate, cost estimate, and runtime/profile problems.

### Server Workspace

- [x] **WORK-01**: User can open one server workspace that summarizes server identity, selected game, hosting mode, owner, runtime state, latest job, worker/provider state, cost/policy status, and cleanup risk.
- [x] **WORK-02**: User can perform relevant lifecycle, cloud, log, owner, configuration, file, and cleanup actions from the server workspace without searching separate cloud administration pages.
- [x] **WORK-03**: User can distinguish runtime cleanup from provider teardown and can see that provider teardown is the cost-stop action.
- [x] **WORK-04**: Administrator-only fleet/provider diagnostics remain available, but the normal server-owner path does not depend on admin-only cloud inventory pages.

### Operational Feedback

- [x] **OPS-01**: User can see lifecycle jobs with accurate queued, running, retrying, succeeded, failed, cancelled, and stale/recovery states plus timestamps and actor/worker context.
- [x] **OPS-02**: User can start log collection and see the created job, progress, completion/failure result, and refreshed log output without the UI appearing stuck.
- [x] **OPS-03**: User sees explicit server and worker status labels instead of unexplained `n/a` when state is unknown, unavailable, deferred, unsupported, or waiting on a background job.
- [x] **OPS-04**: User receives actionable retry, refresh, policy approval, cleanup, provider teardown, or support next steps for failed or blocked operations.

### Verification

- [x] **VER-01**: Automated tests cover generic game-hosting capability projection, Arma 3 compatibility through the generic model, and absence of new Arma-3-only WebApp repository boundaries.
- [x] **VER-02**: Automated tests cover server creation and workspace states for local record, local managed install, cloud planned, cloud provisioned, running, failed job, stuck/recovered job, log collection, cleanup needed, and provider teardown ready scenarios.
- [x] **VER-03**: Browser-level verification proves the redesigned server path is understandable with mock/fake backend states and without live Hetzner, Steam, Arma, bearer, cookie, or secret material.
- [x] **VER-04**: Redaction and generated-client/repository boundary checks confirm server UX changes do not expose provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, bearer tokens, cookies, or raw secret-bearing payloads.

## Future Requirements

### Game Expansion

- **GAME-01**: Administrator can add a new game product beyond currently supported controllers with cloud/runtime behavior through the generic model.
- **GAME-02**: User can migrate existing Arma-3-specific runtime profiles and mission references into fully renamed generic runtime-profile and mission-reference entities.

### Provider Expansion

- **PROV-01**: Administrator can configure a second real cloud provider after the generic server UX and Hetzner path are stable.
- **PROV-02**: User can compare provider-specific templates, prices, regions, and cleanup semantics for the same selected game.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Live Hetzner provider mutation for UAT | Live testing remains deferred until whole-CR readiness and explicit cost-controlled UAT resumption. |
| New game product support beyond existing controllers | v1.12 makes the model generic before expanding runtime coverage. |
| Payment processing, checkout, or customer invoicing | Billing remains internal attribution and provider-cost visibility. |
| Multi-provider orchestration | Hetzner remains the only real cloud provider in this milestone. |
| Kubernetes or cluster scheduling | The milestone fixes server UX and game-hosting contracts, not the hosting substrate. |
| Removing existing local server support | Local record and local managed flows must remain usable. |
