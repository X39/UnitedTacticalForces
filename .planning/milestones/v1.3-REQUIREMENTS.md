# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-17
**Milestone:** v1.3 Cloud Arma 3 Runtime Execution
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.3 Requirements

Requirements for the cloud Arma 3 runtime execution milestone. Each requirement maps to exactly one roadmap phase.

### Worker Runtime Protocol

- [x] **WORK-11**: Cloud worker agent can start from bootstrap configuration, register or resume with the API, and store its worker credential locally without exposing the raw value.
- [x] **WORK-12**: Cloud worker can claim lifecycle jobs through worker-facing API endpoints and receive a bounded execution snapshot without direct database access.
- [x] **WORK-13**: Cloud worker job claiming is constrained to the worker's registered cloud session and game server, while local worker claiming remains compatible.
- [x] **WORK-14**: Cloud worker can heartbeat during long-running jobs and report progress, logs, runtime status, success, retry, and failure through credential-authenticated API calls.

### Arma 3 Cloud Runtime

- [x] **HETZ-07**: System can install, configure, start, update, stop, and clean up Arma 3 on a cloud worker.
- [x] **RUN-05**: Cloud worker can validate SteamCMD, DepotDownloader, install paths, disk/permission assumptions, selected branch, and runtime prerequisites before mutating files.
- [x] **RUN-06**: Cloud worker can install or update Arma 3 dedicated server files and selected workshop/mod-pack content for the assigned game server.
- [x] **RUN-07**: Cloud worker can render server, basic, BattlEye, profile, mission, mod, and startup configuration from the API-provided execution snapshot.
- [x] **RUN-08**: Cloud worker can start, stop, restart, and observe the native Linux `arma3server_x64` process for the assigned game server.
- [x] **RUN-09**: Cloud worker can collect and upload SteamCMD, DepotDownloader, Arma process, and post-exit logs as persisted game-server logs.

### Safety And Recovery

- [x] **RELY-10**: API restart does not lose cloud runtime job state, progress, logs, lifecycle status, audit records, or billing owner attribution.
- [x] **RELY-11**: Cloud worker restart can recover or report the last known runtime state, including running process, partial install, active job, and cleanup-needed cases.
- [x] **RELY-12**: Steam credentials, provider tokens, bootstrap credentials, worker credentials, credential hashes, and secret-bearing command lines are not exposed through DTOs, generated clients, logs, audits, or job errors.
- [x] **CLN-03**: Cloud runtime cleanup stops any owned Arma process and removes or marks runtime files without treating runtime stop as provider cost stop.

### Visibility And Verification

- [x] **VIS-10**: Administrator and server owner can see cloud runtime readiness, current job, progress, endpoint, logs, last heartbeat, and last sanitized failure for their allowed scope.
- [x] **VIS-11**: Runtime retry and cleanup actions are visible only when persisted state says the action is safe and applicable.
- [x] **RELY-13**: Tests cover worker authentication, session-scoped job claiming, local worker compatibility, install/start/stop/log transitions, restart recovery, cleanup state, authorization boundaries, and secret redaction.

## Future Requirements

Deferred to later milestones. Tracked but not in the current roadmap.

### Cost And Policy

- **COST-05**: User can see running cost snapshots while real cloud resources exist.
- **COST-06**: Administrator can reconcile internal usage records against provider billing data or exports.
- **COST-07**: Administrator can define spending limits, approval thresholds, and automatic shutdown policies.
- **COST-08**: UI labels costs as estimated, reconciled, or adjusted after billing reconciliation exists.

### Cloud Reconciliation And Operations

- **HETZ-08**: Administrator can reconcile known inventory records against real Hetzner resources and identify orphans.
- **OPS-02**: Authenticated Aspire/API browser UAT covers live cloud provisioning, metadata sync, row selection, server-admin navigation, runtime install/start/stop, cleanup, and final provider billable resource count `0`; this remains operator-gated until credentials, budget, provider approval, and cleanup window are supplied.

### Advanced Runtime

- **RUN-01**: Worker can report dynamic cloud capacity and capabilities for placement.
- **RUN-02**: Cloud workers can optionally support Arma 3 headless clients.
- **RUN-03**: Multiple game sessions can safely run on one worker when billing, ports, storage, and cleanup are proven.
- **RUN-04**: Arma 3 runtime can be packaged with Docker or Compose where networking and BattlEye constraints allow it.

## Out of Scope

Explicitly excluded from v1.3.

| Feature | Reason |
|---------|--------|
| Provider reconciliation | Requires a proven runtime lifecycle and a later explicit reconciliation milestone. |
| Running cost dashboard | v1.3 can preserve owner attribution and stop/delete distinctions, but continuous cost display follows after runtime lifetime is proven. |
| Spending limits, approvals, and automatic shutdown | Policy enforcement depends on cost snapshots and runtime lifetime behavior from later milestones. |
| Payment processing | CR-0001 defines billing as attribution, not payment collection. |
| Multi-session cloud workers | One server per worker remains the safe billing, firewall, port, storage, and cleanup model. |
| Docker or Compose as default runtime packaging | Native Linux Arma 3 execution should be proven before container networking and BattlEye edge cases are introduced. |
| Arma 3 headless clients | Useful later, but not required to prove primary server runtime. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud runtime is added. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
| Claiming OPS-02 as passed without operator-gated live evidence | Live UAT requires credentials, provider approval, budget, cleanup window, and final provider-side billable resource verification. |
