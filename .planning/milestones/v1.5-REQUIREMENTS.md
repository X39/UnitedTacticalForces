# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-18
**Milestone:** v1.5 Spending Policy And Automated Shutdown
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.5 Requirements

Requirements for the spending policy and automated shutdown milestone. Each requirement maps to exactly one roadmap phase.

### Cost Policy

- [x] **COST-07**: Administrator can define spending limits, approval thresholds, warning thresholds, and automatic shutdown policies.
- [x] **COST-15**: User can see a policy evaluation result before a billable cloud provisioning, start, restart, update, or future resize action proceeds.
- [x] **COST-16**: Billable cloud actions are allowed, warned, blocked, or marked approval-required based on owner policy, projected cost, current accumulated cost, and reconciliation risk.
- [x] **COST-17**: Authorized approver can approve or deny a policy exception with durable scope, expiration, reason, and audit history.
- [x] **COST-18**: Policy-triggered automatic shutdown can enqueue durable runtime stop or provider teardown jobs only when the configured policy action explicitly permits that action.
- [x] **COST-19**: Policy evaluation treats stale cost metadata, stale reconciliation data, cleanup-needed resources, and unknown billable provider resources as risk inputs instead of silently ignoring them.

### Policy Visibility

- [x] **VIS-16**: Administrator can inspect effective policy, current threshold usage, pending approvals, recent denials, automatic actions, and policy evaluation history.
- [x] **VIS-17**: Server owner can see relevant policy warnings, approval requirements, blocked-action reasons, and automatic shutdown status for cloud servers they are allowed to inspect.
- [x] **VIS-18**: Policy DTOs are available through generated WebApp API clients and repository facades, not raw browser HTTP bridges.

### Reliability And Safety

- [x] **RELY-17**: Policy configuration, evaluation decisions, approvals, denials, automatic-action attempts, and errors survive API restarts.
- [x] **RELY-18**: Policy gates are authorization-sensitive and cannot be bypassed by directly calling provisioning, lifecycle, approval, or automatic-action endpoints.
- [x] **RELY-19**: Automatic shutdown and teardown preserve owner attribution, lifecycle/provider audit history, retry visibility, and deletion-as-cost-stop semantics.
- [x] **RELY-20**: Tests cover policy persistence, threshold math, stale-data risk handling, approval expiry, authorization boundaries, automatic-action job enqueueing, restart-safe idempotency, and secret redaction.

## Future Requirements

Deferred to later milestones. Tracked but not in the current roadmap.

### Cost Reconciliation

- **COST-13**: Administrator can reconcile internal usage records against provider invoice exports or provider billing data when that source is available.
- **COST-14**: Administrator can record explicit adjusted cost corrections after invoice reconciliation.

### Operational UAT

- **OPS-02**: Authenticated Aspire/API browser UAT covers live cloud provisioning, metadata sync, row selection, server-admin navigation, runtime install/start/stop, cleanup, and final provider billable resource count `0`; this remains operator-gated until credentials, budget, provider approval, and cleanup window are supplied.

### Advanced Runtime And Cloud Shape

- **RUN-01**: Worker can report dynamic cloud capacity and capabilities for placement.
- **RUN-02**: Cloud workers can optionally support Arma 3 headless clients.
- **RUN-03**: Multiple game sessions can safely run on one worker when billing, ports, storage, and cleanup are proven.
- **RUN-04**: Arma 3 runtime can be packaged with Docker or Compose where networking and BattlEye constraints allow it.

## Out of Scope

Explicitly excluded from v1.5.

| Feature | Reason |
|---------|--------|
| Payment processing, payment-provider billing, or customer invoicing | CR-0001 defines billing as internal attribution, not payment collection. |
| Claiming invoice-grade provider cost or exact customer balances | v1.5 policy decisions use internal estimated cost snapshots and reconciliation risk, not authoritative provider invoice data. |
| Provider invoice/export reconciliation | This remains future scope after policy behavior is proven against internal cost data. |
| Manual adjusted cost corrections | Adjustments depend on invoice/export reconciliation and are deferred with COST-14. |
| Automatic deletion of unknown orphan provider resources | Unknown resources may not have a proven UTF owner; destructive cleanup remains explicit and audited. |
| OPS-02 live/browser/provider UAT closure without operator evidence | Live UAT requires credentials, provider approval, budget, cleanup window, and final provider-side billable resource verification. |
| Multi-session cloud workers | One server per worker remains the safe billing, firewall, port, storage, and cleanup model. |
| Multi-provider orchestration | Hetzner remains the first real cloud target until policy and cleanup behavior are proven. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud orchestration expands. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
