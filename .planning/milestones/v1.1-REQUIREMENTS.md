# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-15
**Milestone:** v1.1 Hetzner Provider Dry-Run & Resource Inventory
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.1 Requirements

Requirements for the Hetzner provider dry-run and resource inventory milestone. Each requirement maps to exactly one roadmap phase.

### Hetzner Provider

- [x] **HETZ-01**: Administrator can configure Hetzner provider availability and a secret-backed project token reference without exposing token material.
- [x] **HETZ-02**: Administrator can verify Hetzner credentials through read-only provider calls and see sanitized verification status.
- [x] **HETZ-03**: API code can access Hetzner integration through a provider interface that separates read-only metadata, dry-run planning, and future mutating operations.
- [x] **HETZ-04**: Dry-run execution cannot create, update, or delete real Hetzner servers, IPs, firewalls, volumes, or other provider resources.

### Provider Metadata

- [x] **META-01**: Administrator can synchronize and cache Hetzner server types with CPU type, cores, memory, disk, included traffic, deprecation, per-location availability, and price fields.
- [x] **META-02**: Administrator can synchronize and cache Hetzner locations, datacenters, and network-zone details needed for later resource placement.
- [x] **META-03**: Administrator can synchronize and cache Hetzner images and firewall capabilities needed to validate future Arma 3 workers.
- [x] **META-04**: Administrator can see metadata sync freshness, source timestamp, last success, last failure category, and stale-cache warnings.
- [x] **META-05**: Cost and dry-run logic uses cached provider metadata snapshots rather than hard-coded server type, location, or price assumptions.

### Resource Inventory

- [x] **INVT-01**: Administrator can persist a planned cloud game-server session before any real cloud resource exists.
- [x] **INVT-02**: Administrator can persist planned resource inventory records for future VMs, primary or floating IPs, firewalls, volumes, and cloud game-server sessions.
- [x] **INVT-03**: Planned inventory records can link to a game server, provider, region/location, billing owner, and nullable future provider resource identifier.
- [x] **INVT-04**: Planned resource states distinguish dry-run, invalid, ready-for-future-provisioning, provisioned-in-future, cleanup-needed, and orphan-candidate concepts without implying real provisioning in v1.1.

### Dry-Run Planning

- [x] **PLAN-01**: Authorized user can request a dry-run Arma 3 cloud worker plan only after selecting exactly one billing owner.
- [x] **PLAN-02**: User can see the selected or recommended Hetzner server type, region/location, image, and one-Arma-3-server-per-CCX-worker assumption.
- [x] **PLAN-03**: User can see expected Arma 3 port and firewall rules, storage assumptions, and any future SSH, RCON, or observability exposure assumptions.
- [x] **PLAN-04**: User can see validation failures for missing credentials, stale metadata, unavailable server types, unsupported images, invalid ports, missing billing owner, or unsupported worker shape.
- [x] **PLAN-05**: API persists dry-run plans and validation results so administrators can audit what was planned without creating real provider resources.

### Cost Estimates

- [x] **COST-01**: User can see estimated hourly and monthly cost before future provisioning using cached Hetzner metadata and configured storage/IP assumptions.
- [x] **COST-02**: Every dry-run cost estimate is linked to exactly one active billing account or assignment from the v1.0 billing foundation.
- [x] **COST-03**: Cost estimate records preserve currency, VAT/exclusion note, source metadata timestamp, server type, location, storage/IP assumptions, and estimate confidence or freshness.
- [x] **COST-04**: Administrator can audit historical dry-run cost estimates even if provider metadata changes later.

### Admin Visibility

- [x] **VIS-04**: Administrator can see Hetzner provider configuration status, last credential verification time, and sanitized failure state.
- [x] **VIS-05**: Administrator can see cached metadata freshness and sync failures for server types, locations, images, and firewall capabilities.
- [x] **VIS-06**: Administrator can inspect dry-run plans with billing owner, planned resources, estimate assumptions, validation failures, and metadata freshness.

### Reliability And Security

- [x] **RELY-05**: Existing local worker lifecycle operations remain usable while Hetzner provider dry-run features are added.
- [x] **RELY-06**: Provider token material and raw provider authentication errors are not exposed through frontend DTOs, generated client models, logs, audit records, lifecycle job errors, or dry-run validation details.
- [x] **RELY-07**: Tests cover provider metadata persistence, dry-run no-side-effect behavior, billing owner enforcement for estimates, and provider secret redaction.

## Future Requirements

Deferred to later milestones. Tracked but not in the current roadmap.

### Cloud Provisioning

- **HETZ-05**: System can create and destroy real Hetzner servers, firewalls, IPs, and volumes through the provider boundary.
- **HETZ-06**: System can bootstrap a cloud worker on a provisioned Hetzner VM and register it with the API.
- **HETZ-07**: System can install, configure, start, update, and stop Arma 3 on a cloud worker.
- **HETZ-08**: Administrator can reconcile known inventory records against real Hetzner resources and identify orphans.

### Cost And Policy

- **COST-05**: User can see running cost snapshots while real cloud resources exist.
- **COST-06**: Administrator can reconcile internal usage records against provider billing data or exports.
- **COST-07**: Administrator can define spending limits, approval thresholds, and automatic shutdown policies.
- **COST-08**: UI labels costs as estimated, reconciled, or adjusted after billing reconciliation exists.

### Advanced Runtime

- **RUN-01**: Worker can report dynamic cloud capacity and capabilities for placement.
- **RUN-02**: Cloud workers can optionally support Arma 3 headless clients.
- **RUN-03**: Multiple game sessions can safely run on one worker when billing, ports, storage, and cleanup are proven.
- **RUN-04**: Arma 3 runtime can be packaged with Docker or Compose where networking and BattlEye constraints allow it.

## Out of Scope

Explicitly excluded from v1.1.

| Feature | Reason |
|---------|--------|
| Creating real Hetzner resources | This milestone is read-only and dry-run only unless explicitly approved later. |
| Cloud worker bootstrap | Depends on real provisioning and worker credential design from a later milestone. |
| Installing or starting Arma 3 in the cloud | Runtime support follows provider provisioning and worker bootstrap. |
| Provider billing reconciliation | Requires real resource lifetime and a chosen authoritative billing source. |
| Spending limits, approvals, and automatic shutdown | Policy enforcement depends on cost records and real resource lifecycle in later milestones. |
| Payment processing | CR-0001 defines billing as attribution, not payment collection. |
| Multi-session cloud workers | One server per worker keeps initial billing, firewalling, ports, and cleanup straightforward. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud foundations are added. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
