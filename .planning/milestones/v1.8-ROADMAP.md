## Overview

v1.8 productizes the cloud control-plane foundations from v1.0 through v1.7 into a coherent `/servers` workflow. Authorized users can create or select one Arma 3 server, assign an active billing owner, review a non-mutating cloud plan, clear policy gates, provision, operate runtime jobs, tear down provider resources as the cost-stop action, and inspect active or historical cost responsibility. `/servers/cloud` remains the administrator provider/fleet console, and Phase 30 live Hetzner/Steam/Arma UAT remains deferred until a separate operator-approved evidence milestone runs.

## Phase Details

### Phase 33: Guided Entry, Ownership, And Scope Boundaries

**Goal**: Authorized users can begin a server-oriented Arma 3 cloud creation workflow with an eligible server, active billing owner, and complete planning inputs before any billable action.
**Depends on**: Phase 32; Phase 30 remains deferred and out of scope
**Requirements**: CREATE-01, CREATE-02, CREATE-03, CREATE-04
**Implementation boundaries**: Use the `/servers` workflow for owners and authorized operators; keep `/servers/cloud` as the admin console; do not mutate provider resources; do not add payment, invoicing, multi-provider, or multi-session-worker scope.
**Success Criteria** (what must be TRUE):

  1. Authorized user can start the Arma 3 cloud creation path from `/servers`.
  2. Authorized user can create a new Arma 3 game server or select an eligible existing Arma 3 game server for cloud planning.
  3. Authorized user must choose an active billing owner and assignment before dry-run planning or provisioning can continue.
  4. Authorized user can enter size, location, storage, port, SSH or administrative CIDR, modpack, and runtime basics with visible validation.
  5. Owner-facing choices are scoped to the user's authorization and do not expose the admin fleet console as the normal creation path.

### Phase 34: Generated Client And Repository Gate Foundation

**Goal**: Cloud workflow actions return consistent, typed, redacted WebApp results through generated clients and repository facades.
**Depends on**: Phase 33
**Requirements**: COST-03
**Implementation boundaries**: Use generated Kiota clients behind WebApp repository facades; do not add raw browser HTTP bridges; do not hand-edit generated client files; keep raw provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, bearer tokens, and secret-bearing payloads out of user-visible results.
**Success Criteria** (what must be TRUE):

  1. User-facing cloud planning, policy, provisioning, lifecycle, teardown, cost, and audit actions surface consistent success, policy, validation, and failure states through repository-backed WebApp code.
  2. Policy gate responses preserve decision identity and continuation details needed for follow-up actions without exposing raw secret-bearing payloads.
  3. User-visible cloud workflow views show only allowlisted fields and never display provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, bearer tokens, or raw secret-bearing payloads.

### Phase 35: Dry-Run Planning And Review

**Goal**: Authorized users can generate and review a non-mutating Arma 3 cloud plan before any provider resource is created.
**Depends on**: Phase 34
**Requirements**: PLAN-01, PLAN-02, PLAN-03
**Implementation boundaries**: Dry-run remains non-mutating; provider provisioning is not available from stale, invalid, mismatched, superseded, or owner-mismatched plans; review content is sanitized and cost-source labeled.
**Success Criteria** (what must be TRUE):

  1. Authorized user can generate a non-mutating Arma 3 cloud dry-run plan for the selected game server and billing owner.
  2. Authorized user can review planned resources, assumptions, firewall rules, validation failures, metadata freshness, hourly estimates, monthly estimates, and cost source labels.
  3. Authorized user is blocked from provisioning stale, invalid, mismatched, superseded, or owner-mismatched dry-run plans.
  4. Authorized user can regenerate a plan when inputs, owner assignment, metadata freshness, or validation state makes the reviewed plan unusable.

### Phase 36: Policy Gate And Approval UX

**Goal**: Authorized users and approvers can resolve spending policy gates as explicit workflow states before billable actions continue.
**Depends on**: Phase 35
**Requirements**: POLICY-01, POLICY-02, POLICY-03
**Implementation boundaries**: Consume existing policy gate and approval foundations; do not redesign policy administration; do not auto-bypass warnings, approvals, denials, expiration, scope, or decision identity; do not mutate provider resources before a matching gate state allows it.
**Success Criteria** (what must be TRUE):

  1. Authorized user can see allow, warning, approval-required, and denied policy outcomes as actionable workflow states.
  2. Authorized user can acknowledge warning decisions or follow approval next steps only for the matching policy scope, expiration, and decision identity.
  3. Authorized approver can approve or deny provisioning and teardown requests from the cloud server workflow with durable audit context.
  4. Expired, denied, mismatched, or missing approvals keep the requested billable action blocked and show the user the next required action.

### Phase 37: Provisioning, Runtime Operation, And Teardown

**Goal**: Authorized users can provision reviewed plans, operate cloud runtime jobs, and tear down provider resources while seeing cost-stop and cleanup boundaries clearly.
**Depends on**: Phase 36
**Requirements**: OPS-01, OPS-02, OPS-03, OPS-04
**Implementation boundaries**: Keep the first cloud shape to one Arma 3 server per Hetzner-backed worker; do not add multi-provider or multi-session worker scope; keep provider teardown as the explicit cost-stop boundary; do not claim live Phase 30 UAT closure.
**Success Criteria** (what must be TRUE):

  1. Authorized user can provision provider resources from the reviewed valid cloud dry-run plan and see session, resource, bootstrap, and worker status.
  2. Authorized user can operate install, update, start, stop, restart, collect logs, and runtime cleanup actions with durable job progress and sanitized failure visibility.
  3. Authorized user can tear down provider resources through an explicit cost-stop action that is separate from runtime stop, runtime cleanup, and local server deletion.
  4. Authorized user can see retryable, cleanup-needed, orphan-risk, partial-failure, and remaining-billable-resource states after provisioning or teardown.
  5. Runtime status and provider teardown status remain visible enough for the user to understand which resources may still cost money.

### Phase 38: Cost Responsibility, History, And Audit Visibility

**Goal**: Authorized users can inspect active and historical cost responsibility for cloud sessions without confusing attribution with payment or customer invoicing.
**Depends on**: Phase 37
**Requirements**: COST-01, COST-02
**Implementation boundaries**: Show internal cost attribution only; do not add payment processing, customer invoicing, taxes, checkout, or legal invoice generation; preserve authorization-scoped cost, assignment, reconciliation, adjustment, cleanup-risk, and audit projections.
**Success Criteria** (what must be TRUE):

  1. Authorized user can inspect active cloud cost responsibility with owner, assignment, estimated labels, reconciled labels, adjusted labels, reconciliation status, and cleanup risk.
  2. Authorized user can inspect historical cloud cost responsibility after ownership transfer, provider teardown, runtime cleanup, or local server deletion.
  3. Authorized user can see relevant lifecycle, cost, policy, and audit context for scopes they are allowed to inspect.
  4. Cost responsibility views distinguish internal attribution from payment, customer invoicing, and checkout workflows.
