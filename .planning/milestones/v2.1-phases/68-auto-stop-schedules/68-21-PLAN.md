Product decision for G-68-3 (orchestrator default adopted; state it in the summary for the user):
- Waiting has no fixed time limit. A due start waits as long as a stop or terminate of the same server is actively in flight, not only for the 15 minute StartGraceWindow. StartGraceWindow keeps its meaning only for an occurrence first seen late (platform not running).
- Bound: a waiting start ends without a start when (a) the stop fails and waits for a person, (b) the same rule's next occurrence comes due while the stop is still running (the newer occurrence takes over, so at most one start per rule waits and a stuck stop can never release a backlog of starts), or (c) the rule's action, days, time or time zone is changed after the occurrence. All three record SkippedStopUnfinished with the real blocker. Removing the rule deletes its run rows (existing cascade).
- At the moment the stop has finished, the normal checks decide: consent for the current cost owner (SkippedConsent), a server that is running again because someone started it (SkippedRunning), another active non-stop job (SkippedBusy), the cost owner's ability to pay (SkippedCost), and a refusal of the lifecycle service (SkippedBusy with its reason). Each closes the same run row.
- D-AUTO-2 stays intact: a failed stop is never escalated; the waiting start is closed instead.

Design (Claude's discretion within the decision above):
- The existing unique run row (ScheduleFk, OccurrenceAt) becomes the durable waiting marker: outcome WaitingForStop, LifecycleJobFk null, Details "waiting for the stop of the server to finish", RecordedAt = the instant waiting began. It is the only outcome the runner later replaces; every other outcome stays final. Exactly once holds because the waiting row is read and turned into Started (or a skip) only under the server-row lock in the same transaction that queues the job.
- Open waiting rows are re-collected each pass by querying run rows of the server with outcome WaitingForStop, independent of the watermark. The watermark logic stays as it is and is driven only by newly collected occurrences, so a waiting server causes no extra write per pass.
- "Stop in flight" means: a LifecycleJob of the server with Kind Stop or Terminate and Status Queued, Running, RetryPending or WaitingForWorker (any deployment, so the short window after TimeStampResolved and before the job is marked Succeeded counts too), or an AutomationPendingStop of the server with Status Pending, StopsAt at or before now, on the server's unresolved deployment (a stop and a start that come due in one catch-up pass; the evaluator executes that pending stop in the same pass).
- "Stop failed" means: the server has an unresolved deployment and its latest Stop or Terminate job (by TimeStampCreated, then Sequence) has Status Failed.
- No audit entry is written when waiting begins (it is a transient state, visible on the rule); the late Start carries `; WaitedForStop=true` in its audit note, and every close writes the usual ScheduledRunSkipped entry through the ledger.
