# Phase 68 - UI Design Contract

> Visual and interaction contract for Phase 68: Auto-Stop & Schedules.
> Generated by gsd-ui-researcher (autonomous mode: `68-CONTEXT.md` has no locked decisions, every decision below is made at the researcher's discretion and recorded with its rationale), verified by gsd-ui-checker.
> Scope: `sources/ReactApp` plus the API, shared-contract and database changes this feature needs (`AGENTS.md`: the API is not a frozen contract). The scheduler, the idle timer, the warning delivery and the durable stop job are control-plane work with no UI contract beyond the data semantics below. `sources/WebApp` (legacy Blazor) is not updated and the generated Kiota client under `sources/WebApp/UtfApi` is never hand-edited. Regenerate the OpenAPI snapshot and `src/generated/api.ts` (`npm run contracts:generate`). No new route and no new `?tab=` value: everything lives in the existing workspace sections.
> Requirements covered: AUT-01, AUT-02, AUT-03, AUT-04 (the React surfaces of them). AUT-05 and AUT-06 are control-plane guarantees; this file defines how they become visible (Activity entries, trigger lines, the "Last run" outcomes).
> Inherits without change: `61-UI-SPEC.md` (design system, spacing, typography, color, state and cost model, shared cost confirmation, unavailable-action pattern, localization, token rules, copy rules, German "du"), `63-UI-SPEC.md` (workspace shell, shell notice slot, Settings section and its reserved `data-slot="automation"` panel, Activity sentence maps, progress strip, "at most one gold control in the workspace view"), `65-UI-SPEC.md` (draft-then-save conventions, `useLeaveGuard`, read-only notice, banned generic button labels) and `66-UI-SPEC.md` (alert surfaces, alert channels, status line reserve, the 3 s anti-flicker rule, "the browser displays, it never calculates", no `refetchInterval`, toast discipline). This file only adds or overrides what automatic shutdown and schedules need. Anything not stated here is exactly as in Phases 61, 63, 65 and 66.

An owner should be able to say "stop this server when nobody is on it", "never run longer than six hours" and "start it Friday at 18:00 and shut it down at midnight", see in one glance what is set and what will happen next, and trust that a member who is playing is warned before the server goes away. The page stays a quiet working tool: the times shown are exactly the instants the control plane sent, an automatic stop is described in the same words as a manual one, and what has not happened yet is never dressed up as a fact. The browser displays; it never schedules, counts idle time or computes a stop instant.

## Research Findings That Shape The Contract

Verified in code on 2026-11-22. They resolve the discretion items in `68-CONTEXT.md` and the Phase 68 carry-over list in `ROADMAP.md`.

| Question | Finding | Consequence |
|----------|---------|-------------|
| Where does the automation UI live? | `SettingsSection.tsx` renders `SlotPlaceholder variant="panel" slot="automation"` with `Server_Settings_AutomationTitle` and the muted `Server_Settings_AutomationUnavailable` line, between Credentials and the Server record panel. | The placeholder is replaced by `AutomationPanel` at the same position. `data-slot="automation"` moves onto the new panel `section`. DOM order of Settings is unchanged: Mods, Configuration, Credentials, Automation, Server record. |
| Is Settings a draft-then-apply surface? | Yes, but only for configuration, mod pack and credentials: `ServerChangeDraftProvider` stages edits, the sticky `PendingChangesBar` offers Review changes and Discard changes, and `useLeaveGuard` holds navigation while `count > 0`. Automation settings are not staged for the next start: they are control-plane records that take effect when saved. | Automation has its own draft and its own Save row inside its panel (the Phase 66 save-row pattern), not an entry in the staged set and not the pending bar. Both drafts share one leave dialog (see Interaction Contract) because two independent `useBlocker` instances must not each open a dialog. |
| Can the page already tell who may change what? | `GameServer` carries `canModify`, `canManageSecrets`, `canManageCostAlerts` (nullable, present only for viewers who may see the owner's alert settings), `costOwnerName`, `isArchived`. There is no automation flag. | A new `canManageAutomation` flag on the server DTO (A1). The UI only reads the flag; it never infers the right from `canModify` or from names. |
| Which form controls exist? | `TextField` (with `trailing`), `SelectField` (native `select` with `optgroup`, styled by `form-field__control--select`, the "app's existing styled select"), `CheckboxField`, `RadioGroupField` (fieldset, per-option `help`, `disabled`), `TextAreaField`; `Disclosure` is a native `<details>` that the owner dislikes (Phase 65 UAT). | Every control is one of these. No `<details>`, no new select, no raw `<input>`. The time zone is the only select; action choice is a `RadioGroupField` (two options), weekdays are a `CheckboxField` group, times are `TextField type="time"`. |
| What does the idle signal look like? | Phase 67 `metricsModel.ts` already carries `playersUnavailableReason` with the code `game-does-not-report` (`Server_Metrics_Reason_NoPlayers`) next to transient reasons. | Idle detection availability has two layers that must not be confused: structural (the game never reports players, so the option is disabled with a reason) and transient (the count is unavailable right now, so the timer waits and the status line says so). The control plane never shuts a server down on an unknown signal. |
| How are alerts and warnings delivered today? | Phase 66: in-app banner and profile-menu rows from an alert record list fed by the socket, one toast per newly arrived record id, Discord DM and email per the cost owner's channel flags, shared recipients rule. | The pre-stop warning reuses the same channels and the same in-app surfaces (menu row, toast) as a second alert kind, plus a workspace notice that every viewer sees (members who are playing must know). The channel choice stays on the cost alerts page; this phase links to it and adds no second channel setting. |
| How is the activity actor shown? | `buildActivityEntries` renders "Requested by {{actor}}" from the job and operation actor projection; null actor renders "The platform". The job sentence map is keyed by status and job-kind label only. | An automatic job needs a trigger line instead of an actor line. The job DTO gains a `trigger` (kind plus the limit that applied); the actor line is replaced by `Server_Activity_Trigger_*`. The sentence maps stay unchanged: an automatic stop is the same "Shut down and stop billing" job. |
| Is there a client clock hook? | `useNow(intervalMs)` (`@/app/useNow`), `useDelayedDisconnect()`, `formatInstant(instant)` (`@/features/hosting/costAlertFormat`), `formatRelativeTime(value, now)` (`@/app/format`). | Relative lines refresh on `useNow` only. No other timer exists in the automation files; a source-scan test asserts it as in Phases 66 and 67. |

## Decisions

| Id | Decision | Rationale |
|----|----------|-----------|
| D-01 | Automation settings live in one panel in the Settings section, at the reserved slot. No new tab, route or page. | Phase 63 reserved the slot and the section order; URLs are not a stable contract but a new route is not needed. Deep link: `?tab=settings#server-automation` (the panel `section` has `id="server-automation"` and `tabIndex={-1}`; on arrival with data loaded it scrolls into view with `behavior: "auto"` and focus moves to the panel `h2`). |
| D-02 | The right to change automation is the API flag `canManageAutomation`. Viewers without it see every value with every control disabled, one notice at the top of the panel explains why, and no Save row renders. | Roadmap success criterion 1 ("disabled with the reason"). One notice instead of a reason under each control follows Phase 65 and 66 and keeps the panel calm. Who gets the flag (server owner, cost owner, administrators) is the API's decision (A1). |
| D-03 | The panel has its own draft and its own Save row with the status line reserved, `variant="primary"` (not gold), and a Discard changes ghost button. | Phase 63 allows at most one gold control in the workspace view (the header Start action); the Settings section also shows the pending bar. A gold Save here would be a second gold control. |
| D-04 | Units and ranges: idle shutdown in whole minutes (5 to 1440, default 30 when switched on), maximum runtime in whole hours (1 to 168, default 6 when switched on), at most 8 schedules. The API enforces the same limits and sends them in the settings (`limits`), so the UI never hard-codes them. | Idle time is naturally minutes, a runtime cap is naturally hours; free numeric fields with a stated range need no select. A schedule limit keeps the form and the control-plane scan bounded (A8). |
| D-05 | Schedules are weekly recurring rules: one action (Start server or Shut down and stop billing), one or more weekdays, one wall-clock time. One time zone per server. No one-off dates and no start-and-stop "window" pairing. | A weekly rule covers the event-night use case with the smallest vocabulary; two independent rules express a window without a pairing model. One-off dates are recorded as out of scope. |
| D-06 | Time zone: a `SelectField` with region `optgroup`s built from `Intl.supportedValuesOf("timeZone")` plus `UTC`, defaulting on first save to the viewer's resolved browser zone. The saved zone is always present as an option even when the runtime does not list it. | The zone must be explicit because the control plane evaluates the rules, not the browser. The grouped native select is the Phase 64 precedent and keeps a 400-entry list inside the native popup. |
| D-07 | Idle shutdown is capability-driven: when the API says the game cannot report players (`idleShutdown.available` false), the checkbox is disabled with the structural reason; a transient unknown count never disables the control, it changes the live status line. | Phase 61/64 principle: the UI is driven by server capabilities. Honest degraded state instead of a control that silently never fires. |
| D-08 | Scheduled starts need an explicit cost consent: saving a draft that adds or changes a Start rule opens a confirmation dialog (cost owner, per hour, per month, number of start rules). The API records the consent bound to the cost owner; when the cost owner changes, scheduled starts pause and the panel offers "Confirm scheduled starts". | The roadmap asks for cost consent and the cost-owner-can-pay check for a scheduled start. A start the owner never confirmed must not spend money. Stop rules, idle shutdown and maximum runtime save money and need no consent. |
| D-09 | The pre-stop warning is (1) a workspace notice for every viewer of the server, first in the shell notice slot, not dismissible, and (2) an alert record of a second kind delivered through the Phase 66 channels, so the profile menu row, the toast, Discord and email follow the cost owner's channel settings. No postpone or "keep running" action. | Members who are on the server must see the warning even when they are not the recipient of the alert; the owner is reached wherever they are. A postpone control would need new semantics (does it reset the idle timer, the runtime cap?) outside AUT-01 to AUT-06; the notice links to the settings instead. |
| D-10 | The warning lead time is API-owned (default 10 minutes, A9) and shown as a fact in the panel. It is not user-configurable. | One number to explain and test; avoids an interaction with the minimum idle time. |
| D-11 | An automatic job is the same lifecycle job as a manual one: same labels, same progress strip, same Activity sentences. Only the meta line changes (trigger instead of actor) and the audit gains seven kinds. | Roadmap success criterion 4 and the closed-vocabulary rule: "Shut down and stop billing" is the one phrase for the cost-stop (63 D-12). |
| D-12 | The panel opens with an always-rendered three-row status list (Idle shutdown, Maximum runtime, Next scheduled action) that shows the saved state, never the draft. | Nothing shifts when the server starts or stops, and the owner sees the effect of what is saved. Mirrors the cost strip rule that rows always render with a fallback. |
| D-13 | Overview gets one optional fact row "Automation" (up to two short lines) only when something is configured, with a link to the panel. | A server that will stop by itself must not be a surprise for members who only open Overview. No empty row and no placeholder when nothing is set. |

## Data The UI Needs (API changes)

The contract names the semantics; exact names, DTO shapes, routes and frame types are the planner's call. Enums are `E`-prefixed in C# (AGENTS.md). Regenerate the OpenAPI snapshot and the clients, add tests in the owning layer.

| Need | Where | Semantics |
|------|-------|-----------|
| Automation block | server DTO: one `automation` object, or absent | Absent means the API does not offer it for this server (older API, unsupported game): the panel shows the unavailable state, never an empty form. |
| Settings | `automation.settings` | `idleShutdownEnabled`, `idleShutdownMinutes`, `maxRuntimeEnabled`, `maxRuntimeHours`, `timeZone` (IANA id), `schedules[]` with `id`, `action` (`Start` or `Stop`), `days[]` (ISO weekday 1 to 7, Monday 1), `time` (`HH:mm` wall clock), `nextRunAt` (instant or null), `lastRun` (`at` instant, `outcome` code) or null, and `version` (concurrency token). Disabled values keep their number so toggling off and on does not lose it. |
| Limits and capabilities | `automation.limits`, `automation.idleShutdown` | `idleMinutesMin/Max`, `maxRuntimeHoursMin/Max`, `maxSchedules`, `warningLeadMinutes`, and `idleShutdown.available` (structural, false when the game cannot report players). |
| Live status | `automation.status` | `idle.state` (`NotRunning`, `PlayersOnline`, `Idle`, `Unknown`), `idle.since` and `idle.stopsAt` instants, `maxRuntimeStopsAt` instant or null, `nextScheduled` (`action`, `at`) or null, `pendingStop` or null. Every instant is calculated by the control plane; the browser never adds minutes to a timestamp. |
| Pending stop | `automation.status.pendingStop` | `reason` (`Idle`, `MaxRuntime`, `Schedule`), `stopsAt` instant, `limit` (the minutes or hours that applied, a snapshot so the sentence does not depend on current settings). Present from the moment the warning is due until the stop job exists or the stop is cancelled. |
| Scheduled-start consent | `automation.startConsent` | `state`: `NotRequired` (no start rule), `Given`, `Needed` (the cost owner changed or consent was never given). The settings PUT carries `startConsent: true` when the viewer confirmed in the dialog; the API records who, when and the hourly estimate shown, and writes an audit entry. A Start rule is not run while consent is `Needed`. |
| Save | `PUT` on the settings | Replaces the whole settings object with `version`; validation errors are field-addressable; a stale `version` returns 409; a lost right returns 403. |
| Flag | server DTO | `canManageAutomation` (A1). |
| Job trigger | lifecycle job DTO | `trigger`: `Manual`, `Idle`, `MaxRuntime`, `Schedule`, with `limit` (minutes or hours) for `Idle` and `MaxRuntime`. Absent means `Manual`. The job actor projection stays as in Phase 63 and is unused when a trigger is not `Manual`. |
| Alert kind | Phase 66 alert record | A `kind` (`CostThreshold`, `AutoStop`). An `AutoStop` record carries `stopsAt` and `reason`; the API resolves (clears with a dismissal frame) it when the stop is cancelled or the stop job has started. The viewer may also dismiss it, which hides only the record, never cancels the stop. |
| Audit kinds | hosting operation kinds | `AutomaticStopWarned`, `AutomaticStopRequested`, `AutomaticStopCancelled`, `ScheduledStartRequested`, `ScheduledRunSkipped`, `AutomationSettingsChanged`, `ScheduledStartsConfirmed`. `ScheduledRunSkipped` carries the reason in its API summary (`ApiText`). |

If an addition is not yet available when a plan lands, the UI degrades without inventing data: no `automation` block renders the unavailable state and no Overview row; no `pendingStop` renders no notice; no alert `kind` means stop warnings are not shown as menu rows; no job `trigger` keeps the actor line.

## Surface Anatomy

Visual anchor: on Settings, the Automation panel heading and its always-rendered status list are the anchor of the panel. In the workspace, the automatic-shutdown notice (`StatePanel kind="warning"`, shown while `pendingStop` is present) outranks every other notice and sits first in the notices area. ### 1. Settings: the Automation panel (AUT-01, AUT-02, AUT-03)

Position: slot 4 of Settings (after Credentials, before Server record). `<section id="server-automation" tabIndex={-1} aria-labelledby className="workspace-panel" data-slot="automation">`. Panel padding, surface, border and elevation are the shared `workspace-panel` ones (`--utf-space-lg`, `--utf-space-md` at <= 520px).

## Interaction Contract

### Draft and save (D-03)

- One in-memory draft of the settings (`idleShutdownEnabled`, minutes, `maxRuntimeEnabled`, hours, `timeZone`, rules). React state only: never written to storage, the URL, router state or a log (source-scan test as in Phases 65 and 66).
- Dirty means the normalized, sorted draft differs from the saved settings (numbers compared as parsed integers, disabled numbers ignored, rules compared by id and normalized day set, a time compared as `HH:mm`). A new rule with no days and no time is not dirty and is invalid on a save attempt (blank rules are not silently dropped).
- Parsing (`automationModel`): trim; digits only for minutes and hours; whole numbers; range from `limits`. Time from a `type="time"` input is `HH:mm`; an empty value is "Enter a time". Validation messages appear after blur or a save attempt, never while the first character is being typed. A disabled number is neither validated nor sent as enabled.
- Save validates everything; on errors nothing is sent, the plural invalid status shows and focus moves to the first invalid field. On success the draft is replaced with the returned settings, the saved status and toast show, and focus stays on Save. On 409 the draft is kept, the conflict status and Reload show; Reload replaces the draft only after the viewer chooses it. On 403 the forbidden status shows and the panel turns read-only once the refetched server no longer has `canManageAutomation`.
- Enter inside a field never saves (the panel is not a `<form>` submit surface); the only way to save is the Save button. Escape does nothing special.
- While saving every control is `aria-disabled` and focusable, text inputs are `readOnly`, change handlers ignore input, and no extra reason text appears.
- When the saved settings change elsewhere while the panel is pristine, the draft follows them; when dirty the draft is kept and the next save returns 409.

### Leave guard (shared with the staged changes)

`SettingsSection` owns one `useLeaveGuard` whose `dirty` is `count > 0 || automationDirty`, with the existing `leavesWorkspaceSection(..., "settings")` predicate. `AutomationPanel` reports its dirty flag upward and registers a `discard` callback. The leave dialog body is chosen by what is dirty: staged changes only keeps `Server_Change_Leave_Body` and the Review action; automation only uses `Server_Automation_Leave_Body` without the Review action; both use `Server_Automation_Leave_BodyBoth`, keep Review (it stays and opens the review of the staged changes), and Discard and leave discards both drafts. Stay here is the initial focus. No second blocker is registered.

### Schedule editing

- Add moves focus to the first radio of the new rule and announces "Schedule added." in the panel's polite region. Remove moves focus to the first field of the next rule, else the previous rule, else the Add button, and announces "Schedule removed." Rule numbers renumber on removal.
- New rule defaults: action Start server, no days, no time. Rules keep entry order while editing (no re-sorting under the cursor); after a successful save the list is shown ordered by the first selected day, then time.
- Selecting an action never auto-changes days or time. The summary line updates as the draft changes and is not a live region.
- Duplicate detection compares every pair of rules per day and time; both rules show the duplicate error under their time field.

### Consent flow (D-08)

Save with a new or changed Start rule opens the consent dialog instead of sending. Confirm sends one PUT with `startConsent: true`; while it is pending both buttons are blocked (`ConfirmDialog` busy); success closes the dialog, shows the saved status and toast and returns focus to Save; failure keeps the dialog open with the error line (conflict keeps the draft and closes nothing until the viewer chooses). A save without any new or changed Start rule never opens the dialog.

### Live behavior and freshness

- The status list, the rule run lines, the notice and the Overview fact render the server DTO. They refresh through the existing exact `server(id)` invalidation (socket frame or the 30 s fallback poll while a job is active) and on "Refresh server". No new socket, no `refetchInterval`, no `setInterval` other than `useNow` exists in the automation files; a source-scan test asserts both.
- The notice's relative line is the only element that ticks (`useNow(30_000)`); no other text changes on a clock. The stale line is not repeated here: the workspace `LiveBadge` and the Phase 66 paused line already carry freshness.
- A `pendingStop` that disappears because the stop job started is not a cancellation: the progress strip replaces the notice and no toast shows. A `pendingStop` that disappears with no stop job shows the cancellation toast once.

### Keyboard and focus

- Every interaction is reachable by keyboard in DOM order; no positive `tabindex`; the focus ring is `--utf-focus-ring`. Disabled controls in the read-only panel are native `disabled` (the single notice at the top is the visible reason, linked by `aria-describedby` from each control group), consistent with the Phase 66 read-only page.
- The deep link `?tab=settings#server-automation` scrolls the panel into view and focuses its heading; the notice link and the Overview link use it. Focus is never moved by a notice appearing.

## Accessibility and Responsive Contract (FND-06 gate for this phase)

- Landmarks and headings: the panel is a `section` labelled by its `h2`; sub-sections use `h3`; rule headings are not headings (they label a group); the notice title is an `h2` inside its status region. No skipped levels.
- Groups: the weekday group and the action group are `fieldset`s with legends; every control has a visible label bound to it; hints and errors are linked through `aria-describedby`; errors are `role="alert"` and set `aria-invalid`.
- The status list is a plain `dl`, not a live region. Live regions: the notice (one polite status region, relative line `aria-live="off"`), the panel's add and remove announcements, the save status line (`role="status"`, errors `role="alert"`), and toasts (`role="status"`). No nested live regions otherwise.
- Disabled-vs-unavailable: read-only panels use native `disabled` plus the notice; the idle structural reason is visible text linked by `aria-describedby`; no `title`-only reasons.
- Icon-only controls: none (every button has visible text). Visible text is contained in each `aria-label`.
- Touch targets: 44px at <= 800px for inputs, selects, checkbox rows, radio rows, weekday cells and buttons; minimum 24px everywhere.
- Color is never the only signal: the notice carries a title and icon, last-run outcomes are sentences, selected weekdays are checked boxes.
- `Intl` for every time, date, list and relative time; `type="time"` renders in the browser's locale format and submits `HH:mm`; German amounts and times use the German formats.
- 320px: no horizontal page scroll; the panel, rule blocks, day grid, hints and buttons wrap; the notice and the dialog fit; verified at 320x568 and 390x844 in English and German.
- Automated check: an `axe` scan (`@axe-core/playwright`, already a dev dependency) of the Settings section with the panel (pristine, dirty, invalid, read-only, consent-needed, unavailable), the workspace with the notice, and the open consent dialog; zero violations at WCAG 2.1 AA tags; each scan asserts at least one rule evaluated and records unmocked requests as in Phase 61 plan 13.
