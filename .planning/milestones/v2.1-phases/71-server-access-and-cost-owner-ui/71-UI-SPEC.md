# Phase 71 - UI Design Contract

> Visual and interaction contract for Phase 71: Server Access and Cost Owner UI.
> Generated by gsd-ui-researcher (autonomous mode: `71-CONTEXT.md` has no locked decisions, discuss was skipped, every decision below is made at the researcher's discretion from the code as it stands on 2026-11-26 and recorded with its rationale).
> Scope: `sources/ReactApp` plus the additive API changes listed in the API Contract section (the API is not frozen, `AGENTS.md`). `sources/WebApp` (legacy Blazor) is not touched; every API change is additive, so its compatibility holds.
> Inherits without change: `61-UI-SPEC.md` (tokens, four type sizes, two weights, localization and copy rules, German "du"), `69-UI-SPEC.md` (closed control list, header kinds, dialog shell geometry, banned dismiss labels, accent reserved list, token-only CSS guard, FND-06 and L10N-03 gates) and `70-UI-SPEC.md` (drawn controls, `SwitchField`, segmented `RadioGroupField`, `Disclosure`, `SettingsPanel`, button variants, `ConfirmDialog` conventions). This file only adds or overrides what access management and the cost-owner transfer need. Anything not stated here is exactly as in Phases 61 to 70.

The Phase 61 parity matrix lists no React consumer for `GET /game-servers/{id}/access`, the four grant and revoke endpoints and `PUT /game-servers/{id}/cost-owner` (v2.1 audit integration finding 2). The legacy Blazor server page never managed either, so there is no screen to port: this phase designs both from the existing API and the Phase 70 building blocks. It adds two Settings panels (Access, Cost owner), one shared search picker, and no new color, size or weight.

## Research Findings That Shape The Contract

Verified in the code on 2026-11-26 (read-only; no build was run).

| Question | Finding | Consequence |
|----------|---------|-------------|
| Who may manage access | `GET /access` and the four POSTs are `[Authorize(Claims.ResourceBased.Server.ManageAccess)]` and then check `ServerManageAccessRequirement.HasExactPermission`: `adm`, `adm:sv`, `adm:hosting`, `sv` on this server, or `sv:manage-access` on this server. `sv:modify` does not imply it. `GameServerDto` carries `canModify`, `canManageSecrets`, `canRevealSecrets` but no manage-access flag. | New API field `canManageAccess` (same exact rule). The React `FullUser.claims` cannot answer it: it holds neither role claims nor the administrator-versus-resource distinction the API applies. |
| Permission model | Eight allowlisted claims: `sv`, `sv:view`, `sv:operate`, `sv:modify`, `sv:manage-access`, `sv:delete-data`, `sv:manage-secrets`, `sv:reveal-secrets`. `HasServerPermission` is: hosting administrator, or `sv` on this server, or the exact claim. There is no implication between the others: `sv:operate` without `sv:view` cannot even list the server. Grants are idempotent (grant of a held claim and revoke of a missing one return 204 and write no audit record). | Permissions are independent switches, `sv` (Full control) shows the rest as included, and a subject who holds something without View gets a visible warning. Per-permission calls are atomic, so toggles apply immediately with no staging layer. |
| What the access list returns | `GameServerAccessDto { allowedPermissions[], users[{userId, nickname, permissions[]}], roles[{roleId, title, description, permissions[]}] }`, users ordered by nickname, roles by title; only subjects with at least one exact grant on this server are listed. Administrators are never listed (their access is the global `adm` claims). The list has no role member count, and nicknames are not unique (`User.Nickname` is a plain indexed column). | Display names exist, so the list needs no extra lookup. A role's reach and duplicate nicknames need two small additive fields (`memberCount`, `detail`). The panel states that administrators are not listed. |
| Finding someone to grant | There is no candidate search on the server routes. `ConfigurationProfilesController` has `access/users/options` and `access/roles/options` (ILike search, take 1 to 50, verified and not banned users) behind `ConfigurationProfileAccessSection`, which renders the matches as `ActionButton role="option"` inside a plain `div role="listbox"` and shows the user's GUID as the secondary line. | Server routes get the same two endpoints, with server-side exclusion of subjects who already hold a grant (so `take` stays honest). The picker becomes a shared, properly built combobox (`SearchPicker`) instead of a third copy of that markup. The profile section keeps its own markup (out of scope, noted as follow-up). |
| Cost-owner transfer rules | `PUT /cost-owner` is `Modify`-gated. The service additionally needs: the caller may use the target owner (`CanUseCostOwnerAsync`: administrator, a `co:use` grant on that owner, or the owner is the caller's own), the target is not frozen (400), the server is not archived (404), and **no unresolved deployment** exists (409 "Cost ownership cannot change while a deployment is unresolved"). A no-op change (same owner) returns 204. It closes the prior assignment, opens a new one, writes a `CostOwnerChanged` audit record and bumps `server.TimeStampUpdated`. | The transfer is only offered while no cloud machine is active and no job is pending, with a visible reason otherwise; the 409 remains mapped as a real message. The dialog can state truthfully that costs already incurred stay with the previous owner (the change is "for future deployments of a stopped server", `GameServerCostOwnerUpdatePayload` doc). |
| Where to get transfer targets | The only owner list is `GET /game-servers/creation/cost-owner-options`, gated by the create claim (`crt:sv`, `adm:*`), unpaged and unsearchable; finance `GET /cost-owners/user-candidates` and the finance owner list need finance claims. A member with `sv:modify` but not `crt:sv` cannot load any list today. An administrator may use every owner (every user has one), so the list can be long. | New `GET /game-servers/{id}/cost-owner/options?search&take` gated by `Modify`, same usable-owner rule, excluding the current owner, with `kind`. The picker covers the short list of a normal member and the long list of an administrator with one control. |
| Live updates | `FleetChangeInterceptor` publishes a fleet-changed frame when a `GameServer` row changes its current cost owner, so every open workspace refetches the server query by itself after a transfer. Grants live in the claim tables, which the interceptor does not cover: no frame follows an access change. `invalidateWorkspaceQueries` uses `exact: true` on `hostingQueryKeys.server(id)`, so a frame never touches per-server sub-keys. Claims are re-read from the database on every request (`OnValidatePrincipal` loads user, roles and role claims), so a grant is effective on the grantee's next request; the React `FullUser` in memory is not refreshed until it is refetched. | Transfer: nothing extra for other viewers; the acting member invalidates explicitly. Access: the list refetches after the member's own change, when the window regains focus and when its panel is opened by hand; another manager's change is not pushed (accepted, a backstop item). The acting member refreshes `me` and the server query after every access change because their own flags may have moved. |
| Settings panel mechanics | Phase 70 `SettingsPanel` already provides the anchor id, the summary line, the badge slot, the open-state memory, the hash opening and `Expand all`. `serverSettingsPanelAnchors` in `urlParameters.ts` is the closed hash allowlist and is kept equal to the rendered panels by `tests/app`. The credentials panel is the precedent for a claim-gated panel: absent without `canManageSecrets`, no heading, no request. | Two more panels, two more anchors, the same gating precedent for Access. |
| Existing cost-owner copy | `Hosting_Common_CostOwner` "Cost owner" / "Kostenträger"; `Server_Create_BilledTo` "Billed to {{owner}}" / "Abgerechnet an {{owner}}"; `Server_Create_BilledTo_Change` "Change cost owner" / "Kostenträger ändern"; `Server_Confirm_OwnerHidden` "Assigned owner" / "Zugewiesener Kostenträger"; `Hosting_Create_CostOwnerFrozen` "frozen" / "gesperrt". `serverCostFacts` and `CostStrip` already resolve hidden and unknown owners (`costOwnerName` equals the placeholder for viewers who may not see the owner). | Reused as is; the new panels follow the same hidden and unknown handling. |
| Dialog and control building blocks | `ConfirmDialog` supports `error`, `busy`, `children`, `confirmVariant`, `dismissVariant`, `closeOnBackdrop`, `initialFocus`. `SwitchField` takes `label`, `hint`, `labelEnd`, required `onLabel` and `offLabel`. `Disclosure variant="inline"` takes `headingLevel`, `badge`, `summary`. `SearchField` exists for list filtering. `useAppToast` exists. | No new primitive other than the picker. |

## Decisions

| Id | Decision | Rationale |
|----|----------|-----------|
| D-01 | Two new collapsible Settings panels, in this order inside the Settings section: Mods, Configuration, Credentials, Automation, **Access** (`server-access`), **Cost owner** (`server-cost-owner`), Server record. Both start collapsed like every Settings panel. | Access and cost owner are ownership topics next to the server record, not content a member edits on every visit. The Phase 70 accordion already solves "Settings is long". Rejected: a new workspace tab (the `workspaceTabIds` registry, the `?tab=` URL contract and the section navigation are closed, and two panels do not justify a section); putting the cost owner inside Server record (different claim, different purpose, and the record panel is the destructive area); putting access in Overview (it is configuration, not status). |
| D-02 | The Access panel renders only when `server.canManageAccess === true`. Without it there is no heading, no placeholder and no request. Archived servers keep the panel and it stays fully operable. | The credentials precedent (Phase 65). Revoking people's access to an archived server is still sound hygiene and the API allows it, so no archived restriction is invented. A non-manager has nothing to read here: the endpoint answers 403. |
| D-03 | The Cost owner panel renders for every viewer of a non-archived server. It shows who pays; the transfer control exists only with `server.canModify`, otherwise one muted sentence explains who may transfer. | Satisfies the read-only state for members who can view but not manage, and it is the one place that explains what a cost owner is. The API rejects archived servers with 404, so the panel is absent there (the cost owner stays visible in the cost strip). |
| D-04 | Access changes apply immediately, one permission per call, using the existing grant and revoke endpoints. There is no staging, no review dialog, no pending bar entry and no leave guard for access. | Each call is atomic, idempotent and individually audited by the API. The Phase 65 draft exists because configuration is applied together at start; here a half-applied batch has no meaning. A draft layer would add review, discard and leave rules for no gain. |
| D-05 | Adding a subject grants exactly one permission, View (`sv:view`). More permissions are switched on afterwards in the subject's row. | One call, no partial failure, and a sensible baseline ("can see this server"). It avoids an eight-way choice in the add form, which would need a custom control or a long checklist. |
| D-06 | Each subject is one `Disclosure variant="inline" headingLevel={3}` row: the subject name is the title, the kind (and "You") are badges, the held permissions are the always-visible summary, and the eight permission switches plus Remove all access are the content. Rows start closed and are never opened by the app. | A scannable list first, detail on demand, one pattern already used by the Settings panels. The summary shows what a subject holds without opening anything. |
| D-07 | The eight permissions are `SwitchField`s (Granted / Not granted), in a fixed order: Full control, View, Operate, Change settings, Manage access, Delete data, Manage credentials, Reveal credentials. The state is also carried by the switch position and the state word, never by color. Full control (`sv`) held means the other seven show as on and disabled with the hint "Included in Full control"; their stored grants are untouched and reappear when Full control is switched off. | Matches Phase 70 D-02 (a switch sets something on or off immediately). Shows the real model: `sv` implies everything, the rest is independent. Never silently deletes stored grants. |
| D-08 | A toggle is optimistic: the switch moves at once, the call runs, and on failure the switch moves back and an inline alert under the switch states why. Success is announced politely in "Name: Permission granted" form. | Immediate controls must feel immediate; a failure is rare and visible. The cache is rolled back from the snapshot taken in `onMutate`. |
| D-09 | Revoke needs no confirmation, with two exceptions that do: (a) the subject is the signed-in member and the permission is Full control, View or Manage access; (b) Remove all access (any subject). Both use `ConfirmDialog` with the danger confirm. Granting never confirms. | A single revoke is reversible with one tap and is announced; confirmation dialogs on every toggle would make the panel unusable. Self-lockout and "wipe a person" are the two cases where the member cannot simply undo it (they may lose the very panel). |
| D-10 | Picking a member or role uses a new shared `SearchPicker` (an ARIA combobox with an inline listbox), never a native `select` and never a long checklist. The member and role flavors sit behind a segmented Member / Role choice. | Standing preference: no ugly native selects, long people lists need search. A combobox with search-as-you-type scales from a small club to hundreds of users. The listbox is in normal flow (not an overlay), so no ancestor `overflow` can clip it and no portal or focus trap is needed at 320px. |
| D-11 | The cost-owner transfer is two steps: choose the new owner in a `SearchPicker` inside the panel, then confirm in a `ConfirmDialog` that names the new and the old owner and states what changes (from now on, costs incurred stay, alerts follow). Confirm is the dialog's only gold button. | A choice plus an explicit, specific confirmation. The listbox stays out of a modal. The dialog copy is written from what the service does, not from what would sound reassuring. |
| D-12 | The transfer is offered only while the API can accept it: no active deployment (`isDeploymentActive(server)` false) and no pending job (`pendingJobCount === 0`). Otherwise the button stays visible and unavailable with the reason in text (the `unavailableReason` capability). The API stays the authority: a 409 still maps to a message in the dialog. | The user sees why, before a request. The two client checks are an approximation of "no unresolved deployment", so the server answer must still be handled. |
| D-13 | The cost strip row "Cost owner" gains a link "Change cost owner" (`Server_Create_BilledTo_Change`) to `?tab=settings#server-cost-owner` for members with `canModify` on a non-archived server. | Discoverability from where the owner is shown; the hash opens the panel and scrolls it into view (Phase 70 behavior). |
| D-14 | New query keys sit under `hostingQueryKeys.server(id)`: `access`, `accessCandidates`, `costOwnerOptions`. They are never touched by a fleet frame (`invalidateWorkspaceQueries` is exact), and they are invalidated by the member's own successful calls. | Prevents a transfer elsewhere from discarding a half-typed search and keeps the invalidation rule of Phase 63 intact. |
| D-15 | A member who loses the ability to manage access through their own change sees the panel disappear after the server refetch; a polite toast says so and focus moves to the Settings heading. A member who loses View of this server (a 403 or 404 on the server query after their own change) is sent to the fleet with the same toast. | Their own change is the cause, so it must be explained, and focus must never land on a removed element. |
| D-16 | Large access lists get a `SearchField` filter from eight subjects up, the same threshold as the Phase 70 configuration filter; the filter matches name and kind, never hides a subject with a warning, and is component state, not a URL parameter. | Standing preference for filterable long lists; the closed `urlParameters` contract stays closed. |
| D-17 | API changes are additive and listed in one place (API Contract). The OpenAPI snapshot `sources/ReactApp/openapi/utf-api.json` and `src/generated/api.ts` are regenerated; the generated Kiota client under `sources/WebApp/UtfApi` is regenerated by its generator, never edited. | `AGENTS.md`: the API is not a frozen contract; generated output changes through the generator. Additive fields cannot break the legacy WebApp. |
| D-18 | No new runtime dependency and no new dev dependency. No new color, font size or weight. | Supply-chain rule of Phase 61, D-17 of Phase 70. |
| D-19 | Every changed screen keeps the Phase 69 gates green: axe WCAG 2.0 to 2.2 AA, keyboard walk, 320 and 390px reflow, text spacing, German walk. New states are added to the screen registry (Accessibility And Responsive Contract). | FND-06 stays a gate, not a phase. |
| D-20 | The legacy `ConfigurationProfileAccessSection` is not migrated to `SearchPicker` in this phase. A follow-up may do it; the picker API is designed so that it can. | Scope: this phase closes the server access finding, not a refactor of a working profile screen. |

Rejected, recorded so they are not reopened: a staged access matrix with a save bar (the profile matrix shape; wide, heavy at 320px, and the server routes are per-permission); a permission preset or role-like "level" radio (invents a model the API does not have); a new workspace section; a native `select` for members or owners; a free-text GUID field; confirming every revoke; transferring while a machine runs.

Exceptions recorded: E-05 `--utf-listbox-max-height` 16rem (256px) is a control dimension declared as a token (Spacing Scale). The control list closed by Phase 69 and amended by Phase 70 is amended again to include `SearchPicker`. The earlier exceptions (E-01 to E-04) stay.

## API Contract Changes

All changes are additive, live in the layer that owns the data (`sources/Api`), keep the architecture boundaries (no game-process or provider concern is touched) and are followed by regenerating the OpenAPI snapshot and the generated clients. Each is covered by API tests (Verification Contract).

| Id | Change | Why the UI needs it |
|----|--------|---------------------|
| API-01 | `GameServerDto` gains `bool CanManageAccess` (computed with the exact rule of `ServerManageAccessRequirement.HasExactPermission`, in the server detail and the list), `bool? CostOwnerIsFrozen` (null when the viewer may not see the cost owner) and `Instant? CostOwnerAssignedAt` (the open `GameServerCostOwnerAssignment.TimeStampAssigned`; detail only, null in the list and when the owner is hidden). | Gating the Access panel without guessing from claims; the frozen-owner warning and unblocking path; "since" in the panel. |
| API-02 | `GET /game-servers/{gameServerId}/access/users/options?search&take` (`ManageAccess`). Returns `GameServerUserAccessCandidateDto[] { userId, nickname, detail }`: users that are not deleted, not banned and verified, **excluding users that already hold an exact allowlisted grant on this server**, ILike match on nickname, ordered by nickname, `take` 1 to 50 (default 20, else 400). `detail` is the Discord username when present, else null. | Search without the profile screen's GUID line; honest paging; disambiguates equal nicknames. |
| API-03 | `GET /game-servers/{gameServerId}/access/roles/options?search&take` (`ManageAccess`). Returns `GameServerRoleAccessCandidateDto[] { roleId, title, description, memberCount }` with the same exclusion, match on title, ordering and bounds. | The same for roles. |
| API-04 | `GameServerUserAccessGrantDto` gains `string? Detail` (same meaning as API-02); `GameServerRoleAccessGrantDto` gains `int MemberCount`. | Disambiguation in the list; the reach of a role. |
| API-05 | `GET /game-servers/{gameServerId}/cost-owner/options?search&take` (`Modify`). Returns `GameServerCostOwnerOptionDto[]` (existing shape plus `ECostOwnerKind Kind`) for the owners the caller may use (the `CanUseCostOwnerAsync` rule, including all owners for administrators), **excluding the server's current owner**, frozen owners included and flagged, match on display name, the caller's own owner first, then by name, `take` 1 to 50 (default 20). 404 for an unknown or archived server. The existing `creation/cost-owner-options` response gains the same `kind`. | A `Modify` holder without the create claim can transfer; administrators get a searchable list instead of every owner in one array. |

Privacy note for the planner (the one open point, see UI Considerations): `detail` must only reach `ManageAccess` holders and the planner confirms the Discord username is already exposed to such members elsewhere; if it is not, the fallback is `detail` = `#` plus the first six characters of the user id.

Error mapping the UI relies on (already produced by `TryMapException`): 400 validation (unassignable permission, frozen or unavailable owner), 403 forbidden, 404 unknown server, user, role or archived server, 409 conflict (unresolved deployment, concurrent change).

## Spacing Scale

Inherited from Phase 61 and 70 without change (all multiples of 4, rem, 1rem = 16px). Control height `--utf-control-height` 40px, `--utf-control-height-touch` 44px at <= 800px.

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Gap between badge and title, gap between a switch's label and its hint |
| sm | 8px | Gap between subject rows, between the grant form's controls, between listbox options (divider rows have none), between dialog actions |
| md | 16px | Row padding, listbox option padding inline, gap between form groups, gap between the intro note and the grant form |
| lg | 24px | Settings panel padding (Phase 70), gap between the grant form, the filter and the list |
| xl | 32px | Not used |
| 2xl | 48px | Not used |
| 3xl | 64px | Not used |

Additive token (the only new value; a multiple of 4, a control dimension, E-05):

| Token | Value | Usage |
|-------|-------|-------|
| `--utf-listbox-max-height` | 16rem (256px) | Maximum height of the picker listbox before it scrolls inside itself |

Layout rules (token-only; the style guard fails on a literal):
- The picker input and the chosen token occupy the same slot and the same height (`--utf-control-height`, `--utf-control-height-touch` at <= 800px), so choosing or clearing never moves the surrounding layout. The listbox is in flow below the input and is the only element that moves content, only while it is open.
- Listbox options are at least `--utf-control-height` high (44px at <= 800px), full width, one divider per option (1px `--utf-border-divider`).
- At >= 521px the grant form lays out as one row after the segmented control: the picker grows, the Give access button sits at the end aligned to the input. At <= 520px everything stacks and the button is full width at touch height.
- The permission switches of a subject lay out in two equal columns above 800px and in one column below; each switch row is at least touch height at <= 800px.
- Text wraps (`overflow-wrap: anywhere`); a nickname (up to 1024 characters), a role description, an owner name (up to 256 characters) and every state or reason string are never truncated with an ellipsis (Phase 69 rule). Names are rendered inside `<bdi>` as React text only.

Breakpoints (constants): `520px` compact, `800px` narrow. Minimum supported width 320px with no horizontal page scroll.

## Access Panel Contract (D-02, D-04 to D-09, D-15, D-16)

### Structure, top to bottom

1. `p.access-intro` (`Server_Access_Intro`, Body muted).
2. Grant form (`form`, `aria-labelledby` its `h3`): `h3` `Server_Access_Grant_Title`, description `Server_Access_Grant_Body`, the segmented `RadioGroupField` (legend `Server_Access_Subject_Legend`, options Member and Role, no help), then one row holding the `SearchPicker` and the Give access button (`primary`, `type="submit"`, `unavailableReason` while nothing is chosen), then the form alert slot (`role="alert"`, reserved only when an error exists).
3. List section: `h3` `Server_Access_List_Title`; from eight subjects the `SearchField` (Access filter keys) and the polite result count; then `ul` of `li` rows, or the empty state, loading state or error state.

### Grant form behavior

- Switching Member and Role clears the query and the chosen option and keeps focus on the segmented control. The picker keeps its input mounted, so the label and placeholder change in place.
- Candidates come from `API-02` and `API-03` with the trimmed query, debounced 250ms, minimum 1 character (`status="idle"` and the `Server_Access_Search_Hint` text below it before that). Previous results stay visible while the next query loads (no flicker); a stale request is aborted.
- Choosing an option replaces the input by the chosen token (name in `<bdi>`, role: the `memberCount` detail, member: the `detail` when present) with an icon-only clear control; the button becomes available.
- Submit (button or Enter in the input when an option is chosen) calls grant with `sv:view`. While pending the button label is `Server_Access_Grant_Submitting`, the picker and segmented control are disabled and `aria-busy` is set on the form; double submit is impossible.
- Success: the picker clears, focus returns to the picker input (so several subjects can be added in a row), the polite region announces `Server_Access_Announce_Granted`, the access list refetches, and the new row appears in its sorted place **closed**. It is never opened or scrolled to by the app.
- Failure: the request error is mapped to the form alert (`Server_Access_Error_Grant`, `Server_Access_Error_Forbidden`, `Server_Access_Error_NotFound`); the chosen option stays so the member can retry; no toast.

### Subject row (`AccessSubjectRow`, D-06, D-07, D-08)

- Markup: `li` > `Disclosure variant="inline" headingLevel={3}` with title = `<bdi>` name (the accessible name of the toggle is the subject name), `badge` = kind `StatusBadge` (neutral: Member or Role), "You" (info, own row only) and the `Server_Access_Badge_CannotView` warning badge when the subject holds permissions but not View and not Full control, `summary` = the held permission labels (`Server_Access_Summary_Held`; Full control alone reads as "Full control"), and for a role also the `memberCount` line.
- Content, top to bottom: for a role the description paragraph (Body muted); the no-View warning `StatePanel` when it applies; the eight `SwitchField`s in the fixed order, each `label` = permission label, `hint` = permission description (and, when included by Full control, `Server_Access_IncludedInFull` replaces the description), `onLabel` `Server_Access_State_On`, `offLabel` `Server_Access_State_Off`; below them one `ActionButton variant="ghost"` `Server_Access_Remove` at the start edge. Switch error alerts sit directly under their switch (`role="alert"`, reserved by the same reserved-slot rule of Phase 65, so a failure adds one line only once).
- Switch states: a held permission is on; with Full control held the seven others are on and `disabled` (visible, `not-allowed`, the hint says why); Full control itself stays operable. Toggling is optimistic (D-08). A switch whose own request is pending is `aria-busy` and ignores further input until it settles; the other switches stay operable.
- Confirmations (D-09): switching Full control, View or Manage access off on the own row opens the self-removal `ConfirmDialog` (`danger` confirm `Server_Access_Self_Confirm`, dismiss `Server_Access_Self_Dismiss` with initial focus on dismiss, no backdrop close); until confirmed the switch has not moved. Remove all access opens the `Server_Access_Remove_*` dialog (own row: the `_Self` variants); confirm is `danger`, dismiss `primary` with initial focus; the dialog is busy while the revokes run; the error slot shows `Server_Access_Error_Remove` after a partial failure.
- Remove all access runs the revokes sequentially for the permissions the row stores (not the implied ones), stops at the first failure, always refetches afterwards, and on full success closes the dialog, announces `Server_Access_Announce_Removed` and moves focus to the list heading `h3` (the row is gone).
- Sorting: the API order is kept (members by nickname, then roles by title); the list is not re-sorted on a toggle, so a row never jumps while it is being edited.
- Open state of rows is local component state keyed by subject id; a refetch never closes an open row.

### Self-awareness and lost access (D-15)

- "You" is the row whose `userId` equals the signed-in user's `primaryKey`.
- After every successful access mutation the server query (exact) and the fleet list are invalidated and the signed-in user is refetched. When the refetched server has `canManageAccess === false` the panel unmounts, focus moves to the Settings `h2` (the existing heading focus counter), and `Server_Access_Toast_SelfLost` is shown with the server title. When the server query answers 403 or 404 the workspace navigates to the fleet with `replace` and shows `Server_Access_Toast_ViewLost`.
- A 403 on any access call (the member lost the permission elsewhere) shows `Server_Access_Error_Forbidden` in place and triggers the same refetch.

## SearchPicker Contract (D-10)

An ARIA 1.2 combobox with a list autocomplete and an inline listbox.

- Anatomy: `div.search-picker` > `label` (visible, `htmlFor` the input) > the slot, which is either `input[type=text][role=combobox]` or the chosen token (never both) > optional idle hint > the live region (`role="status"`, polite, visually hidden) > when open, `ul[role=listbox]` (`id`, `aria-label` = the picker label) of `li[role=option]` rows.
- Input attributes: `role="combobox"`, `aria-autocomplete="list"`, `aria-expanded` (true only while the listbox is shown), `aria-controls` (the listbox id), `aria-activedescendant` (the id of the active option, absent when none), `autocomplete="off"`, `spellcheck="false"`, `aria-describedby` (the idle hint and `describedBy`), `aria-busy` while loading. Focus stays in the input at all times; the listbox is never focusable.
- Open and close: the listbox opens when the input has at least `minQueryLength` characters and is focused (typing, focus with `minQueryLength` 0, or ArrowDown). It closes on Escape (a second Escape clears the query, as `SearchField`), on blur, on selecting an option and when the picker is disabled. Opening does not move focus.
- Keyboard: ArrowDown and ArrowUp move the active option and wrap; Home and End move to the first and last enabled option (while the listbox is open); Enter selects the active option (and never submits the surrounding form while an option is active; with no active option and a chosen token, Enter submits the form); Tab closes and moves on without selecting; disabled options are skipped by the arrows and cannot be selected.
- Pointer: an option is selected on `pointerdown` with `preventDefault` so the input keeps focus and the click never blurs the list closed first. Hover sets the active option but is not selection.
- Options: `li[role=option]` with a stable `id`, `aria-selected` true on the active option (the combobox pattern marks the active descendant as selected for styling), `aria-disabled` for disabled ones; content = decorative icon, name (Body 700, `<bdi>`), detail (Body muted, same item), and the disabled reason inside the item as visible text. The text of an option is its accessible name; the detail is part of it so equal names are distinguishable.
- States in the listbox slot (a single row, `role` none, announced through the live region and not as options): loading (`Picker_Loading` or the caller text, with `Spinner size="tiny"`), error (`Picker_Error` plus a `ghost` compact retry `Picker_Retry`), no match (`Picker_NoMatches` or the caller's text), idle (the hint below the input, no listbox).
- Live region: after each settled query it states the count (`Picker_Results_one`/`_other`) or the no-match text; never on every keystroke (it follows the 250ms settle).
- Chosen token: `div.search-picker__chosen` with the name, the detail and an icon-only `ghost` clear control (`Dismiss16Regular`, `aria-label` `Picker_Clear`, 24px minimum and 44px at <= 800px). Clearing returns focus to the input. The token has the same height as the input and the same border box width, so nothing shifts.
- Listbox geometry: in normal flow under the input, 1px control border, `--utf-radius`, `--utf-surface-overlay`, `max-height: var(--utf-listbox-max-height)` with `overflow-y: auto` inside itself, `overscroll-behavior: contain`; the active option is scrolled into view with `scrollIntoView({ block: "nearest" })`.
- Forced colors and reduced motion: system colors for borders and the active outline; no transition on the listbox.
- It is a project primitive: no `Combobox`, `Dropdown` or `Listbox` of Fluent UI, and no native `select` or `datalist`.
