# Phase 62 - UI Design Contract

> Visual and interaction contract for Phase 62: Fleet & Quick Actions.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Scope: `sources/ReactApp` plus one small, explicitly requested backend signal (see Live Update Contract) and one
> minimal DTO projection (see Mine Filter Data Finding). `sources/WebApp`, generated Kiota output, and
> `sources/Common/Ui/routes.json` are not touched. No new pathnames.
> Requirements covered: FLT-01, FLT-02, FLT-03, FLT-04, FLT-05, ACC-02.
> Inherits without change: the Phase 61 contract (`61-UI-SPEC.md`) for design system, spacing, typography, color,
> state and cost model, cost confirmation, unavailable-action pattern, localization and token rules. This file only
> adds or overrides what the fleet needs; anything not stated here is exactly as in Phase 61.

The fleet at `/command/servers` answers "what exists, what is on, who pays, what next" in one scan. It is a working
tool inside the Command Center, deliberately quieter than the public site (CONTEXT D-01): no hero, no marketing
imagery, accent used only on the one action per card that begins cost.

## Page Anatomy (FLT-01)

Top to bottom, one column, inside the existing `next-hosting-page` container:

| Order | Element | Renders when | Notes |
|-------|---------|--------------|-------|
| 1 | `PageHeader` (h1 "Servers"), description, actions: Refresh servers (`ghost`), Create server | always (for viewers with access) | Create is `primary` on this view, not `gold` (see Color). In the creator empty state it is the only action and is `gold`. |
| 2 | Cost line | any server in the full fleet has cost `live` or `maybe` | One notice, warning tone, static text, `role="note"`. Counts over the whole fleet, never over the filtered result, so a filter cannot hide it. |
| 3 | `FleetToolbar`: search, filter chips | fleet has at least one server | Sticky: no. |
| 4 | `FleetLiveNotice` | socket disconnected or unavailable | `role="status"`. Absent while connected. |
| 5 | Result summary | search text or filter other than All is active | Body size, muted; the container is an always-present `aria-live="polite"` region. |
| 6 | Active section | filter is All, Mine or Running | Always rendered in All and Mine (empty line when it has no cards). |
| 7 | Off section | filter is All, Mine or Off and it has at least one card | Omitted when empty. Never collapsible, never hidden, no disclosure control. |
| - | No-match panel | search or filter yields zero cards | Replaces both sections. |
| - | Empty panel | fleet has zero servers | Phase 61 copy (creator vs member). No toolbar. |

The three-tile summary strip (`Metric` x3) is removed (D-06). Counts live on the filter chips; the single cost line
replaces the per-fleet "possible cost" tile.

Heading levels: h1 page title, h2 section titles, h3 card titles. Cards sit in a `<ul role="list">` of `<li><article>`.

### Cost line

Counted over `deriveServerState(server).cost !== "none"` for the whole fleet. Neutral, factual, not an alarm: icon
`Warning20Regular` (aria-hidden), text in Body size using `--utf-state-warning-*` tokens (foreground on 12% tint,
1px border at 60% alpha). Not `role="alert"`; it does not interrupt.

### Filter and section membership (single source: `deriveServerState`)

| Filter | Shows | Section result |
|--------|-------|----------------|
| All | every visible server | Active and Off |
| Mine | servers where the signed-in user is the server owner (`createdById === me.primaryKey`) or the cost owner (see Mine Filter Data Finding) | Active and Off |
| Running | servers whose derived `cost` is `live` or `maybe` (a machine is allocated or may still be billing) | Active only |
| Off | servers whose derived state is `off` | Off only |

Section assignment: `off` goes to Off. Every other state (`starting`, `running`, `stopping`, `working`, `attention`,
`unconfirmed`, `unknown`) goes to Active. Because `off` is only reachable when `possibleCost` is false (FND-03), a
server that may still cost can never appear in Off or under the Off filter. `attention` or `working` servers whose
cost is `none` appear under All and Mine (always in Active) but not under Running; this is intended, they are not
billing. Search applies first, then the filter. Chip counts are computed over the search result, so each chip shows
what clicking it would list.

Ordering: Active keeps `orderFleetServers` (may-cost first, then pending work, then locale-aware title). Off is
locale-aware title only (`Intl.Collator(currentLocale(), { sensitivity: "base" })`).

## Card Anatomy (FLT-01, FLT-05)

One card layout at every width (D-05): a CSS grid of cards on wide screens, one column when the container is narrower
than two minimum card widths. No compact-row variant. Facts and actions stack inside the card, so the same markup is
used from 320px to desktop.

Top to bottom inside `FleetServerCard` (`<article aria-labelledby={titleId}>`):

| Order | Element | Typography | Rule |
|-------|---------|-----------|------|
| 1 | Kicker: `server.gameIdentifier` | Label 12/700, `--font-label`, uppercase, 0.06em tracking, `--utf-text-muted` | Raw identifier, not localized (proper noun / id). Wraps. |
| 2 | Title `<h3 id>`: `server.title` | Heading 20/700, line-height 1.2, `overflow-wrap: anywhere` | Focal point of the card. Names can be 256 characters; never ellipsized. |
| 3 | `ServerStateSummary` (badge + cost chip) | Label 12/700 | Beside each other, wrapping below at <= 520px (existing component behavior). |
| 4 | Stage line | Body 14/400, `--utf-text-muted` | Only while derived state is `starting`, `stopping` or `working`. Text: the localized `Hosting_DeploymentStatus_{status}` label of `deployment.status` when a deployment exists; otherwise `Server_Fleet_QueuedChange`. Never the raw `deployment.stage` token. Absent in every other state. |
| 5 | Facts `<dl>`: one row, Cost owner | `dt` Label 12/700 muted, `dd` Body 14/400 | `dd` = `costOwnerName`, fallback `Server_Confirm_OwnerUnknown`. A row is never empty. |
| 6 | Actions: primary action, then Open server | Label size at 700, button text not uppercase | Stacked, each full width of the card at every viewport width. Primary action first. |
| 7 | Reason (only when primary is disabled) | Body 14/400, `--utf-text-muted`, 16px info icon | Rendered by `UnavailableReason` directly below the primary control, wrapping, linked via `aria-describedby`. |

Removed from the card (D-04), each marked `relocated` to the Phase 63 workspace in the parity matrix, never deleted:
runtime provider, queue count (`Server_Fleet_PendingJobs_*`), "Updated" time, the card-level possible-cost paragraph
(replaced by the cost chip plus the page cost line), and the Terminate link (D-11, relocated to the workspace and the
`?action=terminate` deep link).

Card surface: `--utf-surface-raised`, 1px `--utf-border-divider`, radius `--utf-radius`, elevation
`--utf-elevation-1`, padding `--utf-space-md` (16px) at every width, vertical gap `--utf-space-md` between blocks.
The card is a flex column and the action block has `margin-top: auto`, so primary actions align along the bottom of a
grid row when neighbouring cards have different amounts of text. Cards in Off use the identical surface and contrast.

Grid: `grid-template-columns: repeat(auto-fill, minmax(min(100%, var(--utf-fleet-card-min)), 1fr))`, gap
`--utf-space-md`. `auto-fill`, not `auto-fit`, so a lone card keeps card width instead of stretching across the page.

### Primary action (FLT-04, D-10)

One primary action per card, chosen by `primaryActionFor(server, derived)` from `server.actions` (case-insensitive id):

| Derived state | Primary | Variant | Enabled when |
|---------------|---------|---------|--------------|
| `off` | `start` ("Start server") | `gold` | action present, `enabled`, not `pending`, not launch-disabled |
| `running` | `stop` ("Shut down and stop billing") | `danger` | action present, `enabled`, not `pending` |
| `starting`, `stopping`, `working` | label `Server_Action_InProgress` ("In progress") | `ghost` | never; always `unavailableReason` |
| `attention`, `unconfirmed` | `stop` when the API offers it | `danger` | action `enabled` and not `pending`; otherwise disabled with reason |
| `attention`, `unconfirmed` without a `stop` action; `unknown`; any state where the needed action is absent | none; Open server becomes the only action | `primary` | always |

Rules:
- `terminate` is never offered on the card. For `attention` and `unconfirmed` the safest cost-stopping action is
  graceful `stop`; if the API offers no `stop`, the card shows Open server only (the member reaches terminate from
  the workspace).
- A disabled primary uses the Phase 61 `unavailableReason` pattern (`aria-disabled`, focusable, visible reason). The
  reason text comes from `UnavailableReason` mapping of `action.unavailableReason`; for the in-progress states the
  reason is `Server_Reason_Pending` when `pendingJobCount > 0` or `action.pending`, else `Server_Reason_State` with the
  localized state label. A member without operate permission sees the mapped `Server_Reason_Operate`.
- Activation calls `useCostConfirmation().request({ serverId, actionId, source: "fleet-card" })` and nothing else.
  The card never executes an action itself and never opens a second dialog.
- Open server is `ghost` (or `primary` when it is the only action), an `ActionLink` to
  `/command/servers/{id}` (no new pathname).
- Create server is hidden from the card list entirely; it lives in the page header.

### After a confirmed action (D-12)

1. The shared flow shows the toast and invalidates the fleet and notification queries (Phase 61 behavior).
2. The card enters a local `submitted` state keyed by server id: primary disabled, label `Server_Action_InProgress`,
   reason `Server_Fleet_Submitted`. The status badge is not changed optimistically.
3. `submitted` clears when the invalidation refetch settles. The card then renders whatever the server reports; if
   the server shows no change and no pending job, the original action is available again (no silent stuck state).
4. Cards submitted independently never block each other.
5. Focus: the dialog returns focus to the invoking control (Phase 61). If the card has moved between Active and Off
   after the refetch and the control no longer exists, focus moves to the same server's Open server link, found by
   `data-server-id`, so focus is never dropped to `<body>`.

## Search, Filter and URL State (FLT-02, FLT-03)

| Concern | Contract |
|---------|----------|
| Search scope | `title`, `gameIdentifier`, `costOwnerName` (D-07). |
| Matching | Fold both sides with `normalize("NFD")`, strip combining marks, `toLocaleLowerCase(currentLocale())`; split the query on whitespace; every term must be a substring of the joined haystack (AND). Blank or whitespace-only query matches everything. |
| Typing | The input is controlled by local state and filters immediately; no submit button, Enter does nothing special. |
| URL | `?q=` (trimmed, omitted when empty) and `?filter=` (`mine`, `running`, `off`; `all` is the default and omitted). Written with `setSearchParams(..., { replace: true })`, the `q` write debounced 250ms. Other params are preserved. Invalid `filter` values fall back to All. Reload and shared links restore both. |
| Clear | A clear control (icon-only `ActionButton`, `Dismiss20Regular`, `aria-label` `Server_Fleet_SearchClear`) appears inside the field when the query is non-empty and returns focus to the input. `Escape` in the field clears it. |
| Filter chips | `FilterChipGroup` with `aria-label` `Server_Fleet_FilterLabel`. Order: All, Mine, Running, Off. Each chip shows its label and the count. Exactly one chip has `aria-pressed="true"`. Pressed state is carried by a 16px `Checkmark16Regular` icon plus a stronger border, never color alone. |
| Chip visuals | Unpressed: `ghost` look, 1px `--utf-border-control`, text `--utf-text`. Pressed: `--utf-surface-overlay` background, 1px `--utf-text` border, leading check icon. Hover changes only background through `--utf-motion-fast`. Focus: `--utf-focus-ring`. Chips are not gold. |
| Counts | `Intl.NumberFormat(currentLocale())`; zero is shown ("Mine 0"), chips with zero stay enabled (selecting one shows the matching empty panel). |
| No match | `StatePanel kind="empty"` with title, body and a `ghost` "Clear search and filter" button that resets both params (replace) and moves focus to the search input. Distinct from the "no servers shared with you" panel, which is the whole-fleet empty case. A Mine filter with no search text uses its own copy. |
| Layout | >= 800px: search field grows, chips sit on the same row to its right. <= 800px: search full width, chips below. <= 520px: chips in a two-column grid (2x2) so German labels with counts never overflow. All controls are 44px tall at <= 800px (`--utf-control-height-touch`), 40px above. |

## Live Update Contract (FLT-04 "updates without a page reload", D-13..D-16)

### Wire (backend, minimal and explicitly requested)

- One new wire message in `sources/WebSocketContracts` (wire messages only): a fleet-changed signal carrying the
  server id and nothing else. No status, cost, name or owner crosses the socket, so the broadcast needs no per-viewer
  filtering. The React app refetches `hostingQueryKeys.fleet` through the normal authorized endpoint.
- Sent through `IUpdateStreamService.SendUpdateAsync` on a path-scoped fleet path from the durable lifecycle executor
  and job transitions (deployment status change, `possibleCost` change, pending job count change). The stream is
  process-local like today; document that a multi-instance API needs a shared backplane (future work, deferred).
- Subscription authorization: the existing `UpdateStreamController.CanSubscribeAsync` accepts only event paths today;
  the fleet path must be added there with the same hosting claim check the fleet endpoint uses (`sv`, `sv:view`,
  `crt:sv`, `adm:sv`, `adm:hosting`). This is a planner handoff, not verified in this research.

### Client (reusable, resource-agnostic)

`useUpdateStream(path, onMessage)` in `src/app`: opens `wss://{api host}/update-stream/subscribe?path=...` through the
existing API base URL, same-site cookie auth. It returns `status`: `connecting`, `open`, `reconnecting`,
`unavailable`.

| Behavior | Contract |
|----------|----------|
| Reconnect | On close or error, retry with exponential backoff 1s, 2s, 4s, 8s, 16s, then 30s cap, +/-20% jitter, indefinitely while mounted. Also retry immediately on `online` and when `document.visibilityState` becomes visible. Not interval polling. |
| Refetch on (re)connect | Every transition to `open` after the first invalidates the fleet and notification queries once, so changes missed while disconnected are recovered. |
| Coalescing | A burst of messages triggers one invalidation (leading edge, then at most one trailing call per 500ms). Messages for unknown ids are still a valid reason to refetch. |
| Unknown messages | Ignored without error. |
| Cleanup | Close on unmount; no reconnect after unmount. |
| Fleet query | `refetchInterval` removed from `useFleetQuery`; `refetchOnWindowFocus` stays at its default (focus return is not interval polling). Manual Refresh stays. No polling fallback (D-15). |
| Mount point | `FleetLiveUpdatesProvider` sits next to `CostConfirmationProvider` in `CommunityLayout` and `CommandCenterLayout` and subscribes only when the viewer can access servers, so the overview and the profile menu (which share the fleet cache) do not go stale after the 10s poll is removed. Other pollers (notifications, workspace) are unchanged. |

### Disconnected indicator (discretion decided)

`FleetLiveNotice` renders only on the fleet page, never while `status` is `open` or during the first `connecting`.

| Status | Shown after | Variant | Content |
|--------|-------------|---------|---------|
| `reconnecting` | 3s of continuous disconnection (avoids flicker on a blip) | `StatePanel kind="info"`, icon `PlugDisconnected20Regular`, `role="status"` | Title, body, "Reconnect now" button (`ghost`) that triggers an immediate attempt and a refetch |
| `unavailable` | 5 consecutive failed attempts without ever having opened in this page session | same shell, different copy | Title, body that points to Refresh servers; retries continue in the background at the 30s cap |

The notice never uses warning or danger tone (the cost line owns warning), never blocks controls, and unmounts without
a toast when the connection returns. A silently stale fleet is not possible: reconnect always refetches.

### State-change announcements

A visually hidden `aria-live="polite"` region announces server state changes that arrive through a refetch (not the
initial load, not changes the viewer just caused): one message per changed server, up to three, then one summary
message. Never moves focus.

## Copywriting Contract

Languages: English and German, both authored here, German informal "du". All strings become keys in
`src/locales/en.json` and `de.json` (flat, `Server_Fleet_*`, plurals with `_one`/`_other` and `{{count}}`); none is
hard-coded in a component. Values of existing keys that change are listed explicitly. Copy rules from Phase 61 apply:

## Accessibility and Responsive Contract (FLT-05, FND-06 gate for this phase)

- 320px and 390px: no horizontal page scroll; every card action, chip, search field and clear control reachable
  without clipping; titles, owner names, badges, chips and reasons wrap. Verified by a Playwright spec
  (`tests/e2e/hosting-fleet.spec.ts`, English and German, viewports 320x568 and 390x844) asserting
  `document.documentElement.scrollWidth <= clientWidth`, that each primary and Open control is in the viewport after
  scrolling, plus an `@axe-core/playwright` scan (WCAG 2.1 AA tags, zero violations, at least one rule evaluated) of
  the populated fleet, the no-match panel and the disconnected notice. Visual baselines at 320 and 390 are a Phase 69
  item (see UI Considerations).
- Keyboard order: header actions, cost line (not focusable), search, clear, chips, live notice action, then each card
  in DOM order (primary, Open server). No positive `tabindex`. Disabled actions stay focusable (`aria-disabled`).
- Focus ring `--utf-focus-ring` on every control; targets 44px at <= 800px, never below 24px.
- Chips use `aria-pressed` inside a `role="group"` with a label; the result summary is a polite live region; the live
  notice is `role="status"`; request errors in the dialog remain `role="alert"` (Phase 61). The cost line is not a
  live region.
- Card actions carry `aria-describedby` for the card title (and the reason when disabled), so a screen-reader user
  listing buttons can tell which server "Start server" belongs to.
- Motion: only `--utf-motion-fast` color and border transitions; no card reorder or section animation; the state
  badge `ArrowSync` icon rotates only under `prefers-reduced-motion: no-preference`.
- A card moving between Active and Off after a refetch must not drop focus (see After a confirmed action).
- No information is color-only: state and cost badges, pressed chips and notices all pair icon and text.

## Mine Filter Data Finding (D-08, researcher-confirmed)

Facts verified in code on 2026-11-18:

| Need | Existing field | Verdict |
|------|---------------|---------|
| Server owner | `GameServerDto.CreatedById` (`Guid`, projected from `server.CreatedByFk` in `GameServerProjectionService`) is a user id; `FullUser.primaryKey` is the signed-in user id | Comparable client-side with no API change |
| Cost owner | `GameServerDto.CostOwnerId` is the primary key of a `CostOwner` entity (kinds `User`, `Verein`, `ExternalOrganization`), not a user id; `CostOwner.UserFk` links a User-kind owner to its user. `CostOwnerName` is display text only | NOT comparable to the signed-in user id with existing fields |

Recommendation (smallest projection inside the existing hosting DTO boundary): add a nullable `CostOwnerUserId`
(`Guid?`, set only when the cost owner kind is `User`, otherwise null) to `GameServerDto` and its projection; the
React app then computes Mine as `createdById === me.primaryKey || costOwnerUserId === me.primaryKey` in the pure
`fleetModel`. Verein and external-organization cost owners are not "mine". The OpenAPI snapshot and generated TypeScript
types are refreshed; generated Kiota output is not edited by hand (regenerate if it is checked in). This addition is
purely additive, so no breaking-change marker is needed. It does not touch worker, provider or lifecycle code.
