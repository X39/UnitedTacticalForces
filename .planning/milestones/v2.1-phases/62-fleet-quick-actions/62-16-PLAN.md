Facts about the implemented behavior (plans 62-13 to 62-15) that the documentation must state accurately. The client requests `game-servers/fleet` and its frame handling is unchanged. The API registers each socket on `game-servers/fleet/{userId}` (the user id in the lower-case D format, derived only from the authenticated principal; a request with any further segment is rejected). The subscribe gate is unchanged and deliberately wide: a global administrator and any holder of `adm:sv`, `adm:hosting`, `crt:sv`, `sv` or `sv:view` may open the socket, including holders of `crt:sv` or a bare `sv:view`, who are never in any server's audience. At publish time the notifier asks `HostingAuthorizationService.GetServerViewAudienceAsync` for the audience of the coalesced batch: users who are neither deleted nor banned and who hold, directly or through a role, an empty-valued `adm`, `adm:sv` or `adm:hosting` claim, or an `sv` or `sv:view` claim whose value is the server id, which is exactly `HasServerPermission` with the view permission; archived servers are included so an archive change reaches viewers; the audience is read from the database on every batch, with no cache. Each recipient gets its own frame on its own path, still one frame per changed server, and the frame is unchanged (server id only). If the audience read fails, nothing is sent for that batch, one warning is logged, and there is no broadcast fallback; the reconnect refetch and the Refresh button are the recovery path (D-15). A claim or role change itself emits no signal: a revoked viewer receives no further frames about the revoked server from the next signal on, but their fleet stays as loaded until the next refetch (reconnect, Refresh, or a later signal for a server they may still view); a newly granted viewer sees the server at the next refetch or the next signal for it. The reason this is not an explicit affected-user notification: claim and role mutations occur at more than five sites in four files (the access service, the resource-claim controller, the role controller and the user controller, including role membership changes that affect arbitrary user sets), which would broaden shared administration code that AGENTS.md forbids broadening without an explicit request. The stream stays process-local (D-14).

This plan changes no source file; a guard in the acceptance criteria enforces that `UpdateStreamService`, `WebSocketContracts`, the React app and the Blazor app are untouched across the whole gap closure.

Decisions implemented: D-17 (claim-scoped delivery, owner decision at UAT test 2), D-13 as amended, D-14 (process-local, restated), D-15 (no polling fallback, restated with the fail-closed consequence).
