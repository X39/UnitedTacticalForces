# Phase 65 - UI Design Contract

> Visual and interaction contract for Phase 65: Change a Server.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Scope: `sources/ReactApp` plus the API, shared-contract and database changes this feature needs (`65-CONTEXT.md` D-00a: the API is not a frozen contract). `sources/WebApp` (legacy Blazor) and generated Kiota output are not touched by hand. URLs are not a stable contract (D-00b): when a route or query parameter changes, `sources/Common/Ui/routes.json` and the route tests change together and stay green.
> Requirements covered: CHG-01, CHG-02, CHG-03, CHG-04, CHG-05, CHG-06, CHG-07.
> Inherits without change: `61-UI-SPEC.md` (design system, spacing, typography, color, state and cost model, unavailable-action pattern, localization, token rules), `63-UI-SPEC.md` (workspace shell, `?tab=` sections, shell notice slot, Settings and Files sections) and `64-UI-SPEC.md` (shared `FormFields`, `Disclosure`, native-select-with-`optgroup` decision, sticky bottom bar geometry, blocked-reason pattern, validation and focus rules). This file only adds or overrides what changing an existing server needs. Anything not stated here is exactly as in Phase 61, 63 and 64.

A member changes a server the way they would edit a document before publishing it: edits collect in one visible draft, a review shows exactly what will differ, and one explicit action applies it. The page stays a quiet working tool: one gold action at a time, the draft always visible but never loud, and the moment changes take effect stated plainly ("the next time the server starts") rather than implied.

## Research Findings That Shape The Contract

Verified in code on 2026-11-20. They resolve the discretion items in `65-CONTEXT.md`.

| Question | Finding | Consequence |
|----------|---------|-------------|
| Where does the mod pack change live today? | `ServerRuntimePanel.tsx` (rendered by `MachineSection`) holds the mod pack select and `changeModPack`, next to runtime profile, storage strategy and terrain and scenario. The Settings section holds `ServerConfigurationPanel` and `ServerSecretsPanel`. | The mod pack moves to a new "Mods" panel in Settings and joins the draft (D-01). Runtime profile, storage strategy and terrain and scenario stay in Machine, immediate and unchanged: they are not in the staged set of D-01, they change cost and hardware, not configuration. Parity rows `CHG-runtime-profile`, `CHG-runtime-storage`, `CHG-content-selection` are marked `kept`. |
| What does `GetModPackOptions` return? | `GameServerModPackOptionDto` has only `primaryKey` and `title`. | D-05 needs an unavailability reason and a contents list. Both are API additions (D-00a), see "Data The UI Needs". |
| Does a configuration entry carry a Common/Advanced marker? | `GameConfigurationEntry` has `group` (a category such as a settings page), `order`, `targetPath`, `sensitive`, `isRedacted`, `source`, but no tier. | D-06 adds a tier field to the game definition option and the DTO. `group` stays the category; the tier is a second, independent axis. |
| Is there a "waits for next start" signal? | No flag on `GameServerDto`; the roadmap says "takes effect next start" may stay copy only where no signal is warranted. | D-09 adds the signal, because the banner must show only when applied changes truly wait. |
| How are changes applied today? | Four independent immediate calls: `selectConfigurationProfile`, `updateConfiguration(values, resetKeys)`, `changeModPack`, `setSecret` / `rotateSecret`. The current panel saves overrides with a bare "Save" button and a raw `window.confirm` leave guard (`useUnsavedChanges`). | The draft applies those same calls in a fixed order and reports a result per item (see Apply Semantics). An API batch endpoint is allowed if it returns per-item results; it is not required. |
| Who can reveal a secret? | Reveal needs `server.canRevealSecrets && secret.revealable && secret.isConfigured`; the whole Credentials panel needs `canManageSecrets`. | Reveal keeps that stricter existing gate; D-07's `canManageSecrets` is the outer gate. |
| What are the file contexts? | `HostingFileContext = "persistent" \| "live"`; the files panel keeps `path` in local state; folder links are buttons. | `?path=` joins the Files section, `?area=live` is written only for the non-default context. Folder links become router links. |
| Existing controls | `ServerConfigurationPanel` and `ServerSecretsPanel` use raw `<input>`, `<select>`, `<textarea>`, `<button className="button ...">`. `FormFields` has no multiline field. | All migrate to `ActionButton`, `TextField`, `SelectField`, `CheckboxField`; one new shared `TextAreaField` is added for string-array entries (AGENTS.md: no page-local control markup). |

## Data The UI Needs (API changes, D-00a, D-05, D-06, D-09)

The contract names the semantics; exact field names and DTO shapes are the planner's call. Regenerate the OpenAPI snapshot and the generated clients, add tests in the owning layer.

| Need | Where | Semantics |
|------|-------|-----------|
| Pending start signal | `GameServerDto` | `hasChangesPendingStart` (boolean): true from the moment a mod pack, configuration or secret change is applied until a deployment starts that uses it. Optionally `changesPendingStartAreas`: any of `ModPack`, `Configuration`, `Credentials`. Computed by the control plane, never inferred by the browser. Cleared by the start that consumes the changes. Does not change fleet cards in this phase (the fleet badge of FUT-02 stays future). |
| Pack availability and reason | `GameServerModPackOptionDto` | `isAvailable` (boolean) and `unavailableReason` (string, English API text, null when available). An unavailable pack stays listed so the chooser can say why. |
| Pack contents | read-only projection on the options DTO or a read-only endpoint per pack | An ordered list of `{ key, title }` plus a total count. Same shape for the current pack and any candidate, so the client can diff by `key`. |
| Option tier | game definition option and `GameConfigurationDto` | A value per option declaring it `Common` or `Advanced`; each game decides its own Common set. An option without a value is treated as `Advanced`. |
| Cost owner | none | Unchanged; changing mods and settings does not change cost. |

If an addition is not yet available when a plan lands, the UI degrades without inventing data: no availability field means every listed pack is selectable; no contents means the review compares titles only and says so; no tier means a flat configuration list (see Configuration panel); no pending signal means no banner and the review notice and toast still state "next start".

### PendingChangesBar

- `position: sticky; bottom: 0; z-index: 10`, opaque `--utf-surface-raised`, top 1px `--utf-border-divider`, padding `--utf-space-sm` block and `--utf-space-md` inline, gap `--utf-space-sm`, `role="region"` named "Pending changes". It contains no `aria-live` of its own.
- Contents in order: the status sentence (Body 14/400), then "Review changes" (`ActionButton variant="gold"`) then "Discard changes" (`ActionButton variant="ghost"`). DOM order equals visual order. > 520px: sentence left, buttons right in one row. <= 520px: the sentence, then the two buttons stacked full width at 44px.
- Height budget, verified at 320x568 in English and German with the longest sentence: at most one third of the viewport (189px). Measured arithmetic: padding 8 + sentence two lines 42 + gap 8 + button 44 + gap 8 + button 44 + padding 8 = 162px.
- The section sets `scroll-padding-block-end: var(--utf-change-bar-reserve)` (192px) and the same bottom padding so a focused field is never hidden behind the bar (WCAG 2.2 focus not obscured). The bar renders only while the draft is non-empty, so it never reserves space otherwise.
- The workspace header is sticky at the top (Phase 63); the bar does not interact with it. Both stay clear of focused controls through scroll padding.

### ReviewChangesDialog

Native `<dialog>` through `ConfirmDialog` (className `dialog--review`).

| Width | Geometry |
|-------|----------|
| > 520px | `width: min(var(--utf-review-dialog-width), calc(100vw - var(--utf-dialog-gutter)))` (704px max), `max-height: calc(100dvh - var(--utf-dialog-gutter))`. |
| <= 520px | `width: calc(100vw - var(--utf-dialog-gutter))`, `max-height: calc(100dvh - var(--utf-dialog-gutter))`, actions stack full width at 44px. |

Structure: title (h2), description, take-effect notice, scrollable body, results line (only after an apply attempt), actions row. Only the body scrolls (`overflow-y: auto`, `tabIndex={0}`, `role="region"`, accessible name "Changes to review") and the title and actions stay fixed, so Apply is always reachable at 320x568. Inside the body, groups are separated by `--utf-space-md`; each item is a flat row with a 1px `--utf-border-divider` bottom border (no nested cards).

An item row: item name (Body 14/700), "Changed" marker only in the panels (not in the dialog), then a `dl` with two pairs "Before" and "After" (`dt` Label 12/700 Barlow Condensed uppercase, `dd` Body). > 520px the pairs sit side by side with an `ArrowRight16Regular` between (decorative, `aria-hidden`); <= 520px they stack (Before above After) with no arrow. Values wrap with `overflow-wrap: anywhere`; nothing is ellipsized or truncated in the dialog.

1. The single primary action of the view: in the Settings section "Review changes" in the pending bar; inside the Review dialog "Apply {{count}} changes" (`ActionButton variant="gold"`); inside the leave guard "Review changes". - Apply item states: Applied uses success with `Checkmark16Regular`; Failed uses danger text with `Warning20Regular` and the reason; Not tried uses neutral text.
- Warnings (incomplete configuration, physical override, required secret missing) use `StatePanel kind="warning"`.
- Unavailable-action reasons use the Phase 61 style (Body, `--utf-text-muted`, 16px `Info16Regular`, under the control, `aria-describedby`).

Contrast: all pairs are existing Phase 61 token pairs guarded by `tests/styles/tokens-contrast.test.ts`; `--quiet` is not used for text in `components/server/*`.

## Copywriting Contract

Language: English and German, both authored here, informal "du". Placeholders use `{{name}}`. All strings become keys in `src/locales/en.json` and `de.json`; none is hard-coded. New keys are flat `Server_{Area}_{Item}` with areas `Change` (draft, bar, review, leave, banner), `Mods`, `Settings` (configuration and the Settings section), `Credentials` and `Files`. Plural keys use `_one` and `_other` with a numeric `count`. Carried strings reuse an existing key and its text unchanged (legacy keys stay until Phase 69); migrated components read keys only through `useTranslation`. API-originated English text is always inside `ApiText`. Raw `Error.message` text is never printed (the current panels print `error.message`; that ends here).

## Interaction Contract (CHG-01..CHG-07)

### Draft model (CHG-03, D-01, D-02, D-08)

- One in-memory draft per Settings section instance. Shape (conceptual): `modPack?: { to: id | null }`, `profile?: { profileId, revisionId }`, `values: Map<key, string>`, `resets: Set<key>`, `secrets: Map<key, { kind: "set", value } | { kind: "rotate" }>`.
- A staged value that equals the saved value is removed (normalization), so "dirty" means at least one effective change. The count in the bar is the number of effective items: mod pack 1, profile 1, each setting 1, each reset 1, each secret 1.
- The draft lives in React state only. It is never written to `localStorage`, `sessionStorage`, IndexedDB, cookies, the URL, router state, the TanStack query cache or a log. A source-scan test fails on `localStorage`, `sessionStorage`, `indexedDB`, `document.cookie` and `console.` in the draft, panel and dialog files, and a runtime test asserts storage is untouched while staging.
- Typed secret values exist only inside the draft's `secrets` map and the input; they are cleared on apply success for that item, on discard, on "Remove from changes", on "Undo", and on unmount. Mutations that carry a secret value use `gcTime: 0` so the mutation cache does not retain the variables.
- Panels render saved values merged with the draft; every staged item shows a "Changed" badge and an "Undo change" control next to it. Undo restores the saved value in the control and removes the item.
- While an apply runs, every control in the Settings section is `aria-disabled` and focusable with no extra reason text (the dialog is busy); the draft cannot change mid-apply.
- If the saved data refetches while a draft exists (live update, another member), the draft is kept and re-normalized against the new saved values; "Before" in the review always reads the latest saved values.

### Mod picker (CHG-01, D-05)

- Chooser is a `SelectField` (native `select`) with options: "No mod pack" (only when the capability does not require a mod pack), then available packs, with the current pack's option suffixed "(current)"; unavailable packs are `disabled` options suffixed "(not available)", placed last. The default selected option is the current pack (or "No mod pack"). No `gameIdentifier` literal appears in the component (source-scan test as in Phase 64: `arma3`, `aska`, `counterstrike2` must not appear in the mod files).
- Below the select, in order: the current line; the staged line when a different pack is chosen; the "Contents of {pack}" disclosure for the effective selection (collapsed; count in the title; first 10 items, "Show all" expands inline); the "Packs that are not available ({count})" disclosure (omitted when none) listing each pack title with its reason in `ApiText`, wrapping.
- Choosing a different pack stages the change immediately (no separate stage button) and loads the contents of both packs for the review (`useQueries`; cached by pack id). Choosing the current pack again removes the item.
- Review shows the contents diff (see Review Step). Required capability (`requiresModPack`) removes the "No mod pack" option; the saved pack stays selected if still available.
- Disabled when read-only (`canModify` false, archived): the select is `aria-disabled`, focusable, with the single read-only notice above explaining why.

### Configuration (CHG-02, D-06)

- Structure: profile choice (stages a profile change; when a profile is selected the revision radio group "Follow the latest revision" / "Stay on revision {n}" appears and stages the revision mode), then "Common settings", then the "Advanced settings" disclosure.
- Tier handling (API-declared): entries with tier `Common` render under Common; every other entry (tier `Advanced` or missing) renders inside Advanced. If the game declares no Common entry at all, there is no split: all entries render in one list grouped by `group` with no Common heading and no Advanced disclosure (so Common is never an empty stub).
- Inside each tier, entries group by `group` as a `fieldset` with `legend` (existing behavior), sorted by `order`. The generated target path is shown as a muted caption (`Server_Settings_Target`) under the legend of its first group, only inside Advanced. Control-plane-only entries show the carried control-plane label instead.
- Advanced is collapsed by default, with an always-visible summary line. It opens automatically and stays open until the member closes it when: a staged change exists inside it, a field inside has a validation error after a review attempt, or a required entry inside is empty. Nothing required is hidden in a collapsed disclosure.
- Each entry renders through `ConfigurationEntryField`: label, source line, the control by `kind` (game contribution renderer first, else `Boolean` select Enabled/Disabled, `Selection` select with "Not set" when not required, `StringArray` `TextAreaField` with one value per line, numeric `TextField` with `type="number"` and `min`/`max`, otherwise `TextField`), hint (the `description`), `warning`, "Reset to inherited value" when `source === "Server"` (stages a reset, not an immediate call).
- Sensitive entries (`sensitive` or `isRedacted`): `type="password"`, `autoComplete="new-password"`, the stored-value placeholder, staged as "changed" and shown in the review as "Changed. The value is not shown." There is no reveal here; reveal exists only in Credentials.
- Validation: `validateConfigurationEntry` runs on blur and when "Review changes" is activated. With invalid staged fields no dialog opens; the invalid-fields `role="alert"` message appears in the bar, focus moves to the first invalid field in DOM order (opening Advanced first when it lives there), and each invalid field has `aria-invalid="true"` with its error linked by `aria-describedby`. "Review changes" itself is never disabled for validation (a disabled button would hide the cause).
- Warnings carried: incomplete configuration (`isComplete` false), physical override of a generated file (the group is replaced by the warning and its entries are not editable), the placement estimate with its muted "based on saved settings" note while the draft is non-empty.
- Read-only when `canModify` is false or the server is archived: controls `aria-disabled`/`disabled` (native `disabled` is acceptable for inputs; focusable buttons use `unavailableReason`), one notice at the top of the section.

### Credentials (CHG-07, D-07, D-08)

- The panel exists only with `canManageSecrets`. Each secret is an `article` with an h3 (the name), the status line, the required warning when `requiredForStart && !isConfigured`, the masked value, the set input (non-generated) or the Rotate control (generated), and the Reveal control when `server.canRevealSecrets && secret.revealable && secret.isConfigured`.
- Reveal: activating it calls `revealSecret` on demand (a mutation, never a cached query); the value renders in a `code` element in that row, the control becomes "Hide value", a 30-second timer starts, and the polite region announces the reveal. The value hides again on: Hide, the timer, the section unmounting, the tab becoming hidden (`visibilitychange`), a successful or staged change to that secret, and a failed request never shows a partial value. At most one value is revealed at a time per panel (revealing another hides the first). The revealed value is held only in component state; it is never put into the draft, a query cache, a URL, router state, storage or a log.
- Set: typing a value stages "set" (non-empty only; clearing the input removes the item). Rotate (generated secrets) toggles a staged "rotate" with the staged line and "Keep current value".
- Review shows secrets as "Changed. The value is not shown." (set) or "A new value will be generated." (rotate). No secret value, typed or revealed, appears in the review, the toast, an announcement or an error.
- The set input uses `type="password"`, `autoComplete="new-password"`, `spellCheck={false}`; pasting is allowed. A masked, never-partial display is the only representation of an existing value.
- Server-side: reveal, set and rotate remain audited and values stay out of logs (existing behavior). The UI adds no `console` output and no value in error telemetry; an apply failure shows only the three reason strings.

### Review step and apply (CHG-03, D-03, D-04)

- Activating "Review changes" (valid draft) opens the Review dialog; the dialog is the review step. Focus moves to the dismiss button "Keep editing" (safe default, `initialFocus="dismiss"`); Escape and "Keep editing" close it and return focus to the "Review changes" button (or the section heading when the bar is gone).
- Group order is fixed: Mod pack, Configuration profile, Settings, Credentials. A group renders only when it has items. Setting items sort by `group` then `order`. Each item row shows Before and After; per-item "Remove from changes" removes that item (focus moves to the next item's remove control, or to the dialog title when the last item is removed, and the dialog closes if the draft becomes empty).
- Mod pack item: names before and after packs, then `ModPackDiff`: three groups Added, Removed, Unchanged, each with its count in the heading (`dt`-style label plus a list). Removed and Added lists show the first 10 entries and a "Show all {n}" control; Unchanged is collapsed behind its count with "Show all" only (the common unchanged mods rarely matter). Lists are semantic `ul`; each entry shows its marker icon, the word-bearing group heading provides the text. While either pack's contents load: "Comparing the contents…" and the Apply control is `unavailableReason` "Comparing the mod pack contents…". If loading failed or the API sends no contents: show only the two titles plus the failed or unknown line; Apply stays available. If both lists are equal: the "Both packs contain the same mods." line.
- Take-effect notice (info panel) at the top of the body uses the running or not-running variant from the derived server state (`isDeploymentActive`, the Phase 61 semantics: a server that may still incur cost counts as running).
- Apply order and dependencies (one request per group, sequential): 1 mod pack, 2 configuration profile, 3 configuration values and resets (single `updateConfiguration` call, skipped as "Not tried" with the dependency reason when step 2 failed, because values are validated against the selected profile), 4 each credential in `key` order (independent). A failed item never blocks an independent item. Nothing is rolled back.
- Results (D-04): after the run, applied items leave the draft and the dialog; failed and not-tried items stay staged and remain in the dialog with state text and the reason. The results line `role="alert"` ("{applied} of {total} changes applied. The rest stay staged.") receives focus. The confirm action becomes "Try {n} changes again". If everything applied: the dialog closes, the toast `Server_Change_Toast_Applied_*` shows, focus returns to the Settings section heading, queries are invalidated (server, configuration, configuration options, storage demand, mod pack options, secrets, fleet), and the pending-start banner appears once the API signal arrives.
- Busy state: the dialog is `aria-busy`, Escape and dismissal blocked (existing `ConfirmDialog` behavior), the confirm shows the Fluent `Spinner` plus `Server_Change_Apply_Pending`.

### Take effect (CHG-04, D-09)

- The review notice and the post-apply toast state "the next time the server starts" for every change (mods, settings, credentials), because nothing applies to a running process.
- The pending-start banner is driven only by the API signal. It shows in every section of the workspace, in the shell notice slot, in the running or not-running wording, with the areas line when the API sends areas, and it never shows when the signal is false (so it never claims drift that does not exist). It carries no action; starting and stopping use the existing header actions and the Phase 61 cost confirmation.
- Files do not trigger the banner. The Files immediate note is the only statement about timing there.
- Reload and revisit: the banner and the take-effect wording come from API data, so they survive a reload; the draft does not (D-02).

### Leave guard (CHG-05, D-10)

`useLeaveGuard` guards the Settings section whenever the draft is non-empty.

| Leave path | Behavior |
|------------|----------|
| Section switch (`?tab=` change), including SectionNavigation links, breadcrumbs, header links, fleet link | `useBlocker` with a predicate: block when the next location differs from the current `pathname` or its resolved section is not `settings`. A navigation that stays on `?tab=settings` (for example a hash or an unrelated parameter) is not blocked. The leave dialog opens. |
| Router navigation (back, forward, `navigate()`) | Same blocker; Back is blocked and the history stack is unchanged after "Stay here". |
| Tab close, reload, external navigation | A `beforeunload` handler registered only while dirty calls `preventDefault` and sets `returnValue`; the browser shows its own native prompt (its wording cannot be customized). |

- Dialog actions (Phase 61 dialog rules): "Stay here" is the default and initial focus, closes the dialog and calls `blocker.reset()`; "Discard and leave" (`danger`) clears the draft and calls `blocker.proceed()`; "Review changes" (`gold`) calls `blocker.reset()`, closes the dialog and opens the Review dialog. Escape equals "Stay here". Focus returns to the element that triggered the navigation when it still exists, otherwise the section heading.
- The Files section uses the same hook and dialog for its existing guard (queued uploads, unsaved preservation selection) with the two-action variant and no Review action. Dirty tracking there is unchanged.
- No guard while the draft is empty, and none after a fully successful apply (the draft is empty by then). During an apply the guard stays active.
- The guard never uses `window.confirm`.

### Files and the URL (CHG-06, D-11)

- URL contract: `/command/servers/{id}?tab=files&path=<folder>`; `path` is the normalized server-relative folder (no leading or trailing slash, `/` separators, case preserved); root omits `path`. `area=live` is written only for the live context; persistent omits it. `path` and `area` are read only while `tab=files`; `sectionSearch("files")` writes only `tab=files` (switching section drops them). `sources/Common/Ui/routes.json` and the route tests are updated together if the manifest lists query parameters (D-00b).
- Reading: `filesLocation.ts` parses untrusted `path` with the existing `normalizeServerRelativePath`; empty, `.`/`..` segments, backslashes, control characters or more than 1024 characters are invalid and treated as root with `Server_Files_PathInvalid`. A syntactically valid path that the file list request reports as not found (404, or an empty parent resolution) falls back to root with `Server_Files_PathFallback`. Other request errors keep the existing error panel with Try again and do not rewrite the URL.
- Fallback rewrites the URL with `replace: true` (drops `path` and, for a missing live context folder, keeps `area`), so Back does not return to the dead link.
- Writing: every user-driven folder change (folder name link, breadcrumb crumb, tree item, "Top level", Up) pushes a new history entry; clicking the current folder is a no-op (no duplicate entry). Back and Forward restore the previous folder; the local selection, search text and expanded tree state reset on every location change (as `navigateTo` does today), the tree expands the ancestors of the new path.
- Links, not buttons: breadcrumb crumbs and folder names in the table are router links with a real `href` (open in a new tab, copy link), styled as in the current file panel; the tree keeps its keyboard-navigable buttons and calls the same navigation function. Context switching (persistent, live) is also a location change that pushes and resets `path`.
- Focus and announcements: after a user-driven folder change the folder heading (`tabIndex={-1}`) receives focus and the polite region announces `Server_Files_FolderAnnounce`; on first load, Back and Forward only the announcement runs (focus is not stolen on load).
- Files operations stay immediate and never enter the draft: upload, delete, create folder, preservation edits keep their dialogs and confirmations unchanged.

### Keyboard and focus

- DOM order equals visual order: panels in the order of the section anatomy, then the bar. No positive `tabindex`.
- Staging never moves focus. "Review changes" moves focus into the dialog; closing returns it. "Undo change" and "Remove from changes" keep focus on a sensible neighbor (the field's control, or the next item).
- Reveal and Hide keep focus on the button; the value is announced through the live region, not by moving focus.
- Enter in a configuration text field does not apply anything (there is no form submit; Enter only commits the field). Space and arrows operate native radios; the disclosure toggles with Enter and Space.
- Focus ring `--utf-focus-ring` on every control; the bar never covers a focused control (`scroll-padding-block-end`).

### Motion

Disclosure chevron rotation and open/close use `--utf-motion-base`; under `prefers-reduced-motion: reduce` durations resolve to 0.01ms and the chevron does not animate. The dialog uses the existing dialog presentation without extra animation. The only moving glyph is the Fluent `Spinner` while an apply runs.

## Accessibility and Responsive Contract

Phase 69 closes FND-06; this phase enforces it for what it touches.

- Every control has a visible, programmatically associated label; hints and errors use `aria-describedby`; invalid fields use `aria-invalid`; required fields use `required`. Label in name (WCAG 2.5.3): Reveal, Hide, Rotate, Undo and Remove controls have visible text that is a prefix of their accessible name, which appends the item name.
- Masked values have an accessible name ("Value hidden"); bullets are not read as characters (`aria-hidden` on the glyphs, the label carries the text).
- Status messages: one dedicated polite region for staging counts, apply results, reveal and auto-hide; `role="alert"` for the invalid-fields message, the results line, request errors and the reveal error; the banner is a `role="status"` `StatePanel`; the bar and dialog contain no other `aria-live`.
- Dialogs: native `<dialog>` modal with focus trap and labelled title; the scrollable review body is a focusable `region` with a name; Escape maps to the safe action.
- Targets: 44px at <= 800px for every control, minimum 24px everywhere; radio, checkbox and diff "Show all" rows are full-row targets.
- Reflow: 320x568 and 390x844, English and German, no horizontal page scroll; the bar stays within one third of the viewport; dialog actions reachable without scrolling the page.
- Automated checks for this phase: Playwright e2e at 320 and 390 in English and German covering (a) staging a mod pack, a setting and a secret, the bar count, the review dialog, a full apply and a partial apply (one mocked 500), the banner, (b) the leave guard on a tab switch, a router back and the `beforeunload` registration with all three dialog outcomes, (c) Files `?path=` reload, Back, a shared link and an invalid and a missing path, (d) Reveal, auto-hide at 30 seconds (fake timers) and that no secret value appears in the DOM, storage, URL or console. An `axe` scan (`@axe-core/playwright`, existing dev dependency) at WCAG 2.1 AA tags with zero violations and a non-vacuous rule count on Settings with a staged draft and with the review dialog open, a focus-not-obscured assertion for the last Advanced field at 320, and the existing token, style-guard and locale checks (new keys in both files, plural pairs, banned-label test, `identical-allowed.json` entries with reasons). Unit tests for `serverChangeDraft` (normalization, counts, plan order, dependency skip), `filesLocation` and the leave predicate. Visual baselines arrive with Phase 69 (VER-03).
