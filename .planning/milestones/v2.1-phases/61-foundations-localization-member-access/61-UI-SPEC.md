# Phase 61 - UI Design Contract

> Visual and interaction contract for Phase 61: Foundations, Localization & Member Access.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Scope: `sources/ReactApp` only. `sources/WebApp`, generated Kiota output, and `sources/Common/Ui/routes.json` are not touched.
> Requirements covered: FND-01, FND-02, FND-03, FND-04, FND-05, FND-07, L10N-01, L10N-02, ACC-01, ACC-03.

This phase builds the shared foundations (state model, cost confirmation, tokens, locale ownership, parity matrix,
member access states) that Phases 62-69 consume. It does not redesign the fleet or the workspace layout; it makes the
existing screens use the shared pieces so the redesign phases inherit them.

## Spacing Scale

Declared values (all multiples of 4, defined as rem so browser zoom is respected; 1rem = 16px):

| Token | Value | Usage |
|-------|-------|-------|
| `--utf-space-xs` | 4px (0.25rem) | Icon-to-label gap, badge inner gap |
| `--utf-space-sm` | 8px (0.5rem) | Chip padding, gap between badge and cost chip, compact rows |
| `--utf-space-md` | 16px (1rem) | Default padding of notices and dialog sections, form gaps |
| `--utf-space-lg` | 24px (1.5rem) | Dialog padding, panel padding, gap between fact groups |
| `--utf-space-xl` | 32px (2rem) | Gap between major blocks on a page |
| `--utf-space-2xl` | 48px (3rem) | Major section breaks (page level only) |
| `--utf-space-3xl` | 64px (4rem) | Page-level spacing; not used inside the shared server components |

Control sizing: `--utf-control-height` 40px (replaces the 38px used by `--control-height` inside server components); 44px at viewport widths <= 800px for every button, input, and icon-only control in the shared server components.

Exceptions: 1px borders, the 2px focus ring (2px offset), and the 16px icon render size inside badges. Rationale: borders and the focus ring are strokes, not spacing, and WCAG 2.2 focus appearance needs at least a 2px indicator; the 16px badge icon is the Fluent regular-glyph render size, which is a multiple of 4 and already on the grid (the only non-grid case is the 12px Label text size, which is a type size, not a spacing value). No other non-multiple-of-4 values in the new shared components. Hard-coded spacing in new CSS is not allowed; use the tokens.

Breakpoints (constants, CSS custom properties cannot be used in media queries): `520px` compact (stack facts, stack dialog actions), `800px` narrow (44px targets). Minimum supported width 320px with no horizontal page scroll.

## Typography

Exactly four sizes and two weights for the shared server components and everything new in this phase.

| Role | Size | Weight | Line Height | Where |
|------|------|--------|-------------|-------|
| Body | 14px (0.875rem) | 400 | 1.5 | Descriptions, reasons, dialog copy, `dd` values |
| Label | 12px (0.75rem) | 700 | 1.35 | State badges, cost chips, kickers, `dt` terms, button text in compact size. Barlow Condensed, uppercase with 0.06em tracking only for badges and kickers. Never below 12px. |
| Heading | 20px (1.25rem) | 700 | 1.2 | Dialog title, notice title, panel title, the cost amount in the confirmation |
| Display | 28px (1.75rem) | 700 | 1.2 | Reserved for the Phase 63 workspace header title and accrued cost figure; defined now, unused by Phase 61 components |

- Weights: 400 and 700 only. No 500/600.
- Text does not scale with viewport width (no `clamp()` in the new components).
- Buttons use Label size at 700 (existing buttons already run 700); button text may not be uppercase.
- German text expands up to roughly 35% over English: no fixed-width buttons or badges, labels wrap instead of truncating, and nothing in the new components uses `text-overflow: ellipsis` on a state, cost, or reason string.
- Numbers and currency always go through `Intl` with `currentLocale()` (EUR; German renders `0,42 €`).

## State and Cost Model (FND-02, FND-03)

One pure function, `deriveServerState(server, options?)`, decides the badge for every surface. Fleet card, workspace header, profile notifications, and the confirmation dialog call it; no component compares `deployment.status` strings itself.

Inputs from `GameServerDto`: `deployment?.status` (`EDeploymentStatus`), `deployment?.possibleCost`, `pendingJobCount`, `deployment` presence. Output: `{ state, cost, tone, labelKey, detailKey? }`.

State rules, first match wins:

| Order | Condition | State | Tone |
|-------|-----------|-------|------|
| 1 | status `Failed`, `PreservationFailed`, or `TerminatedDueToFault` | `attention` | danger |
| 2 | status `Provisioning`, `WaitingForWorker`, or `Preparing` | `starting` | info |
| 3 | status `Running` | `running` | success |
| 4 | status `Stopping`, `Terminating`, or `TerminatingDueToFault` | `stopping` | info |
| 5 | status `Stopped` or `Terminated`, or no deployment, and `possibleCost` is true | `unconfirmed` | warning |
| 6 | status `Stopped` or `Terminated`, or no deployment, `possibleCost` false, `pendingJobCount` > 0 | `working` | info |
| 7 | status `Stopped` or `Terminated`, or no deployment, `possibleCost` false, `pendingJobCount` = 0 | `off` | neutral |
| 8 | any other status string (API added a value) | `unknown` | warning if `possibleCost` else neutral |

Cost rules, independent of state:

| Condition | Cost |
|-----------|------|
| `possibleCost` true and status `Running` | `live` |
| `possibleCost` true, any other state | `maybe` |
| status in `Provisioning`, `WaitingForWorker`, `Preparing`, `Running`, `Stopping`, `Terminating`, `TerminatingDueToFault` regardless of `possibleCost` | `live` (an allocated deployment is never "not costing") |
| everything else with `possibleCost` false | `none` |

Invariant (FND-03), enforced by a property test over every `EDeploymentStatus` value x `possibleCost` x `pendingJobCount in {0, 1}` x `deployment` null/present: when `possibleCost` is true the state is never `off` and the cost is never `none`; when the state is `off` the cost is always `none`.

Notifications (FND-02): `GameServerNotificationDto.statusLabel` is the raw deployment stage or the literal "Stopped"/"Lifecycle work pending" and must not be rendered. The profile menu joins each notification to the fleet query result by `serverId` (same React Query key, no new endpoint) and renders `ServerStateBadge` + `CostIndicator` from `deriveServerState`. If the server is not in the fleet result yet, render `unknown` state with the notification's `possibleCost` deciding the cost chip (`maybe` or hidden), never "Stopped". API changes are out of scope for this phase.

Presentation:
- `ServerStateBadge`: 16px icon + Label-size text. Icons: off `CircleOff`-style outline, starting/stopping/working `ArrowSync` (static, spins only when motion is allowed), running `CheckmarkCircle`, attention `DismissCircle`, unconfirmed and unknown `Warning`. Choose the nearest `@fluentui/react-icons` regular glyph; the choice is fixed per state and tested.

## Cost Confirmation Contract (FND-04, FND-05)

One dialog, one request path. Every cost-bearing action opens `CostConfirmDialog` through `useCostConfirmation().request({ serverId, actionId, source })`. `source` is one of `workspace-primary`, `workspace-action`, `fleet-card`, `notification`, `deep-link`, `create` (Phase 64) and is used only for analytics-free test assertions and focus return.

In scope (must route through it): any action whose `costImpact` is `StartsCost` or `StopsCost` (today `start`, `stop`, `terminate`). Actions with `KeepsCostRunning` or `NoCostImpact` keep the existing confirmation rules (`confirmationText`, challenge) but render in the same dialog shell, with the cost row shown for `KeepsCostRunning` ("Cost keeps running") and hidden for `NoCostImpact`.

Entry points that currently bypass or duplicate it and must be converted:
1. Profile menu notification cost-stop: executes immediately when the action has no `confirmationText` or challenge. It must open the dialog instead.
2. Fleet card terminate link: keeps navigating to `/command/servers/{id}?action=terminate` (no new pathnames), which the deep-link path turns into the dialog.
3. Workspace primary action and `ServerActions` list: the existing per-action dialog is replaced by the shared one.
4. `?action=` deep link: today it only opens for actions that have a `confirmationChallenge`, so `?action=start` silently does nothing. It opens for every found, enabled, non-pending action.
5. Start is non-confirming at the API (`requiresConfirmation` false), so this dialog is the only guard for a cost-starting action. A test fixture currently models Start as `dangerous: true`; correct the fixtures so Start is `dangerous: false` and the dialog still opens.

Anatomy, top to bottom, inside `ConfirmDialog` (native `<dialog>`, `showModal()`):
1. Kicker (Label): "Confirm action".
2. Title (Heading 20/700), from the copy table, wrapping with `overflow-wrap: anywhere` for long server names (names can be 256 characters).
3. Body (Body 14/400), one or two sentences from the copy table.
4. Facts `dl` (Estimated cost, Cost owner, How to stop). The estimated amount renders at Heading size 20/700; labels at Label size. Two columns (term / value) above 520px, stacked at <= 520px.
5. Secondary server note, only when an action has API text that no key covers: collapsed `details` titled "Server note" with the text in a `lang="en"` span. Never replaces the copy above.
6. Challenge field when `confirmationChallenge` exists: label "Type {{challenge}} to continue" using the existing `React_Confirm_*` pieces, a shared text field with `--utf-border-control`, `autoComplete="off"`, helper text "Enter it exactly as shown." The confirm button is disabled until the value matches exactly; the helper text is linked with `aria-describedby`.
7. Error slot (`role="alert"`), empty until a request fails.
8. Actions: the outcome-specific dismiss button (`ghost`, label from the `Dismiss label` columns of the Action vocabulary table, for example "Don't start server") and the confirm button (label is the action label, for example "Start server"). Confirm variant: `gold` for `start`; `danger` for `stop` and `terminate`; `primary` for other actions. Order: dismiss then confirm in the row at > 520px; stacked full width with confirm on top at <= 520px. The dismiss label is passed to `ConfirmDialog` through its existing `cancelLabel` prop, resolved from the action id; there is no shared default.

States of the dialog:

| State | Behavior |
|-------|----------|
| Idle | Initial keyboard focus on the dismiss button (Enter never starts or stops cost by accident). Confirm enabled unless a challenge is unmatched. |
| Pending | Confirm shows a `Spinner` and "Starting..." / "Shutting down..." (key per action), `aria-busy="true"` on the dialog, dismiss button and Escape disabled, backdrop click ignored. |
| Error | Dialog stays open, error slot filled with the request-error copy, Confirm re-enabled, focus moves to the error slot. |
| Success | Dialog closes, an app toast announces "requested", queries for fleet, server, jobs, operations, and notifications are invalidated, `action` is removed from the URL (`replace`), focus returns to the invoking control (or the page `h1` for a deep link). |
| Estimate missing | Dialog still opens with the fallback row. A missing estimate never blocks the action and never hides the row. |

Responsive: dialog `width: min(480px, 100vw - 32px)`, `max-height: calc(100dvh - 32px)`, body scrolls, padding 24px at > 520px and 16px at <= 520px, section gap 16px. Focal point: the title and the Estimated cost row (largest type and first fact).

Motion: dialog fades in over `--utf-motion-slow` (no slide); disabled when `prefers-reduced-motion: reduce`.

## Deep Link and Unavailable Action Contract (FND-05, ACC-03)

### `?action=` resolution

Resolved once the server query has data; nothing action-related renders while loading, and a load error shows the existing error panel only.

| Case | Result |
|------|--------|
| Viewer lacks view permission, or server not found | Existing forbidden / not-found panel. No action hint (no information leak about actions). |
| Action found (case-insensitive id), `enabled`, not `pending` | Open `CostConfirmDialog` for it. Never auto-executes. |
| Action found but `!enabled` or `pending` | `DeepLinkActionNotice` (`StatePanel kind="warning"`, `role="status"`) at the top of the workspace content: "{{action}} isn't available right now. {{reason}}", with a Dismiss control. Focus is not stolen. |
| Action id not present for this server | `DeepLinkActionNotice` (`kind="info"`): "This server has no action called "{{id}}"." The id is rendered as text, truncated to 40 characters. |
| Dialog cancelled, confirmed, or notice dismissed | Remove `action` from the query string with `replace`, keep other params. |

Fleet and notification cost-stop controls follow the same rules: they never execute directly.

### Disabled action with reason (ACC-03)

Rule: an action the viewer cannot perform on a screen that offers it is rendered disabled with its reason visible. Whole destinations the viewer can never use (navigation entries, whole admin areas) stay hidden. Never both, never a dead link.

Pattern, implemented once as an additive `unavailableReason` capability of the shared action control:
- The control uses `aria-disabled="true"` instead of the `disabled` attribute so it stays focusable; activating it does nothing.
- The reason is visible text directly below the control (Body size, `--utf-text-muted`, 16px info icon), wraps instead of truncating, and is linked with `aria-describedby`.
- `title`-only reasons are not allowed (not available on touch or to keyboard users).
- Reason text goes through `UnavailableReason`, which owns the mapping table above and the `lang="en"` fallback for unknown strings.
- Applies to: fleet card cost-stop and start, workspace primary and secondary actions, notification cost-stop, and the fleet "Create server" control (shown disabled with "You need permission to create servers. Ask an administrator." / "Du brauchst die Berechtigung, Server zu erstellen. Frage eine Administration." when the member lacks the creation claim).

## Accessibility and Responsive Contract (FND-06 gate for this phase)

Phase 69 closes FND-06 formally; each phase enforces it for what it touches.

- Dialog: native `<dialog>` with `showModal()` (focus trap, inert background), `aria-labelledby` the title, `aria-describedby` the body and facts, Escape cancels unless pending, focus returns to the invoker.
- Live regions: notices use `role="status"`; request errors use `role="alert"`; state changes in the fleet do not steal focus.
- Badges and chips carry text and icon; the icon is `aria-hidden`; no information is color-only.
- Disabled actions stay focusable (`aria-disabled`) and expose their reason via `aria-describedby`.
- Icon-only controls (Dismiss) require `aria-label` and a 44px target at <= 800px; minimum target is 24px everywhere (WCAG 2.2 target size).
- All interactive elements are reachable in DOM order; no positive `tabindex`; the focus ring uses `--utf-focus-ring` on every control in the new components.
- 320px: no horizontal page scroll; dialog, notices, badges, and cost chips wrap; verified at 320x568 in English and German in unit/e2e tests for the Phase 61 components (full Playwright mobile projects arrive in Phase 69).
- Automated check for this phase: an `axe` scan (jest-axe or `@axe-core/playwright`, a dev dependency) of the confirmation dialog in each state and of the deep-link notice; zero violations at WCAG 2.1 AA tags.
