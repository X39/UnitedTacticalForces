# Phase 61 Parity Matrix: Server Capabilities

This matrix is the capability parity checklist for the v2.1 server experience redesign (requirement FND-07,
decisions D-08 and D-12). It has one row for every capability the React server screens expose today: workspace
tabs, every `hostingService` method, projected lifecycle actions, fleet and entry points, facts shown, change
operations, files, jobs, the server record, create-form field groups, and the adjacent configuration-profile and
finance pages.

Rules:

- Every row starts as `pending`. Each UI phase (62 to 69) updates the rows for the capabilities it touches.
- Status vocabulary: `pending` (initial value), `kept`, `relocated`, `removed`.
- `relocated` requires a non-empty New location (not an em dash).
- `removed` requires a written reason and an explicit user sign-off recorded in Evidence (the word "sign-off" must
  appear in the Evidence cell).
- Rows are never deleted. A capability that disappears from the UI keeps its row with status `removed`.
- A new capability discovered later gets a new row with a deterministic ID of the same family.
- Row IDs are deterministic: `TAB-<tabId>` per workspace tab id, `SVC-<method>` per `hostingService` method,
  `ACT-<actionId>` per projected lifecycle action. The Vitest guard `tests/hosting/parity-matrix.test.ts` fails
  when a tab id or a `hostingService` method has no row, when a status is empty or unknown, or when a relocated or
  removed row lacks its required text.
- Keep the table a single table, one row per line, with no empty cell (use an em dash when a value does not apply).
- The Phase column names the planned owner phase from the roadmap (62 Fleet and Quick Actions, 63 Workspace Shell
  and Activity, 64 Guided Server Creation, 65 Change a Server, 69 Consistency, Accessibility and Verification).
