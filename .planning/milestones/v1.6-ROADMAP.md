### Phase 25: Billing Import And Normalization

**Goal:** Add a durable provider billing import foundation that stores Hetzner invoice/consumption exports as normalized, redacted, idempotent billing facts.

**Requirements:** COST-13, COST-20

**Success Criteria:**

1. Billing import batch entities, EF configuration, migrations, DTOs, and admin-only API boundaries store provider, source period, invoice/reference metadata, file hash, row counts, status, importer, timestamps, and sanitized diagnostics.
2. Hetzner consumption CSV parsing normalizes supported rows into provider, resource reference, usage period, amount, currency, tax/source metadata, and source-row diagnostic fields.
3. Duplicate import detection prevents accidental reimport of the same source unless explicitly recorded as ignored or superseded.
4. Parser failure and row-level diagnostics are bounded and redacted; raw provider token, Steam, worker, and full raw row details are not exposed through logs or DTOs.
5. Tests cover representative CSV fixtures, invalid rows, duplicate source hashes, status transitions, authorization, restart persistence, and redaction.

**Plans:** 3/3 plans complete

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 25-02-PLAN.md - Hetzner consumption CSV parser, normalized line items, and diagnostics.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 25-03-PLAN.md - Admin import API, duplicate handling, redaction, and parser verification.

### Phase 26: Cost Matching And Discrepancy Engine

**Goal:** Match imported provider billing rows to UTF cloud resources, sessions, billing assignment intervals, and estimated cost snapshots while preserving unresolved and ambiguous cases for review.

**Requirements:** COST-21, COST-22

**Success Criteria:**

1. Matching service links provider line items to `CloudResourceInventoryRecord`, `CloudGameServerSession`, `GameServerBillingAssignment`, and `CloudCostSnapshotContribution` records using exact provider references before lower-confidence fallbacks.
2. Provider-derived cost is allocated across historical billing assignment intervals when a billing owner transfer overlaps the imported usage period.
3. Match records persist confidence, match method, review status, discrepancy amount, currency, and sanitized explanation details.
4. Ambiguous, low-confidence, and unmatched rows remain visible as unresolved review items instead of being silently assigned.
5. Tests cover exact matches, missing inventory, ambiguous names, ownership transfers, estimate variance, stale/deleted provider resources, and idempotent reruns.

**Plans:** 3/3 plans complete

**Wave 1**

- [x] 26-01-PLAN.md - Matching model, exact provider-resource matching, and rerun idempotency.

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 26-02-PLAN.md - Owner interval allocation and estimated-versus-provider discrepancy calculation.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 26-03-PLAN.md - Ambiguous/unresolved review queue, confidence rules, and matching tests.

### Phase 27: Adjustment Workflow And Audit

**Goal:** Allow authorized administrators to record reviewed cost corrections as explicit immutable overlays while preserving source imports, estimates, ownership, and audit history.

**Requirements:** COST-14, COST-23, RELY-22

**Success Criteria:**

1. Adjustment entities and DTOs store provider/import/match links, owner/resource/session scope, previous estimate or reconciled amount, adjusted amount, currency, reason, actor, status, and timestamps.
2. Authorized administrators can create, apply, reject, and inspect adjustments with durable audit events and without mutating raw import line items or original estimated cost snapshots.
3. Adjustment application preserves billing owner attribution, provider source evidence, and assignment interval history even when the current owner differs from the historical owner.
4. Direct API calls cannot create or apply adjustments without the required administrative claim and valid reconciled scope.
5. Tests cover adjustment immutability, audit records, authorization boundaries, invalid scopes, duplicate applications, ownership transfers, and redacted details.

**Plans:** 3/3 plans complete

**Wave 1**

- [x] 27-01-PLAN.md - Adjustment schema, service model, and immutable overlay semantics.

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 27-02-PLAN.md - Adjustment create/apply/reject APIs with audit and authorization.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 27-03-PLAN.md - Adjustment safety, ownership transfer, redaction, and immutability verification.

### Phase 28: Reconciled Cost Visibility And Verification

**Goal:** Surface estimated, provider-imported, reconciled, and adjusted cost history to administrators and affected owners through generated clients, then verify the complete v1.6 workflow.

**Requirements:** VIS-19, VIS-20, VIS-21, RELY-21, RELY-23

**Success Criteria:**

1. Admin API projections expose import batches, parse diagnostics, match/discrepancy summaries, unresolved row counts, adjustments, source labels, and review status.
2. Server-owner scoped projections expose estimated, reconciled, and adjusted cost labels/history only for game servers and billing scopes the owner is allowed to inspect.
3. Generated Kiota clients and WebApp repository facades are refreshed for v1.6 billing reconciliation surfaces; no raw browser HTTP bridge is introduced.
4. End-to-end import, matching, review, and adjustment state survives API restarts and reruns without duplicating source rows, matches, or applied adjustments.
5. Verification covers CSV fixtures, duplicate imports, matching confidence, ownership transfers, adjustment immutability, visibility projection, authorization, and secret/raw-row redaction.

**Plans:** 3/3 plans complete

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 28-02-PLAN.md - Admin and server-owner reconciled cost visibility.
