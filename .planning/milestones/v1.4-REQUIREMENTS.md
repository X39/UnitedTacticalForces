# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-17
**Milestone:** v1.4 Running Cost Visibility And Provider Reconciliation
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.4 Requirements

Requirements for the running cost visibility and provider reconciliation milestone. Each requirement maps to exactly one roadmap phase.

### Cost Visibility

- [x] **COST-05**: User can see running cost snapshots while real cloud resources exist.
- [x] **COST-08**: UI labels cloud costs as estimated, reconciled, or adjusted.
- [x] **COST-09**: User can see accumulated historical cost for cloud sessions they are allowed to inspect.
- [x] **COST-10**: Cost snapshots preserve billing account and billing assignment attribution at the time the cost interval is recorded.
- [x] **COST-11**: Cost calculations treat provider deletion, not runtime stop or powered-off state, as the cost-stop boundary for billable Hetzner resources.
- [x] **COST-12**: Administrator can inspect cost snapshot assumptions, metadata freshness, currency, confidence, and billable resource contribution without seeing secret material.

### Provider Reconciliation

- [x] **HETZ-08**: Administrator can reconcile known inventory records against real Hetzner resources and identify orphans.
- [x] **HETZ-09**: The Hetzner provider boundary can read live servers, floating IPs, volumes, and firewalls through paged, secret-safe provider calls.
- [x] **HETZ-10**: Reconciliation runs are persisted with status, start/end timestamps, provider resource counts, finding counts, and sanitized failure details.
- [x] **HETZ-11**: Reconciliation findings identify missing provider resources, unknown provider resources, state mismatches, and cleanup-needed billable resources without deleting provider resources automatically.
- [x] **HETZ-12**: Newly provisioned Hetzner resources carry UTF-owned labels or equivalent safe metadata that improves future reconciliation without exposing credentials.

### Visibility And Operations

- [x] **VIS-12**: Administrator can see current cost, accumulated cost, reconciliation status, finding counts, orphan indicators, and cleanup risk in the cloud operations surface.
- [x] **VIS-13**: Server owner can see current cost, accumulated cost, cost source label, and relevant reconciliation risk for their allowed cloud server scope.
- [x] **VIS-14**: Admin and owner views distinguish runtime cleanup from provider teardown and show billable resources that still exist after runtime stop.
- [x] **VIS-15**: Cost and reconciliation DTOs are available through generated WebApp API clients and repository facades, not raw browser HTTP bridges.

### Safety And Verification

- [x] **RELY-14**: Cost snapshot and reconciliation state survives API restarts and can be recomputed or refreshed idempotently without duplicating unsafe findings.
- [x] **RELY-15**: Provider tokens, Steam credentials, worker credentials, bootstrap credentials, bearer headers, and secret-bearing user data are not exposed through cost snapshots, reconciliation findings, audits, DTOs, generated clients, or logs.
- [x] **RELY-16**: Tests cover cost math, deletion-as-cost-stop behavior, ownership transfer attribution, provider list pagination/failures, reconciliation finding types, authorization boundaries, and secret redaction.

## Out of Scope

Explicitly excluded from v1.4.

| Feature | Reason |
|---------|--------|
| Spending limits, approvals, and automatic shutdown | Policy enforcement depends on reliable cost snapshots and provider reconciliation signals from this milestone. |
| Payment processing, payment-provider billing, or customer invoicing | CR-0001 defines billing as internal attribution, not payment collection. |
| Claiming provider invoice-grade actual cost | v1.4 uses internal estimates and provider-resource reconciliation, not authoritative provider invoices or exports. |
| Automatic deletion of orphan provider resources during reconciliation | Reconciliation is read-only in this milestone; destructive cleanup remains an explicit audited action. |
| OPS-02 live/browser/provider UAT closure without operator evidence | Live UAT requires credentials, provider approval, budget, cleanup window, and final provider-side billable resource verification. |
| Multi-session cloud workers | One server per worker remains the safe billing, firewall, port, storage, and cleanup model. |
| Multi-provider orchestration | Hetzner remains the first real cloud target until cost/reconciliation behavior is proven. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud orchestration expands. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
