# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-22
**Milestone:** v1.11 CR-0001 Operator Live Evidence Closure
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.11 Requirements

Requirements for the operator-controlled CR-0001 live evidence closure pass. The implementation is expected to be ready from previous milestones; this milestone captures real operator, browser, provider, runtime, teardown, and redaction evidence or records exact blockers without claiming pass status. As of 2026-06-22, live UAT is deferred by operator direction, so unresolved live evidence requirements remain deferred rather than active input requests.

### Approval And Preflight

- [x] **PREP-01**: Operator can complete the live approval package with approver, timestamp, Hetzner project, token reference, resource shape, budget ceiling, maximum lifetime, cleanup window, selected game server, billing account, template/profile snapshot, dry-run plan, and policy approval identifier when required.
- [x] **PREP-02**: Operator can verify authenticated administrator and server-owner access to `/servers/cloud`, `/servers`, and required API surfaces without storing cookies, authorization headers, bearer tokens, OAuth material, or session secrets.
- [x] **PREP-03**: Operator can verify provider configuration, provider metadata freshness, active billing owner, current dry-run plan, usable template/profile snapshots, cost budget, policy gate, and reconciliation state before any live provider mutation.

### Live Provisioning

- [ ] **PROV-01**: Operator can execute exactly one approved live Hetzner provisioning path from the reviewed WebApp plan and capture cloud session id, provider resource identifiers, endpoint, billing owner, template/profile context, cost source, policy state, reconciliation state, and audit records without credential material.
- [ ] **PROV-02**: Operator can record safe failure or partial-provisioning evidence with owner attribution, cleanup risk, retry or manual cleanup action, and no duplicate or hidden billable resources.

### Runtime And Visibility

- [ ] **RUNT-01**: Operator can verify cloud worker bootstrap, registration, heartbeat, and capabilities, then execute Steam/Arma install, configure, start, stop, update, and log collection or classify an explicit environment blocker with safe diagnostics.
- [ ] **RUNT-02**: Authenticated administrator and server-owner views expose lifecycle state, worker health, endpoint, logs, current cost, accumulated cost, policy, reconciliation, billing owner, template/profile context, and audit history for the live scenario without exposing provider, Steam, worker, authorization, bearer, cookie, or raw secret-bearing payload data.

### Cleanup And Redaction

- [ ] **CLN-01**: Operator can execute provider teardown and any required manual cleanup fallback, then record provider-side server, floating IP, volume, firewall, and final billable resource counts with final billable resource count `0` before pass classification.
- [ ] **RED-01**: Operator can complete redaction review for approval records, browser evidence, provider evidence, worker/runtime evidence, logs, screenshots, comments, and exported artifacts before classifying Phase 30 or CR-0001 acceptance as passed, failed, or blocked.

### Acceptance Classification

- [ ] **ACC-01**: Operator can update Phase 30, OPS/EVID gates, and CR-0001 acceptance criteria from the captured evidence with passed, failed, blocked, or deferred status and concrete follow-up actions for any unmet criteria.

## Out of Scope

Explicitly excluded from v1.11.

| Feature | Reason |
|---------|--------|
| New cloud product features beyond fixes required to safely complete the live evidence pass | v1.11 is an operator evidence closure milestone, not a feature expansion milestone. |
| Live provider mutation before approval, preflight, budget, cleanup-window, policy, reconciliation, and redaction readiness are complete | Provider actions can create real costs and must stay operator-controlled. |
| Marking live Hetzner, Steam, Arma, browser, teardown, cleanup, or final billable-resource evidence as passed without captured evidence | This milestone exists to produce trusted evidence, not infer success from implementation tests. |
| Payment processing, payment-provider billing, customer invoicing, taxes, checkout, or legal invoice generation | CR-0001 defines billing as internal attribution, not payment collection. |
| Multi-provider orchestration | Hetzner remains the first real cloud target until runtime and cleanup behavior are proven. |
| Multi-session cloud workers | One server per worker remains the safe billing, firewall, port, storage, and cleanup model. |
| Headless clients, resource resize, snapshots, backups, marketplace templates, or broad template marketplace behavior | These remain future extensions after live CR acceptance. |
| Manual SSH or provider-console workflows as the normal path | Manual provider cleanup is allowed only as fallback evidence when automated teardown fails or is blocked. |
| Treating runtime stop or runtime cleanup as provider cost stop | Hetzner resources remain billable until provider teardown/deletion succeeds. |
| Persisting raw provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, bearer tokens, cookies, OAuth codes, or raw secret-bearing payloads in evidence | Security constraints require redaction and allowlisted evidence. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud orchestration is validated. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
