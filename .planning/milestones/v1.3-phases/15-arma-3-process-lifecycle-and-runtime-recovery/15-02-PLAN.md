<objective>
Extend the worker-facing API protocol so cloud workers can report runtime status durably and update-stream-visible
logs/status without exposing credentials.
</objective>

<tasks>
<task id="15-02-01" type="execute">
<action>
Add a `CloudWorkerRuntimeStatusPayload` and expose a job-scoped `runtime-status` report endpoint under
`lifecycle-workers/cloud/{workerId}/jobs/{jobId}`.
</action>
<acceptance_criteria>
- Reports require the authenticated worker assigned to the running job.
- Accepted reports refresh the job lease.
- Wrong worker, wrong job, and wrong session reports cannot mutate game-server state.
</acceptance_criteria>
</task>

<task id="15-02-02" type="execute">
<action>
Persist accepted runtime status reports into `GameServer.Status`, append `LifetimeEvent` rows, and broadcast
`LifetimeStatusHasChanged` update-stream messages. Make worker log reports broadcast `LogMessage` updates after
persistence.
</action>
<acceptance_criteria>
- API restart does not lose last known cloud runtime status because the status is stored on `GameServer`.
- Lifetime events retain the requesting actor from the lifecycle job where available.
- Worker log payloads are sanitized before persistence and before update-stream broadcast.
</acceptance_criteria>
</task>

<task id="15-02-03" type="execute">
<action>
Allow cloud heartbeat payloads to carry optional runtime status for worker restart recovery when no lifecycle job is
running.
</action>
<acceptance_criteria>
- Heartbeat status updates are accepted only after normal worker credential and session validation.
- Heartbeat status updates are scoped to the worker's assigned game server.
- Returned DTOs and audit records do not expose worker credentials or command-line secrets.
</acceptance_criteria>
</task>
</tasks>
