## Phase Interaction Contract

### Route And Scope

| Surface | Contract |
|---------|----------|
| `/servers` | Primary owner/operator cloud workflow. Policy gate panel appears after a valid dry-run review and before any enabled billable action. Warning acknowledgement, approval status, and blocked next steps stay with the selected server. |
| `/servers` for approvers | If the signed-in user has the required approval authority, show approve/deny controls for approval requests tied to the selected server/session/dry-run scope. Do not expose unrelated global policy administration here. |
| `/servers/cloud` | Admin provider/fleet console. It may keep a policy tab or pending approval queue for administrators, but owner workflow copy must not route normal users there as the next step. |
| Policy administration | Out of scope. Do not add spending policy creation, threshold editing, automatic action configuration, or global policy redesign. |
| Generated client boundary | Razor code consumes repository facade methods and hand-written safe models only. Do not bind generated DTOs, request builders, `AdditionalData`, raw JSON, raw exception bodies, headers, or request/response payloads to UI. |
| Billable action boundary | Provisioning, runtime lifecycle, and provider teardown controls remain disabled unless the current gate state, action kind, scope key, billing owner, dry-run/session identity, approval request, and expiration match. |
| UAT boundary | Manual authenticated browser UAT, live Hetzner resource creation, Steam validation, Arma runtime validation, provisioning, teardown, provider billable-resource verification, and Phase 30 live evidence remain deferred and must not be claimed as passed. |

### Policy Gate Flow

| Step | UI Contract | Blocking Rule |
|------|-------------|---------------|
| 1. Review plan | A valid fresh dry-run plan shows `Review policy decision` as the next safe step. This command evaluates or refreshes policy state, not provider mutation. | Disabled until the selected dry-run plan is valid, fresh, current, and owner-matched. |
| 2. Show gate outcome | Render exactly one selected policy gate panel with outcome, decision id, action kind, scope key, owner ids, projected cost, expiration, and required next step. | Do not hide expired, denied, mismatched, or missing approval states behind generic errors. |
| 3. Allow | Allow state shows success treatment and makes the matching billable next action eligible for later execution only when identity still matches. | If selected server, owner, dry-run plan, session, scope, or expiration changes, return to blocked policy review. |
| 4. Warning | Warning state shows acknowledgement copy and `Acknowledge warning`. User must acknowledge the specific decision id before the action can continue. | No auto-acknowledgement. A stale or different decision id blocks continuation. |
| 5. Approval required | Approval-required state shows pending approval request identity, approver next step, expiration, and audit context. Owner sees request status; approver sees approve/deny controls if authorized. | Billable action stays disabled until the matching request is approved and unexpired. |
| 6. Denied or expired | Denied, expired, missing, or mismatched approval states show an error/warning result with the next required action. | Billable action remains disabled. Do not offer a continuation button. |
| 7. Approved continuation | After approval, the owner/operator can run `Continue approved action` only for the same action kind and scope identities displayed in the gate panel. | Passing an approval request id for a different server/session/owner/action is never represented as a UI success. |

### Gate State Contract

| State | Visual Treatment | Required Content | Action Contract |
|-------|------------------|------------------|-----------------|
| No policy decision | `FluentMessageBar` warning inside `section.detail-section` | Selected server, selected owner, dry-run plan id if present, next non-mutating step | Show `Review policy decision` if prerequisites are valid; otherwise show the exact prerequisite to fix. |
| Loading | `FluentStack` plus `FluentProgress` in the policy panel | Action noun, selected server, selected plan/session | Disable only policy evaluation/continuation and conflicting selected-server billable actions. |
| Policy allow | Success message bar plus `status-badge status-success` | Decision id, action kind, scope key, projected total, owner ids, expiration/evaluated timestamp | Enable only the matching next action for later phases; in Phase 36, do not create provider resources unless existing endpoint flow is explicitly policy-allowed and already in scope. |
| Policy warning | Warning message bar plus `status-badge status-info` | Decision id, reason code, projected current/additional/total cost, expiration, acknowledgement requirement | Primary action is `Acknowledge warning`; pass only `acknowledgedDecisionId` for the shown decision. |
| Approval required | Warning message bar plus `status-badge status-warning` | Approval request id, decision id, action kind, requester, owner ids, scope ids, projected costs, reason code, expiration | Owner action is `Refresh approval status`; approver actions are `Approve request` and `Deny request` after confirmation. |
| Approved | Success message bar plus `status-badge status-success` | Approval request id, resolved by, expiration, decision id, matching scope | Owner action is `Continue approved action` only while approval is unexpired and identities match. |
| Denied | Error message bar plus `status-badge status-danger` | Decision id, approval request id if present, reason code, sanitized explanation, next safe action | No continuation. Show `Regenerate dry-run plan` or `Refresh policy status` when appropriate. |
| Expired | Warning message bar plus `status-badge status-neutral` | Approval request id, expiration timestamp, decision id, required next step | No continuation. Primary action is `Refresh policy status` or `Request approval` if a new request path is available. |
| Scope mismatch | Error message bar plus `status-badge status-danger` | Mismatched identity labels: server, session, dry-run plan, billing account, billing assignment, action kind, or scope key | No continuation. Require policy re-evaluation from current selected state. |
| Failure | Error message bar | Sanitized failure summary, retryability, action id/correlation if allowlisted | Show `Retry policy action` only when repository result marks retryable; otherwise show `Refresh policy status`. |
| Redaction blocked | Error message bar | Redaction-blocked copy only | Do not display returned gate, approval, audit, or cost details. Show `Refresh policy status`. |

### Approver Interaction Contract

| Area | Contract |
|------|----------|
| Approval queue | Show pending requests as a compact list or table grouped by selected server first. Each row shows request id, action kind, server/session/dry-run id, billing owner ids, projected total, reason code, requester, expiration, and status. |
| Approval detail | Selecting a request opens or focuses an inline `section.detail-section` with the same allowlisted scope and cost fields plus recent audit context. Do not use a global admin form style inside the owner workflow. |
| Approval reason | Approve and deny forms use a visible multiline label `Reason`. Reason is optional only if the API contract allows it, but the UI should still invite a short audit note. |
| Approval expiration | Approve form includes an expiration field labeled `Approval expires`. Default copy must state that approvals are temporary and scoped. |
| Approve confirmation | Confirmation title: `Approve policy request`. Body: `Approve this request only for the displayed action, owner, scope, and expiration.` Primary button: `Approve request`. |
| Deny confirmation | Confirmation title: `Deny policy request`. Body: `Deny this request and keep the billable action blocked for the displayed scope.` Primary button: `Deny request`. |
| Post-resolution | After approve or deny, replace controls with resolved status, resolver if allowlisted, timestamp, reason if sanitized, and `Refresh policy status`. |
| Unauthorized approver | Users without approval authority see request status and next step copy, not disabled approve/deny buttons that imply permission can be fixed locally. |

### Allowed Display Fields

| Category | Allowed Fields |
|----------|----------------|
| Identity | Server id/title, session id, dry-run plan id, policy decision id, approval request id, audit record id, billing account id, billing assignment id, resource inventory id when already inventory-visible. |
| Policy scope | Action kind, action label, scope key, provider identifier, policy id/name, warning/approval/limit threshold labels, effective status. |
| Policy decision | Decision label, evaluation status label, reason code, required next step, current cost, projected additional cost, projected total cost, currency, cost metadata freshness, cleanup-risk counts, evaluated timestamp, expiration timestamp. |
| Approval request | Status, requester id, resolver id, created/updated/resolved/expires timestamps, request reason, approval reason, denial reason, projected costs, matching scope ids. |
| Audit context | Audit id, kind, actor id if allowlisted, timestamp, sanitized summary, related server/session/owner/action ids. |
| Sanitized diagnostics | Sanitized failure summary/details, retryable flag, validation summary, high-level reason labels. |

### Forbidden Display Fields

| Forbidden Field Type | Contract |
|----------------------|----------|
| Provider secrets | Provider tokens, token values, token references that identify secret storage, authorization headers, bearer tokens, provider raw credentials. |
| Steam secrets | Steam username, Steam password, Steam API key, Steam guard/session values, DepotDownloader credentials. |
| Worker secrets | Worker credentials, bootstrap credential secrets, worker hashes, worker registration secrets, private keys, SSH private material. |
| Raw policy payloads | Raw policy input snapshots, risk details JSON, audit details JSON, approval audit JSON, generated DTO dumps, `AdditionalData`, exception bodies, request/response bodies, headers, and raw validation details. |
| Misleading evidence | UI copy, screenshots, logs, or notes that imply live Hetzner, Steam, Arma, authenticated browser, provider mutation, provisioning, teardown, or Phase 30 UAT passed. |

### Copy Boundary Rules

- Use "policy decision", "approval request", "warning acknowledgement", "scope", "expiration", "billing owner", "cost responsibility", "internal attribution", and "billable action".
- Use "provider teardown" only when referring to the later cost-stop action; do not call runtime stop or runtime cleanup a cost stop.
- Do not use "payment", "invoice", "checkout", "charge", "customer billing", "taxes", "launch", "deploy", or "provision now" in Phase 36 copy.
- Do not describe a denied or expired policy decision as a technical failure. It is an explicit workflow state.
- Do not route owner workflow users to `/servers/cloud` as the normal way to resolve their current policy gate.

## Layout Contract

| Area | Contract |
|------|----------|
| Page shell | Reuse `.servers-page`: flex column, 16px padding, 16px page gap. |
| Header | Reuse `.servers-toolbar`; do not put policy gate badges in the page title row. |
| Main workspace | Keep `FluentDataGrid` first. Policy gate and approval panels appear below the grid in the selected-server workflow. |
| Policy panel | Use `section.detail-section cloud-workflow-result-panel` or a sibling `policy-gate-panel` with one visible selected policy state. Do not nest cards inside it. |
| Gate header | Left: `Policy decision` title and one-line scope copy. Right: outcome badge. Stack on mobile. |
| Gate summary | Use `dl.meta-grid` for decision id, approval request id, action, scope, owner, costs, status, expiration, and next step. Values must wrap with `overflow-wrap: anywhere`. |
| Approval queue | Use `.data-table` or `FluentDataGrid` for pending requests. Keep columns compact: request, action, scope, projected total, expires, status, requester, actions. |
| Approval detail | Use a single `section.detail-section` with `dl.meta-grid`, optional `.data-table` for audit rows, and `div.guided-actions` for approve/deny/refresh. |
| Actions | Use `div.guided-actions` for `Review policy decision`, `Acknowledge warning`, `Refresh approval status`, `Approve request`, `Deny request`, and `Continue approved action`. On mobile, buttons are full width. |
| Mobile | At max-width 860px, policy summaries, approval tables, metadata grids, and actions collapse to one column; table values wrap with `overflow-wrap: anywhere`; icon-only actions are at least 44px. |

## Component Contract

| Need | Component |
|------|-----------|
| Policy evaluation | `FluentButton` with `Appearance.Accent`, `ShieldCheckmark` or `Shield` icon, label `Review policy decision`. |
| Warning acknowledgement | `FluentButton` with `Appearance.Accent`, `CheckmarkCircle` icon, label `Acknowledge warning`. |
| Approval refresh | `FluentButton` with `ArrowSyncCircle` icon, label `Refresh approval status` or `Refresh policy status`. |
| Approved continuation | `FluentButton` with `Appearance.Accent`, `PlayCircle` icon, label `Continue approved action`; enable only when identity and expiration match. |
| Approve request | `FluentButton` with `Appearance.Accent`, `CheckmarkCircle` icon, label `Approve request`, shown only to authorized approvers after confirmation. |
| Deny request | `FluentButton` with `DismissCircle` or `Delete` icon, label `Deny request`, danger styling if available, shown only to authorized approvers after confirmation. |
| Confirmation | Fluent dialog through existing `FluentDialogProvider`; title and primary button must name the action. |
| Loading | `FluentStack` plus `FluentProgress` with action-specific loading copy. |
| Page/result errors | `FluentMessageBar` with error intent and sanitized copy. |
| Warning/approval states | `FluentMessageBar` with warning intent plus structured `dl.meta-grid`; message alone is not enough. |
| Status | Existing `.status-badge` classes: neutral, info, warning, success, danger. |
| Structured summary | Existing `dl.meta-grid`; never raw JSON. |
| Repeated rows | `.data-table` or `FluentDataGrid`, using 8px cell padding and wrapping values. |

| Token | Value | Usage |
|-------|-------|-------|

| sm | 8px | Compact row gaps, table cell padding, approval reason spacing, status/action gaps |
| md | 16px | Default page gap, toolbar gap, panel gap, page padding, gate subsection padding |
| lg | 24px | Empty state padding and major policy/approval group separation |
| xl | 32px | Wide desktop split-panel gap only when the page has enough width |
| 2xl | 48px | Major workflow break between server grid and selected gate/result panels when both are visible |

Exceptions: icon-only touch targets and checkboxes must be at least 44px high/wide on mobile; desktop Fluent and native controls may keep the existing 32px minimum height; status badges may keep compact density but new padding must use 4px/8px values.

| Approval required heading | Approval is required before this action can continue |

| Approved heading | Approval is active |

| Denied heading | Policy denied this action |

| Error state | Policy status could not be loaded. Refresh policy status and try again. |
| Redaction failure state | Policy result was blocked because it contained a forbidden field. The result was not displayed. |

## Accessibility And Responsive Contract

| Concern | Contract |
|---------|----------|
| Keyboard | Every policy action, approval row, confirmation control, reason field, expiration field, and refresh command must be reachable by keyboard in DOM order matching the visual flow. |
| Focus | Use visible Fluent/default focus rings; do not remove outlines. After policy evaluation or approval resolution, move focus to the policy panel heading or message bar. |
| Labels | Reason and expiration controls must have visible labels. Placeholder text is not a label. |
| Errors | Gate errors appear in `FluentMessageBar`; field validation appears adjacent to fields; repeated blockers use `.guided-validation-list`. |
| Touch | Icon-only actions and checkboxes in touched surfaces must have at least 44px touch targets on mobile and `Title`/tooltip text for icon-only commands. |
| Text fit | Button labels wrap or become full-width on mobile; no clipped labels inside toolbars, policy actions, approval rows, or grid action cells. |
| Contrast | Status badges must keep readable foreground on light and dark Fluent themes; never encode blocking state by color alone. |
| Screen readers | Message bars must contain actionable text, not only status icons. Result summaries use semantic `dl` pairs and approval tables use headers. |
| Confirmation | Approve/deny dialogs must keep focus trapped while open, return focus to the triggering control after close, and expose confirm/cancel labels to screen readers. |

## Security And Redaction Contract

| Gate | Contract |
|------|----------|
| Repository projection | Owner/approver UI consumes repository facade result types and typed safe policy/approval models only. Generated DTOs with sensitive or raw fields cannot be bound directly to Razor output. |
| Continuation identity | Warning acknowledgement passes only the displayed `acknowledgedDecisionId`. Approved continuation passes only the displayed `approvalRequestId`. UI must not synthesize ids or reuse ids after selected scope changes. |
| Scope verification | The panel displays the scope fields required to explain why a continuation is eligible: action kind, scope key, server/session/dry-run id, billing account, billing assignment, expiration, and decision/request id. |
| Redaction failure | If a result contains a forbidden field, show `Policy result was blocked because it contained a forbidden field. The result was not displayed.` and log only sanitized diagnostic context server-side. |
| Raw JSON | UI may show parsed, allowlisted labels only. Never show raw `InputSnapshotJson`, `RiskDetailsJson`, `AuditDetailsJson`, approval audit JSON, generated `AdditionalData`, or raw request/response text. |
| Cost source | Projected policy costs must be labeled as internal attribution estimates, not payment, invoice, customer billing, or provider invoice truth. |
| Evidence | Any automated/component evidence for Phase 36 must label live Hetzner, Steam, Arma, authenticated browser UAT, provider mutation, provisioning, teardown, and Phase 30 evidence as deferred. |
