## Phase Interaction Contract

### Route And Scope

| Surface | Contract |
|---------|----------|
| `/servers` | Primary owner/operator workflow. Provisioning, runtime lifecycle actions, retry, cleanup status, and provider teardown appear in the selected-server workflow below the server grid and policy/dry-run panels. |
| `/servers/cloud` | Admin provider/fleet console only. It may continue to show inventory and fleet reconciliation, but normal owner copy must not route users there to operate or tear down their selected server. |
| Generated client boundary | Razor consumes `IGameServerRepository` facade methods and hand-written safe models only. Do not bind generated DTOs, request builders, `AdditionalData`, raw JSON, request/response bodies, headers, provider payloads, or exception bodies to UI. |
| Policy continuation boundary | Provisioning, runtime start/restart/update, and provider teardown controls continue only when Phase 36 gate identity is current: decision/request id, action kind, scope key, server/session/dry-run id, billing owner, assignment, and expiration all match. |
| Cost-stop boundary | Only provider teardown/deletion is shown as the cost-stop action. Runtime stop, runtime cleanup, local server deletion, and log collection must never be labeled as stopping provider cost. |
| UAT boundary | Manual authenticated browser UAT, live Hetzner, Steam, Arma, provider mutation, provisioning, teardown, final provider-side billable-resource verification, OPS-02/OPS-03 live UAT, and Phase 30 evidence remain deferred and must not be claimed as passed. |

### Operation Flow

| Step | UI Contract | Blocking Rule |
|------|-------------|---------------|
| 1. Provision reviewed plan | Show `Provision cloud resources` only from a valid, fresh, owner-matched dry-run plan whose policy gate allows the same provisioning scope. | Disabled when the dry-run plan is stale, invalid, mismatched, superseded, owner-mismatched, missing approval, denied, expired, or redaction-blocked. |
| 2. Show provisioning result | Render a `Cloud action result` panel with status, dry-run plan id, session id, game server id, billing owner, assignment, endpoint, resources, and required next step. | Do not present provider raw payloads. If redaction blocks the result, hide details and show the redaction-blocked message only. |
| 3. Monitor runtime | Render a `Cloud runtime` panel with readiness, endpoint, worker, heartbeat, runtime status, current job, progress, recent log timestamp, sanitized failure, allowed actions, cost source, billable resources, cleanup risk, and policy status. | Runtime controls stay disabled while a conflicting lifecycle job is running or while policy state for that action is blocked. |
| 4. Operate lifecycle jobs | Install, update, start, stop, restart, collect logs, and runtime cleanup queue durable lifecycle jobs and refresh the status/result panels. | Runtime start/restart/update obey policy continuation. Stop, collect logs, and runtime cleanup must not be described as provider cost-stop. |
| 5. Retry failed work | Retryable provisioning, runtime, or teardown states show `Retry cloud action` with the failed action name, attempt count when available, next attempt timestamp when available, and sanitized failure summary. | Retry button is shown only when repository result or session status marks the action retryable. Non-retryable failures show `Refresh cloud status` or the exact safe next step. |
| 6. Provider teardown | Show `Teardown provider resources` as a visually distinct destructive cost-stop action for a selected provisioned session. Require confirmation naming the session and remaining billable risk. | Disabled unless the current session can be torn down and policy gate for `ProviderTeardown` is current and allowed. |
| 7. Post-teardown review | After teardown, show deleted resource count, remaining billable resource count, cleanup failure status, cleanup-needed resources, orphan candidates, and next step. | If remaining billable resources are greater than 0, the success state must not read as fully complete; required next step is `Review billable resources`. |

### State Contract

| State | Visual Treatment | Required Content | Action Contract |
|-------|------------------|------------------|-----------------|
| Not ready to provision | Warning `FluentMessageBar` inside `cloud-workflow-result-panel` | Missing prerequisite: valid dry-run plan, billing owner, policy decision, approval, or selected server | Show the exact next non-mutating action such as `Review dry-run plan`, `Refresh policy status`, or `Regenerate dry-run plan`. |
| Provisioning queued/running | Info/warning badge plus `FluentProgress` | Action name, job id if available, session or dry-run id, worker status, current progress, last update timestamp | Disable conflicting provisioning, teardown, and runtime actions for the selected server. |
| Provisioned | Success message bar plus `status-badge status-success` | Session id, endpoint, worker/bootstrap status, resource rows, billing owner, assignment, cost source | Primary next action is `Refresh cloud status`; runtime actions become available according to status and policy. |
| Runtime ready | Success badge in `Cloud runtime` | Endpoint, worker heartbeat, runtime status, current job, allowed actions, billable resources | Show start/stop/restart/update/log/cleanup controls according to server capabilities and policy. |
| Runtime stopped | Neutral/info badge | Runtime status, active billable resource count, note that provider resources can still cost money | Do not show runtime stop as cost-stop. Keep provider teardown action visible when permitted. |
| Retryable failure | Warning badge and error `FluentMessageBar` | Failed action, sanitized failure summary, retryable flag, related job/session/action id, next attempt timestamp if available | Show `Retry cloud action` only when `IsRetryable`, `CanRetry`, `CanRetryCleanup`, or retryable action list allows it. |
| Cleanup-needed | Danger badge for resource state, warning message for panel | Cleanup-needed billable resource count, affected resource ids/display names, session id, required next step | Offer `Teardown provider resources` or `Retry cloud action` when authorized and gate-allowed; otherwise show blocked next step. |
| Orphan-risk | Warning badge | Orphan finding count, candidate resource rows, provider identifier, last reconciliation timestamp if available | Show `Review billable resources`; do not imply local cleanup resolves provider cost. |
| Partial failure | Error message bar plus danger/warning badges | Deleted resource count, remaining billable resources, failed cleanup summary, affected resources, timestamp | If remaining billable resources > 0, the action is not complete. Show `Retry cloud action` when retryable and `Review billable resources`. |
| Remaining billable resources | Danger badge when count > 0; success badge only when count is 0 | Active billable resource count, cleanup-needed billable count, remaining billable count after teardown, cost source | Keep the risk note visible: `Provider teardown stops billable resources; runtime stop and runtime cleanup do not.` |
| Teardown completed | Success badge only when remaining billable resources = 0 | Session id, deleted resource count, remaining billable resources = 0, resource states, timestamp | Next action is `Refresh cloud status`; no copy may claim live provider verification unless separately approved and performed. |
| Redaction blocked | Error `FluentMessageBar` | Redaction-blocked copy only | Hide returned provisioning, runtime, teardown, resource, audit, and cost details. Show `Refresh cloud status`. |

### Allowed Display Fields

| Category | Allowed Fields |
|----------|----------------|
| Identity | Server id/title, dry-run plan id, cloud session id, lifecycle job id, policy decision id, approval request id, audit record id, billing account id, billing assignment id, resource inventory id. |
| Provisioning | Provider identifier, resource display name, kind label, state label, state reason, location/datacenter/network labels, server type label, image label, public endpoint host/port, timestamps. |
| Runtime | Runtime readiness label, endpoint, worker display/status, last heartbeat, current job kind/status/progress, recent log timestamp, retryable flag, allowed action labels. |
| Teardown | Deleted resource count, remaining billable resource count, cleanup failed flag, sanitized failure summary, resource state rows, session updated timestamp. |
| Cost and risk | Cost source label, freshness label, estimated/reconciled/adjusted internal attribution values, active billable resource count, cleanup-needed billable count, orphan finding count, confidence label. |
| Sanitized diagnostics | Sanitized failure summary/details, retryability, validation summary, required next step, action id/correlation id if already allowlisted. |

### Forbidden Display Fields

| Forbidden Field Type | Contract |
|----------------------|----------|
| Provider secrets | Provider tokens, token references that identify secret storage, authorization headers, bearer tokens, provider raw credentials, cloud-init secret material. |
| Steam secrets | Steam username, Steam password, Steam API key, Steam guard/session values, DepotDownloader credentials. |
| Worker secrets | Worker credentials, bootstrap secret values, worker hashes, worker registration secrets, private keys, SSH private material. |
| Raw payloads | Provider request/response bodies, raw policy inputs, raw risk/audit JSON, generated DTO dumps, `AdditionalData`, exception bodies, request headers, response headers, and raw validation payloads. |
| Misleading evidence | UI copy, screenshots, logs, or notes that imply live Hetzner, Steam, Arma, authenticated browser, provider mutation, provisioning, teardown, or Phase 30 UAT passed. |

### Copy Boundary Rules

- Use "provider teardown" or "teardown provider resources" for the cost-stop action.
- Use "runtime stop" only for stopping the game process/service on an existing cloud worker.
- Use "runtime cleanup" only for cleaning local runtime artifacts on the worker; include the cost warning when it appears near billable resources.
- Use "internal attribution estimate" or "runtime cost estimate"; do not use "payment", "invoice", "checkout", "charge", "customer billing", or "tax".
- Use "remaining billable resources" whenever teardown leaves provider resources active or cleanup-needed.
- Do not use vague labels such as `Next`, `Submit`, `OK`, `Launch`, `Deploy`, or `Done` for Phase 37 actions.

## Layout Contract

| Area | Contract |
|------|----------|
| Page shell | Reuse `.servers-page`: flex column, 16px padding, 16px page gap. Do not add hero, decorative, landing, or marketing treatments. |
| Header | Reuse `.servers-toolbar`; keep page title as `Game servers`. Do not place cost-stop warnings in the title row. |
| Main workspace | Keep `FluentDataGrid` first. Phase 37 operation panels appear below selected-server setup, dry-run review, and policy gate panels. |
| Cloud action result | Reuse `section.detail-section.cloud-workflow-result-panel`; header left is `Cloud action result`, right is state badge. |
| Runtime panel | Use one `section.detail-section` titled `Cloud runtime` with `dl.meta-grid` for session, worker, job, status, cost, policy, and cleanup-risk data. |
| Runtime actions | Use `.runtime-actions` for refresh, install, update, start, stop, restart, collect logs, and runtime cleanup. On mobile, actions stack full width. |
| Teardown panel/action | Add a visibly separate subsection or action group titled `Provider teardown`. It must sit after runtime controls and before stuck-job tables, with a danger/warning message when resources may still be billable. |
| Teardown confirmation | Use Fluent dialog through the existing provider. Title: `Teardown provider resources`. Body must include session id and the cost-stop distinction. Primary button: `Teardown provider resources`. |
| Resource rows | Use `.data-table` or `FluentDataGrid` for resource inventory rows. Compact columns: resource, kind, state, billable/risk, endpoint/location, updated, action/next step. |
| Failure details | Use `FluentMessageBar` plus `dl.meta-grid` and optional `.guided-validation-list`. Do not add raw log panes or JSON viewers. |
| Mobile | At max-width 860px, operation summaries, metadata grids, resource tables, runtime actions, and teardown actions collapse to one column; long ids wrap with `overflow-wrap: anywhere`; icon-only controls are at least 44px. |

## Accessibility And Responsive Contract

| Concern | Contract |
|---------|----------|
| Keyboard | Every provisioning, runtime, retry, refresh, teardown, confirmation, resource row, and policy continuation control must be reachable by keyboard in DOM order matching the visual flow. |
| Focus | Use visible Fluent/default focus rings. After provisioning, retry, runtime action, or teardown completes, move focus to the `Cloud action result` heading or message bar. |
| Labels | Buttons must have visible text when space allows; icon-only grid actions require `Title` or tooltip text. Confirmation dialogs must expose clear confirm and cancel labels. |
| Errors | Operation errors appear in `FluentMessageBar`; validation and blockers appear adjacent to the affected panel; repeated blockers use `.guided-validation-list`. |
| Touch | Icon-only actions and checkboxes in touched surfaces must have at least 44px touch targets on mobile. |
| Text fit | Button labels wrap or become full-width on mobile; no clipped labels inside toolbars, runtime actions, teardown actions, table cells, or grid action cells. |
| Contrast | Status badges must keep readable foreground on light and dark Fluent themes; never encode billable risk by color alone. |
| Screen readers | Message bars must contain actionable text, not only status icons. Runtime, teardown, cost, and resource summaries use semantic `dl` pairs and tables use headers. |
| Confirmation | Provider teardown dialog must trap focus while open, return focus to the triggering control after close, and require an explicit destructive primary action. |

## Security And Redaction Contract

| Gate | Contract |
|------|----------|
| Repository projection | Owner/operator UI consumes repository facade result types and typed safe operation models only. Generated DTOs with sensitive or raw fields cannot be bound directly to Razor output. |
| Continuation identity | Provisioning, lifecycle, and teardown continuation passes only the displayed `acknowledgedDecisionId` or `approvalRequestId`; UI must not synthesize ids or reuse ids after selected scope changes. |
| Scope verification | Operation panels display the scope fields required to explain eligibility: action kind, scope key, server/session/dry-run id, billing account, billing assignment, expiration, decision/request id. |
| Redaction failure | If a result contains a forbidden field, show `Cloud result was blocked because it contained a forbidden field. The result was not displayed.` and do not display returned operation, resource, cost, audit, or failure details. |
| Raw JSON | UI may show parsed, allowlisted labels only. Never show raw provider payloads, raw policy inputs, audit JSON, generated `AdditionalData`, request/response text, headers, or exception bodies. |
| Cost source | Runtime and teardown costs must be labeled as internal attribution estimates/reconciled/adjusted labels, not payment, invoice, customer billing, or provider invoice truth. |
| Evidence | Any automated/component evidence for Phase 37 must label live Hetzner, Steam, Arma, authenticated browser UAT, provider mutation, provisioning, teardown, final provider-side billable-resource verification, OPS-02/OPS-03 live UAT, and Phase 30 evidence as deferred. |
