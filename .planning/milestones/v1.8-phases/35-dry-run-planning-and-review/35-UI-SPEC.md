## Phase Interaction Contract

### Route And Scope

| Surface | Contract |
|---------|----------|
| `/servers` | Primary owner/operator surface. Add dry-run generation and plan review for the selected guided Arma 3 server inside the existing cloud setup/detail workflow. |
| `/servers/cloud` | Admin provider/fleet console only. It can keep aggregate plan tables, but normal owner review and regeneration stay in `/servers`. |
| Generated client boundary | Razor code must call `IGameServerRepository.CreateArma3CloudDryRunPlanResultAsync` or a repository facade equivalent. Do not inject generated request builders into components and do not add raw browser HTTP bridges. |
| Provider mutation | Phase 35 must not create, provision, update, or delete provider resources. Any future provisioning command is hidden or disabled with a reason until later phases. |
| Review payloads | Render typed plan data and repository projections only. Do not show raw `ValidationDetailsJson`, `PlannedOperationsJson`, `AssumptionsJson`, `DetailsJson`, `AdditionalData`, exception bodies, headers, or request/response dumps. |
| UAT boundary | Manual authenticated browser UAT, live Hetzner resource creation, Steam validation, Arma runtime validation, provider billable-resource verification, and Phase 30 live evidence remain deferred and must not be claimed as passed. |

### Dry-Run Flow Shape

Use one dense operational flow under the existing server grid.

| Step | UI Contract | Blocking Rule |
|------|-------------|---------------|
| 1. Ready inputs | Reuse the Phase 33 readiness summary for selected server, billing owner, billing assignment, runtime basics, size, location, storage, ports, SSH exposure, CIDR, modpack, and readiness blockers. | `Generate dry-run plan` disabled until readiness is true and selected owner/assignment match the active server owner. |
| 2. Generate plan | User clicks `Generate dry-run plan`. Show loading in the selected plan review panel, not a full-page overlay. | Disable only dry-run generation/regeneration and conflicting selected-server actions while the request runs. |
| 3. Review plan | Show one selected plan review panel with plan id, session id, status, owner ids, provider, resource summary, assumptions, firewall rules, validation failures, metadata timestamp/freshness, hourly estimate, monthly estimate, currency, and cost source. | Provider mutation remains unavailable. A valid plan can show future next step copy, but no enabled provider mutation command is introduced in Phase 35. |
| 4. Resolve blockers | Invalid, stale, mismatched, superseded, owner-mismatched, or metadata-stale plans render as actionable states with exact next step copy. | Future provisioning remains blocked and the primary available command is `Regenerate dry-run plan` or the specific correction action. |
| 5. Regenerate | User can regenerate when inputs, owner assignment, metadata freshness, validation state, or supersession makes the current plan unusable. | The old reviewed plan remains visible enough to explain why it is unusable, but the selected actionable plan becomes the newest repository result after regeneration. |

### Plan State Contract

| State | Visual Treatment | Required Content | Action Contract |
|-------|------------------|------------------|-----------------|
| No plan | `FluentMessageBar` warning inside `section.detail-section` | Missing prerequisite and next non-mutating step | Show `Generate dry-run plan` only if readiness is true; otherwise keep readiness correction CTAs. |
| Loading | `FluentStack` plus `FluentProgress` in the plan review panel | Selected server, selected owner, action noun | Disable generate/regenerate and conflicting selected-server cloud actions. |
| Valid fresh plan | Success message bar, `status-badge status-success`, and structured review sections | Plan id, session id, valid status, owner ids, provider, fresh metadata label, source timestamp, hourly/monthly estimates, source label | Show `Review policy decision` only as a future/blocked next step if policy flow is not implemented in this phase; do not enable provider mutation. |
| Valid stale metadata | Warning message bar, `status-badge status-warning` on freshness | Same as valid plan plus stale/unknown freshness and metadata timestamp | Primary action is `Regenerate dry-run plan`; future provisioning remains disabled. |
| Invalid plan | Warning message bar plus `.guided-validation-list` | Validation summary, field/subsystem targets, severity, sanitized messages, plan id if persisted | Primary action is `Regenerate dry-run plan`; field correction links scroll/focus existing inputs when practical. |
| Superseded plan | Warning badge and non-current label | Superseded plan id, newest known plan id when available, timestamp | Primary action is `Review latest plan` or `Regenerate dry-run plan`; future provisioning disabled. |
| Input mismatch | Warning message bar | Which selected inputs no longer match the reviewed plan: server, owner, assignment, size, location, storage, ports, SSH/CIDR, modpack, or runtime basics | Primary action is `Regenerate dry-run plan`; highlight changed inputs with warning state. |
| Owner mismatch | Error message bar and `status-badge status-danger` | Reviewed plan owner ids, current active owner ids, sanitized reason | Future provisioning disabled. Primary action is `Save owner` or `Regenerate dry-run plan` after owner correction. |
| Failure | Error message bar | Sanitized failure summary, retryability, action name, correlation/action id if allowlisted | Show `Retry dry-run plan` only when repository result marks retryable; otherwise show `Refresh cloud status`. |
| Redaction blocked | Error message bar | Redaction-blocked copy only | Do not display any returned plan details. Show `Refresh cloud status`; log only sanitized context server-side. |

### Plan Review Sections

Render review content as structured UI, not raw JSON.

| Section | Contract |
|---------|----------|
| Plan summary | Use `dl.meta-grid` for dry-run plan id, session id, game server id/title, billing account id, billing assignment id, requested by if allowlisted, provider, status, created/updated, and required next step. |
| Planned resources | Use `.data-table` or `FluentDataGrid` for resource kind, display name, state, location/datacenter, server type/image when relevant, state reason, and metadata timestamp. Hide provider resource id for dry-run-only resources when it is empty. |
| Firewall rules | Use compact table columns: protocol, port/range, source CIDR, description. Treat administrative CIDR as visible planning input, not a secret. |
| Assumptions | Use a compact list or `dl.meta-grid` from typed assumptions: code, label, value, description, user-selected badge. Do not render `AssumptionsJson`. |
| Validation failures | Use `.guided-validation-list`; each item shows target or code, severity badge, and message. Also summarize blockers in `FluentMessageBar`. |
| Cost estimate | Use `dl.meta-grid` for hourly estimate, monthly estimate, currency, cost source label (`Dry-run estimate`), metadata freshness (`Fresh`, `Stale`, or `Unknown`), confidence score if present, and source timestamp. |
| Cost breakdown | If shown, use a dense breakdown for server hourly/monthly, storage monthly, IP monthly, firewall monthly, additional hourly, and additional monthly. Each amount must keep source/freshness nearby. |
| Next step | Use message copy, not a hidden rule. Valid plan: `Review the dry-run plan before policy review.` Blocked plan: `Regenerate the dry-run plan after correcting the highlighted state.` |

### Allowed Display Fields

| Category | Allowed Fields |
|----------|----------------|
| Identity | Server id/title, session id, dry-run plan id, resource inventory id, cost estimate id, billing account id, billing assignment id, audit/action id when already allowlisted. |
| Provider labels | Provider identifier, resource kind, display name, location, datacenter, network zone, server type, image name, planned endpoint ports. |
| Plan state | Dry-run plan status, resource state, validation summary, validation failure code/target/severity/message, required next step, retryable flag. |
| Firewall | Protocol, port, port range, source CIDR, client-safe description. |
| Assumptions | Assumption code, label, value, client-safe description, user-selected flag. |
| Cost | Currency, hourly estimate, monthly estimate, cost source label, freshness label, confidence score, metadata source timestamp, estimate created/updated timestamps. |
| Timing | Plan created, plan updated, metadata source timestamp, result timestamp. |
| Sanitized diagnostics | Sanitized failure summary/details, validation summary, high-level reason labels. |

### Forbidden Display Fields

| Forbidden Field Type | Contract |
|----------------------|----------|
| Provider secrets | Provider tokens, token values, token references that identify secret storage, authorization headers, bearer tokens, provider raw credentials. |
| Steam secrets | Steam username, Steam password, Steam API key, Steam guard/session values, DepotDownloader credentials. |
| Worker secrets | Worker credentials, bootstrap credential secrets, worker hashes, worker registration secrets, private keys, SSH private material. |
| Raw payloads | Raw request/response bodies, generated DTO dumps, raw `AdditionalData`, raw exception bodies, raw audit payload JSON, raw input snapshot JSON, raw risk details JSON, raw validation details JSON, raw planned operations JSON, raw resource details JSON. |
| Misleading evidence | UI copy, screenshots, logs, or notes that imply live Hetzner, Steam, Arma, authenticated browser, provider mutation, or Phase 30 UAT passed. |

### Copy Boundary Rules

- Use "dry-run plan", "planned resources", "cost estimate", "cost source", "metadata freshness", "billing owner", "cost responsibility", "assignment", and "internal attribution".
- Do not use "launch", "deploy", "provision now", "payment", "invoice", "checkout", "charge", "customer billing", or "tax workflow" in Phase 35 UI.
- Do not describe runtime stop or runtime cleanup as cost stop. Provider teardown remains a later cost-stop action.
- Do not route owner workflow users to `/servers/cloud` as the normal plan review path.

## Layout Contract

| Area | Contract |
|------|----------|
| Page shell | Reuse `.servers-page`: flex column, 16px padding, 16px page gap. |
| Header | Reuse `.servers-toolbar`; do not put plan status badges in the page title row. |
| Main workspace | Keep `FluentDataGrid` first. Guided setup and selected plan review appear below the grid or in selected-server details. |
| Guided panel | Keep Phase 33's `section.detail-section guided-cloud-panel`; add the dry-run generation action after readiness summary, not as a separate wizard page. |
| Plan review panel | Use one `section.detail-section cloud-workflow-result-panel` or a sibling `dry-run-plan-review-panel` with the selected plan as the focal surface. Do not nest cards inside it. |
| Review header | Left: `Dry-run plan review` title and one-line scope copy. Right: status badge for plan state or freshness. Stack on mobile. |
| Review sections | Use section titles, `dl.meta-grid`, `.data-table`, and `.guided-validation-list`. Keep each section compact and scannable; no decorative cards. |
| Actions | Use `div.guided-actions` for `Generate dry-run plan`, `Regenerate dry-run plan`, `Refresh cloud status`, and any future disabled next-step command. On mobile, buttons are full width. |
| Tables | Use `.data-table` for firewall and planned resources when row count is small; use `FluentDataGrid` only if sorting/paging is required. |
| Mobile | At max-width 860px, plan review sections, tables, metadata grids, and actions collapse to one column; table values wrap with `overflow-wrap: anywhere`. |

## Component Contract

| Need | Component |
|------|-----------|
| Primary dry-run command | `FluentButton` with `Appearance.Accent`, `PlayCircle` icon, label `Generate dry-run plan`. |
| Regeneration | `FluentButton` with `ArrowSyncCircle` icon, label `Regenerate dry-run plan`. Use accent only when the current plan is unusable and regeneration is the primary next safe action. |
| Refresh | `FluentButton` with `ArrowSyncCircle` icon, label `Refresh cloud status`. |
| Disabled future mutation | If shown, default or disabled `FluentButton` with explicit helper text. Do not make it accent in Phase 35. |
| Page/result errors | `FluentMessageBar` with error intent and sanitized copy. |
| Validation warning | `FluentMessageBar` with warning intent plus `.guided-validation-list`. |
| Success | `FluentMessageBar` success intent plus structured review; success message alone is not enough. |
| Loading | `FluentStack` plus `FluentProgress` with action-specific loading copy. |
| Status | Existing `.status-badge` classes: neutral, info, warning, success, danger. |
| Structured summary | Existing `dl.meta-grid`; never raw JSON. |
| Repeated review rows | `.data-table` or `FluentDataGrid`, using 8px cell padding and wrapping values. |

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline label/control spacing, status badge icon gap |
| sm | 8px | Compact row gaps, table cell padding, validation list spacing, assumption item gaps |
| md | 16px | Default page gap, toolbar gap, plan panel gap, page padding, review subsection padding |
| lg | 24px | Empty state padding and major review group separation |
| xl | 32px | Wide desktop split-panel gap only when the page has enough width |
| 2xl | 48px | Major workflow break between server grid and selected plan/result panels when both are visible |
| 3xl | 64px | Reserved for page-level separation; do not use inside plan review panels |

Exceptions: icon-only touch targets and checkboxes must be at least 44px high/wide on mobile; desktop Fluent and native controls may keep the existing 32px minimum height; status badges may keep compact density but new padding must use 4px/8px values.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Generate dry-run plan |
| Regenerate CTA | Regenerate dry-run plan |
| Refresh CTA | Refresh cloud status |
| Disabled future action | Provider provisioning is not available in this phase. Review and regenerate the dry-run plan first. |
| Success heading | Dry-run plan ready |
| Success body | Review planned resources, firewall rules, assumptions, validation, and cost estimates before any provider action. |
| Empty state heading | No dry-run plan |
| Empty state body | Complete cloud setup for an eligible Arma 3 server and generate a non-mutating dry-run plan. |
| Invalid state | Dry-run planning found blockers. Correct the highlighted state and regenerate the dry-run plan. |
| Stale state | This dry-run plan uses stale or unknown metadata. Regenerate the dry-run plan before continuing. |
| Superseded state | This dry-run plan was replaced by a newer plan. Review the latest plan or regenerate. |
| Owner mismatch state | This dry-run plan no longer matches the active billing owner. Save the correct owner and regenerate the dry-run plan. |
| Error state | Dry-run plan could not be loaded. Refresh cloud status and try again. |
| Redaction failure state | Dry-run plan was blocked because it contained a forbidden field. The result was not displayed. |
| Deferred UAT note | Live Hetzner, Steam, Arma, authenticated browser UAT, provider mutation, provisioning, teardown, and Phase 30 evidence are deferred. |
| Destructive confirmation | None for Phase 35. Do not add provider teardown, local server delete, or provisioning confirmation in this phase. |

Button labels must be verb plus noun. Allowed Phase 35 labels include `Generate dry-run plan`, `Regenerate dry-run plan`, `Refresh cloud status`, `Review latest plan`, `Save owner`, `Cancel setup`, and `Review policy decision` as a disabled or future next step only. Do not use vague labels such as `Next`, `Submit`, `Go`, `OK`, `Launch`, or `Deploy`.

## Accessibility And Responsive Contract

| Concern | Contract |
|---------|----------|
| Keyboard | Every plan action, field correction target, table action, and refresh/regenerate command must be reachable by keyboard in DOM order matching the visual flow. |
| Focus | Use visible Fluent/default focus rings; do not remove outlines. After generation, move focus to the plan review heading or message bar. |
| Labels | Every input/select/toggle must have a visible label. Placeholder text is not a label. |
| Errors | Field errors appear adjacent to fields; plan validation appears in `FluentMessageBar` and `.guided-validation-list`; blocked future provisioning explains the blocking reason in text. |
| Touch | Icon-only actions and checkboxes in touched surfaces must have at least 44px touch targets on mobile and `Title`/tooltip text for icon-only commands. |
| Text fit | Button labels wrap or full-width on mobile; no clipped labels inside toolbars, plan actions, or grid action cells. |
| Contrast | Status badges must keep readable foreground on light and dark Fluent themes; never encode blocking state by color alone. |
| Screen readers | Message bars must contain actionable text, not only status icons. Result summaries use semantic `dl` pairs and tables use headers. |

## Security And Redaction Contract

| Gate | Contract |
|------|----------|
| Repository projection | Owner-facing dry-run review consumes repository facade result types and typed safe DTO fields only. Generated DTOs with sensitive or raw fields cannot be bound directly to Razor output. |
| Structured details | Render typed `ValidationFailures`, `FirewallRules`, and `Assumptions` collections. Never render raw plan, resource, assumption, validation, or operation JSON in `/servers`. |
| Redaction failure | If a result contains a forbidden field, show `Dry-run plan was blocked because it contained a forbidden field. The result was not displayed.` and log only sanitized diagnostic context server-side. |
| Cost source | Every cost estimate must display source label and freshness label near the amount. Dry-run estimates must not be presented as reconciled provider billing. |
| Evidence | Any automated/component evidence for Phase 35 must label live Hetzner, Steam, Arma, authenticated browser UAT, provider mutation, provisioning, teardown, and Phase 30 evidence as deferred. |
| Secrets in names | Do not render token reference values, worker hash-like identifiers, bearer strings, private key fragments, credential fingerprints, or source hashes as user-visible labels. |
