## Phase Details

### Phase 5: Hetzner Provider Configuration And Metadata Cache

**Goal:** Administrators can configure secret-backed Hetzner access and synchronize provider metadata needed for later dry-run planning.
**Mode:** mvp
**Depends on:** v1.0 Local Worker Foundation
**Requirements:** HETZ-01, HETZ-02, HETZ-03, META-01, META-02, META-03, META-04, META-05, RELY-06

**Success Criteria** (what must be TRUE):

1. Administrator can store and inspect Hetzner provider configuration status without exposing token material.
2. Administrator can verify credentials through read-only provider calls and receive sanitized success/failure status.
3. API code uses a provider boundary for Hetzner read-only metadata and future operation separation.
4. Metadata sync persists server types, locations/datacenters, images, firewall capabilities, pricing-relevant fields, deprecation, and freshness status.
5. Provider token material and raw authentication failures are redacted across DTO, logging, audit, and error paths touched by this phase.

**Plans:** 3/3 plans executed
Plans:
**Wave 1**

- [x] 05-01: Add secret-safe provider configuration, verification status, and redaction contract.

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 05-02: Add read-only Hetzner provider interface/client and metadata persistence model.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 05-03: Implement metadata sync, freshness tracking, and metadata parsing tests.

### Phase 6: Cloud Resource Inventory And Dry-Run Records

**Goal:** Planned cloud sessions and resources can be stored durably as inventory without issuing any real Hetzner mutating API calls.
**Mode:** mvp
**Depends on:** Phase 5
**Requirements:** HETZ-04, INVT-01, INVT-02, INVT-03, INVT-04, PLAN-05

**Success Criteria** (what must be TRUE):

1. Administrator can persist a planned cloud game-server session before any real provider resource exists.
2. Planned VMs, IPs, firewalls, volumes, and cloud game-server sessions are represented as inventory records with nullable future provider ids.
3. Inventory links planned resources to provider, region/location, game server, and billing owner context.
4. Dry-run plan persistence records validation results and planned operations without creating, updating, or deleting provider resources.
5. Planned resource states clearly distinguish dry-run, invalid, ready-for-future-provisioning, future-provisioned, cleanup-needed, and orphan-candidate concepts.

**Plans:** 3/3 plans executed
Plans:
**Wave 1**

- [x] 06-01: Add cloud session and planned resource inventory entities, DTOs, and migrations.

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 06-02: Add dry-run plan persistence and explicit no-mutating-provider-operation guard.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 06-03: Add inventory state transitions, ownership links, and persistence tests.

### Phase 7: Arma 3 Dry-Run Planner And Cost Estimates

**Goal:** Authorized users can generate one-worker Arma 3 dry-run plans with billing-owned hourly/monthly estimates and clear validation failures.
**Mode:** mvp
**Depends on:** Phase 6
**Requirements:** PLAN-01, PLAN-02, PLAN-03, PLAN-04, COST-01, COST-02, COST-03, COST-04

**Success Criteria** (what must be TRUE):

1. User cannot request or persist a dry-run estimate without selecting exactly one active billing owner.
2. User can see selected or recommended Hetzner server type, location, image, one-Arma-3-server-per-CCX-worker assumption, and planned firewall/storage assumptions.
3. API validates missing credentials, stale metadata, unavailable server type, unsupported image, invalid ports, missing owner, and unsupported worker shape.
4. Hourly and monthly estimates are calculated from cached metadata and configured assumptions, with currency, VAT note, metadata source timestamp, and freshness stored.
5. Administrator can audit historical estimates even after metadata changes.

**Plans:** 3/3 plans executed
Plans:
**Wave 1**

- [x] 07-01: Implement Arma 3 dry-run planner and validation rules.

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 07-02: Add cost estimate records linked to billing accounts/assignments and metadata snapshots.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 07-03: Expose estimate/dry-run APIs and tests for owner enforcement, assumptions, and validation failures.

### Phase 8: Admin Visibility And Compatibility Hardening

**Goal:** Administrators can inspect provider status, metadata freshness, dry-run plans, planned inventory, and estimate assumptions while existing local worker operations remain stable.
**Mode:** mvp
**Depends on:** Phase 7
**Requirements:** VIS-04, VIS-05, VIS-06, RELY-05, RELY-07

**Success Criteria** (what must be TRUE):

1. Administrator can see provider configuration status, last verification time, and sanitized failure state.
2. Administrator can see metadata freshness and sync failures for server types, locations, images, and firewall capabilities.
3. Administrator can inspect dry-run plans with billing owner, planned resources, estimate assumptions, validation failures, and metadata freshness.
4. Existing local worker lifecycle operations still build and pass focused regression checks.
5. Tests cover provider metadata persistence, dry-run no-side-effect behavior, billing owner enforcement, and provider secret redaction.

**Plans:** 3/3 plans executed
**UI hint:** yes
Plans:
**Wave 1**

- [x] 08-01: Add admin API/DTO projections for provider status, metadata freshness, plans, estimates, and inventory.

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 08-02: Add WebApp admin surfaces for provider configuration, metadata freshness, dry-run validation, and planned inventory.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 08-03: Run compatibility hardening, focused regression tests, and secret/no-side-effect verification.
