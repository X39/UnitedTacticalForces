## Overview

v1.12 is a change request for the server area. The current UI exposes too many implementation details, splits normal user tasks across server and cloud surfaces, relies on Arma-3-specific cloud and runtime concepts, and gives weak feedback for lifecycle jobs, log collection, worker state, provider state, and cleanup. Users should not have to understand "cloud plans" or inspect raw lifecycle job lists to create a server and get it running.

The milestone first makes the backend and WebApp contracts truly generic for currently supported game controllers, then rebuilds the frontend around a coherent task path:

1. Choose a supported game and hosting mode.
2. Assign an accountable billing owner.
3. Select runtime/template/options relevant to the selected game.
4. Review readiness, cost, policy, and provider implications.
5. Create/provision/run the server.
6. Track progress, logs, failures, retries, cleanup, and teardown from one server workspace.

Live Hetzner/Steam/Arma UAT remains parked. v1.12 should be verified with mock/fake backend states and automated/browser checks, not live provider mutation.

## Phase Details

### Phase 55: Generic Game Hosting Capability Contracts

**Goal:** API and WebApp can describe supported game-hosting capabilities without hard-coded Arma 3 cloud entry contracts.
**Depends on:** Existing game-controller abstraction, game-server creation service, guided cloud entry endpoints, and WebApp repository facade.
**Requirements:** GEN-01, GEN-02
**Implementation boundaries:** Do not remove existing Arma 3 behavior. Do not add new game products. Do not expose provider, Steam, worker, bearer, cookie, or secret-bearing values.
**Success Criteria** (what must be TRUE):

1. Supported controllers project game display metadata, hosting modes, lifecycle actions, local/cloud support, and required configuration through generic DTOs.
2. Game server creation and guided cloud entry contracts no longer require Arma-3-named API/repository methods for the generic path.
3. Existing Arma 3 creation, local lifecycle, and cloud eligibility still work through compatibility tests.
4. WebApp repository boundaries expose generic creation/planning methods and keep generated DTOs out of Razor-facing models.
5. Tests fail if new generic server UI code calls Arma-3-only cloud entry methods directly.

**Plans:** 3/3 plans executed

### Phase 57: Guided Server Creation Journey

**Goal:** Users can create a supported-game server through one coherent guided path that leads to the next runnable action.
**Depends on:** Phase 56.
**Requirements:** CREATE-01, CREATE-02, CREATE-03, CREATE-04
**Implementation boundaries:** Do not create live provider resources without the existing dry-run, policy, approval, and provisioning gates. Do not rely on admin-only cloud pages for normal server creation.
**Success Criteria** (what must be TRUE):

1. The creation UI starts with game and hosting mode, then shows only relevant owner, local/cloud, runtime, template, and provider choices.
2. The UI explains server record, local managed install, cloud review, provisioning, and running state as user tasks rather than implementation nouns.
3. Cloud-capable creation leads directly to review/provision/run next steps without requiring users to discover separate cloud plan pages.
4. Validation messages are specific, actionable, and tied to the selected game/hosting mode.
5. Repository-backed component tests cover empty options, unsupported hosting mode, missing owner, missing metadata, stale plan, policy gate, and successful creation paths.

### Phase 58: Unified Server Workspace

**Depends on:** Phase 57.
**Requirements:** WORK-01, WORK-02, WORK-03, WORK-04
**Implementation boundaries:** Keep admin fleet/provider diagnostics available for administrators. Keep server-owner projections authorization-scoped and redacted.
**Success Criteria** (what must be TRUE):

1. The workspace summary shows game, hosting mode, owner, runtime status, latest job, worker/provider state, cost/policy status, and cleanup risk with explicit labels.
2. Relevant lifecycle, cloud, log, owner, configuration, file, cleanup, and teardown actions are discoverable from the server workspace.
3. Runtime cleanup and provider teardown are visually and textually distinct, and only provider teardown is described as cost stop.

### Phase 59: Lifecycle, Log, And Status Feedback Repair

**Goal:** Background operations produce clear progress, completion, failure, and next-step feedback instead of stuck jobs or unexplained `n/a` labels.
**Depends on:** Phase 58.
**Requirements:** OPS-01, OPS-02, OPS-03, OPS-04
**Implementation boundaries:** Do not fabricate job completion. Unknown/deferred/unsupported states must be labeled honestly. Preserve durable job truth in PostgreSQL.
**Success Criteria** (what must be TRUE):

1. Lifecycle job lists and summaries show queued, running, retrying, succeeded, failed, cancelled, stale, and recovered states with timestamps and actor/worker context.
2. Log collection actions show the created job, progress/status, completion/failure result, and refreshed logs.
3. Runtime, worker, and provider status labels distinguish unknown, unavailable, unsupported, deferred, waiting, stale, and failed states instead of falling back to `n/a`.
4. Failed or blocked operations provide next actions such as retry, refresh, request approval, cleanup runtime, teardown provider resources, or inspect diagnostics.
5. Tests cover stuck/recovered jobs, background log collection, status label mapping, and action availability.
