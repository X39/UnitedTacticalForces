### Phase 9: Hetzner Provisioning Execution

**Goal:** Convert validated, owner-linked dry-run plans into real Hetzner provider resources while preserving provider identifiers and rejecting unsafe plans before any mutating call.

**Requirements:** HETZ-05, PROV-01, PROV-02, PROV-03, PROV-04

**Success Criteria:**

1. Administrator can trigger real provisioning only from a valid, fresh, owner-linked dry-run plan.
2. Mutating provider methods are explicit and separate from existing read-only metadata and dry-run paths.
3. Created server, firewall, IP, and optional volume records store provider IDs, requested shape, operation results, and inventory transitions.
4. Invalid, stale, ownerless, unsupported, or already-consumed dry-run plans fail before provider mutation.
5. Public endpoint details are visible after required network resources are created.

### Phase 10: Ownership, Audit, And Teardown Safety

**Goal:** Make every provisioned or partially provisioned billable resource owner-attributed until explicit provider deletion succeeds, with auditable cleanup and failure states.

**Requirements:** BILL-05, BILL-06, AUDT-04, CLN-01, CLN-02

**Success Criteria:**

1. Provisioned and partially provisioned resources always have exactly one active billing owner snapshot.
2. Partial provisioning failures preserve ownership and mark cleanup-needed for any created billable resource.
3. Provisioning, failure, cleanup, orphan marking, and teardown actions write sanitized immutable audit records.
4. Administrator can delete a cloud session through a teardown operation that deletes associated billable provider resources.
5. Teardown records deletion as the cost-stop boundary and reports cleanup failure when billable resources remain.

### Phase 11: Cloud Worker Bootstrap Credentials

**Goal:** Prepare provisioned VMs to connect back as cloud workers using short-lived, scoped credentials and secret-safe bootstrap configuration.

**Requirements:** HETZ-06, WORK-05, WORK-06, WORK-07

**Success Criteria:**

1. API can create a cloud worker identity tied to one provisioned cloud session.
2. API can issue short-lived bootstrap credentials scoped to that worker identity or cloud session.
3. VM bootstrap receives only the API endpoint, worker identity, bootstrap credential, and non-secret runtime configuration required for registration.
4. Provider tokens, Steam credentials, and worker credential material are redacted from DTOs, logs, audit records, lifecycle job errors, and provider status output.

### Phase 12: Cloud Worker Registration And Visibility

**Goal:** Let bootstrapped cloud workers register, heartbeat, report capabilities, survive API restarts, and expose safe provisioning/bootstrap controls in admin and owner views.

**Requirements:** WORK-08, WORK-09, WORK-10, RELY-08, VIS-07, VIS-08, VIS-09, RELY-09

**Success Criteria:**

1. Cloud worker authenticates to the API, registers itself, and links to its cloud session and inventory records.
2. Cloud worker heartbeat and capability reports include game type support, operating system, architecture, region, and one-session worker shape.
3. Persisted worker projections distinguish local and cloud workers without regressing existing local worker execution.
4. API restart preserves provisioned resource state, worker identity, heartbeat state, cleanup-needed state, and bootstrap status.
5. Admin and server-owner views expose provisioning, bootstrap, teardown, cleanup-needed, orphan-candidate, and retryable states without exposing secrets.
