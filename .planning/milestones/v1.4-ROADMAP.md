### Phase 17: Runtime Cost Snapshot Foundation

**Goal:** Add durable cost snapshot records and calculation services that estimate current and historical Hetzner resource cost from provider-resource lifetime, cached pricing, and billing owner intervals.

**Requirements:** COST-09, COST-10, COST-11, COST-12, RELY-14

**Plans:** 3/3 plans complete
Plans:
**Wave 1**

- [x] 17-01-PLAN.md - Runtime cost snapshot schema and migration

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 17-02-PLAN.md - Core interval cost calculation and historical owner summaries

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 17-03-PLAN.md - Metadata, secret-safe audit, idempotency, and final validation

**Success Criteria:**

1. Cloud cost snapshot entities, enums, EF configuration, and migrations store provider, session, resource, owner, interval, source, currency, rate, assumption, metadata freshness, confidence, and timestamp fields.
2. Cost calculation treats cloud server, IP, and volume resources as billable while they exist and uses provider deletion timestamps as the cost-stop boundary.
3. Runtime stop, worker cleanup, powered-off VM state, and Arma process state do not stop provider cost attribution.
4. Historical accumulated cost can be calculated for a cloud session across billing assignment intervals without moving old cost to the current owner.
5. Cost snapshot creation and refresh are idempotent and restart-safe, with secret-safe audit records and assumption visibility.

### Phase 18: Provider Reconciliation Runs And Findings

**Goal:** Add read-only Hetzner reconciliation that compares live provider resources against persisted inventory and records durable findings without deleting provider resources automatically.

**Requirements:** HETZ-08, HETZ-09, HETZ-10, HETZ-11

**Success Criteria:**

1. Hetzner provider client exposes paged, secret-safe read/list methods for servers, floating IPs, volumes, and firewalls.
2. Reconciliation run records persist status, actor, start/end timestamps, live provider counts, known inventory counts, finding counts, orphan counts, and sanitized failure details.
3. Reconciliation findings identify provider resources missing from inventory, inventory resources missing from provider, state mismatches, and cleanup-needed billable resources.
4. Findings preserve attributable billing account/session/resource references when a match is known and use safe orphan records when no UTF owner can be proven.
5. Reconciliation does not call provider delete/detach APIs or mutate provider resources.

**Plans:** 3/3 plans complete

**Wave 1**

- [x] 18-01-PLAN.md - Hetzner live resource read boundary.

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 18-02-PLAN.md - Durable reconciliation run and finding schema.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 18-03-PLAN.md - Reconciliation service, admin trigger, audit, and tests.

### Phase 19: Cost And Reconciliation Visibility

**Goal:** Surface current cost, accumulated cost, cost source labels, reconciliation status, and cleanup risk to administrators and authorized server owners through generated API clients and existing WebApp surfaces.

**Requirements:** COST-05, COST-08, VIS-12, VIS-13, VIS-14, VIS-15

**Success Criteria:**

1. API DTOs and endpoints expose server/session cost summaries, latest snapshots, accumulated cost, source label, confidence, metadata freshness, and billable resource contribution.
2. Administrator cloud operations view shows current cost, accumulated cost, reconciliation run status, finding counts, orphan indicators, and cleanup risk.
3. Server-owner cloud status/detail views show current cost, accumulated cost, source label, and relevant reconciliation risk only for allowed server scope.
4. UI copy and DTO naming distinguish estimated, reconciled, and adjusted costs and avoid claiming invoice-grade actual cost.
5. Generated Kiota clients and WebApp repository facades are refreshed; no raw browser HTTP bridge is introduced for v1.4 surfaces.

**Plans:** 3/3 plans complete

### Phase 20: Labeling, Safety, And Verification Hardening

**Goal:** Improve future reconciliation with UTF-owned provider labels and close the milestone with focused verification around authorization, redaction, cost math, provider failures, and destructive-boundary safety.

**Requirements:** HETZ-12, RELY-15, RELY-16

**Success Criteria:**

1. Newly provisioned Hetzner servers, floating IPs, volumes, and firewalls include safe UTF labels or equivalent provider metadata for project/session/game-server/resource correlation.
2. Provider tokens, Steam credentials, worker credentials, bootstrap credentials, bearer headers, and secret-bearing user data are absent from cost snapshots, reconciliation findings, audits, DTOs, generated clients, and logs.
3. Tests cover cost math, deletion-as-cost-stop behavior, ownership transfer attribution, provider list pagination and failures, reconciliation finding types, authorization boundaries, and secret redaction.
4. Tests or reflection guards prove reconciliation remains read-only and does not invoke provider delete/detach methods.
5. Verification artifacts document that OPS-02/live provider UAT remains operator-gated unless explicit credentials, budget, approval, and cleanup evidence are supplied.

**Plans:** 3/3 plans complete

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 20-02-PLAN.md - Redaction and read-only safety guards.

**Wave 3** *(blocked on Wave 2 completion)*
