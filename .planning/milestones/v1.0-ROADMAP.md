# Roadmap: United Tactical Forces - Cloud Game Server Orchestration

## Overview

This milestone moves game-server hosting from API-owned local process state toward a durable control-plane and worker model. It starts with lifecycle jobs, adds a local worker with restart recovery, enforces billing ownership and audit history, then exposes the resulting state through API and frontend surfaces. Hetzner provisioning and real provider cost reconciliation stay deferred until this foundation is proven.

## Phase Details

### Phase 1: Durable Lifecycle Jobs

**Goal:** Operators can request game-server lifecycle actions as durable, authorized jobs instead of API-local fire-and-forget work.
**Mode:** mvp
**Depends on:** Nothing (first phase)
**Requirements:** LIFE-01, LIFE-02, LIFE-03, RELY-03
**Success Criteria** (what must be TRUE):

  1. Operator can request configure, install, start, stop, restart, update, collect logs, and delete operations and receive a durable job id.
  2. Operator can inspect job state, attempt count, timestamps, assigned worker placeholder, and failure reason from persisted data.
  3. Existing game-server authorization checks still gate lifecycle job creation.
  4. Long-running lifecycle endpoints no longer report final success before execution has completed.

### Phase 2: Local Worker Execution And Recovery

**Goal:** A local worker can execute durable jobs through the existing game-controller abstraction and recover from API or worker restarts.
**Mode:** mvp
**Depends on:** Phase 1
**Requirements:** WORK-01, WORK-02, WORK-03, WORK-04, LIFE-04, RELY-01, RELY-02
**Success Criteria** (what must be TRUE):

  1. Administrator can see a local worker registered with active/stale heartbeat status.
  2. Worker can claim eligible lifecycle jobs with a lease so duplicate execution is prevented.
  3. Worker can execute existing local Arma 3 controller operations through job handlers without breaking current hosting behavior.
  4. Operator can recover, retry, or fail jobs abandoned by stale workers according to persisted recovery rules.
  5. API and worker restarts preserve queued, running, failed, and completed job truth.

### Phase 3: Billing Ownership And Audit Foundation

**Goal:** Managed game-server operations have exactly one active billing owner and immutable audit history before cloud costs exist.
**Mode:** mvp
**Depends on:** Phase 2
**Requirements:** BILL-01, BILL-02, BILL-04, AUDT-01, AUDT-02, AUDT-03, RELY-04
**Success Criteria** (what must be TRUE):

  1. Administrator can define user-backed billing accounts with an extensible owner kind for future teams, events, or organizations.
  2. Operator cannot create or operate a managed game server unless exactly one active billing owner is assigned.
  3. Administrator can inspect immutable audit records for lifecycle jobs, billing assignment changes, cleanup failures, and abandoned jobs.
  4. Historical billing assignment intervals are preserved across ownership changes, stops, deletes, and cleanup failures.
  5. Steam, worker, and future provider secrets are not exposed through frontend DTOs, job errors, or persisted logs.

**Plans:** 3/3 plans complete
Plans:
**Wave 1**

- [x] 03-01: Add billing account, assignment, and assignment history model.

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 03-02: Enforce active owner validation in lifecycle job creation.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 03-03: Add lifecycle/billing audit events and secret-safe error/log handling.

### Phase 4: User And Admin Lifecycle Visibility

**Goal:** Users and administrators can see the durable lifecycle, ownership, and recovery state needed to operate local managed servers confidently.
**Mode:** mvp
**Depends on:** Phase 3
**Requirements:** BILL-03, VIS-01, VIS-02, VIS-03
**Success Criteria** (what must be TRUE):

  1. User can see queued, running, succeeded, failed, cancelled, and retrying lifecycle operations in the frontend.
  2. User can open a server details view and see lifecycle state, current job progress, active billing owner, relevant logs, and failure messages.
  3. Administrator can identify stale workers, stuck jobs, and servers requiring manual cleanup from API or frontend surfaces.
  4. Generated client and repository layers expose the new job, owner, and worker state without hand-editing generated Kiota code.

**Plans:** 3/3 plans complete
**UI hint**: yes

- [x] 04-02: Update WebApp repository and server detail surfaces for jobs and owners.
