# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-22
**Milestone:** v1.10 CR-0001 Live Acceptance And Operational Closure
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.10 Requirements

Requirements for the final operator-gated CR-0001 live acceptance milestone. Each requirement maps to exactly one roadmap phase. Live provider mutation remains blocked until approval, preflight, budget, cleanup-window, and redaction requirements are satisfied.

### Approval And Preflight

- [x] **LIVE-01**: Operator can record a fresh Phase 30 approval package with approver, timestamp, Hetzner project, token reference, resource shape, budget ceiling, maximum lifetime, cleanup window, selected game server, billing account, template/profile snapshot, dry-run plan, and policy approval identifier when required.
- [x] **LIVE-02**: Operator can verify authenticated administrator and server-owner access to `/servers/cloud`, `/servers`, and required API surfaces without storing cookies, authorization headers, bearer tokens, OAuth material, or session secrets.
- [x] **LIVE-03**: Operator can verify that provider configuration is enabled and verified, provider metadata is fresh, the selected game server has exactly one active billing owner, the dry-run plan is valid and current, template/profile snapshots are usable, cost estimate is within budget, policy gates are resolved, and reconciliation has no unknown billable blockers before mutation.

### Live Provisioning

- [ ] **PROV-01**: Operator can execute exactly one approved live provider provisioning path from the reviewed WebApp plan and capture cloud session id, provider resource identifiers, endpoint, billing owner, template/profile context, cost source, policy state, reconciliation state, and audit records without credential material.
- [ ] **PROV-02**: Operator can record safe failure or partial-provisioning evidence with owner attribution, cleanup risk, retry or manual cleanup action, and no duplicate or hidden billable resources.

### Runtime And Visibility

- [ ] **RUNT-01**: Operator can verify cloud worker bootstrap, registration, heartbeat, and capabilities, then either execute Steam/Arma install, configure, start, stop, and log collection or classify an explicit environment blocker with safe diagnostics.
- [ ] **RUNT-02**: Authenticated administrator and server-owner views expose lifecycle state, worker health, endpoint, logs, current cost, accumulated cost, policy, reconciliation, billing owner, template/profile context, and audit history without exposing provider, Steam, worker, authorization, bearer, cookie, or raw secret-bearing payload data.

### Cleanup And Classification

- [ ] **CLN-01**: Operator can execute provider teardown and any required manual cleanup fallback, then record provider-side server, floating IP, volume, firewall, and final billable resource counts with final billable resource count `0` before pass classification.
- [ ] **CLN-02**: Operator can complete redaction review for approval records, browser evidence, provider evidence, worker/runtime evidence, logs, screenshots, comments, and exported artifacts before classifying Phase 30 as passed, failed, or blocked.

### CR Acceptance

- [x] **ACC-01**: Operator can map CR-0001 acceptance criteria to captured evidence with a passed, failed, blocked, or deferred classification and concrete follow-up actions for any unmet criteria.

## Out of Scope

Explicitly excluded from v1.10.

| Feature | Reason |
|---------|--------|
| Live provider mutation before approval, preflight, budget, cleanup-window, and redaction evidence are complete | Phase 30 is operator-gated and can create real costs. |
| Marking live Hetzner, Steam, Arma, browser, teardown, cleanup, or final billable-resource evidence as passed without captured evidence | This milestone exists to produce trusted evidence, not infer success from implementation tests. |
| Additional cloud product features beyond blocker fixes needed for the live evidence path | v1.10 validates the completed CR-0001 implementation rather than expanding scope. |
| Payment processing, payment-provider billing, customer invoicing, taxes, checkout, or legal invoice generation | CR-0001 defines billing as internal attribution, not payment collection. |
| Multi-provider orchestration | Hetzner remains the first real cloud target until runtime and cleanup behavior are proven. |
| Multi-session cloud workers | One server per worker remains the safe billing, firewall, port, storage, and cleanup model. |
| Headless clients, resource resize, snapshots, backups, marketplace templates, or broad template marketplace behavior | These remain future extensions after live CR acceptance. |
| Manual SSH or provider-console workflows as the normal path | Manual provider cleanup is allowed only as fallback evidence when automated teardown fails or is blocked. |
| Treating runtime stop or runtime cleanup as provider cost stop | Hetzner resources remain billable until provider teardown/deletion succeeds. |
| Persisting raw provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, bearer tokens, cookies, OAuth codes, or raw secret-bearing payloads in evidence | Security constraints require redaction and allowlisted evidence. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud orchestration is validated. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
