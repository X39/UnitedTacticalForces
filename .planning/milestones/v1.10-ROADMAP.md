## Phase Details

### Phase 45: Approval, Authenticated Access, And Live Preflight Evidence

**Goal:** Operator can prove that live provider mutation is approved, budgeted, authenticated, and safe to attempt.
**Depends on:** v1.9 closeout and parked Phase 40 guardrails
**Requirements:** LIVE-01, LIVE-02, LIVE-03
**Implementation boundaries:** Do not mutate provider resources until all preflight evidence is recorded. Do not store cookies, authorization headers, bearer tokens, OAuth material, provider tokens, Steam credentials, worker secrets, or raw secret-bearing evidence.
**Success Criteria** (what must be TRUE):

1. Approval evidence records approver, timestamp, budget ceiling, maximum lifetime, cleanup window, selected game server, billing account, template/profile snapshot, dry-run plan, provider project, and policy approval identity when required.
2. Authenticated administrator and server-owner access to required WebApp/API surfaces is verified or explicitly blocked with safe diagnostics.
3. Provider configuration, metadata freshness, active billing owner, dry-run currency, template/profile usability, cost budget, policy state, and reconciliation state are verified before mutation.
4. Phase 40 readiness evidence is updated without treating its existence as authorization by itself.
5. Redaction checks confirm no secret-bearing approval, auth, provider, or browser material is persisted.

**Plans:** 3/3 plans complete

### Phase 46: Controlled Live Provisioning Evidence

**Goal:** Operator can run or safely block exactly one approved live WebApp provisioning path with complete evidence and no hidden billable resources.
**Depends on:** Phase 45
**Requirements:** PROV-01, PROV-02
**Implementation boundaries:** Execute only the approved scenario. Do not create duplicate provider resources. If provisioning fails or partially completes, preserve owner attribution and immediately transition to cleanup evidence.
**Success Criteria** (what must be TRUE):

1. The reviewed `/servers` plan is used as the source of truth for live provisioning.
2. Provisioning evidence captures cloud session id, provider resource identifiers, endpoint, billing owner, template/profile context, cost source, policy state, reconciliation state, and sanitized audit records.
3. Failure or partial-provisioning evidence captures cleanup risk, retry or manual cleanup action, and visible owner attribution.
4. Reconciliation or provider-side inspection confirms there are no duplicate or hidden billable resources beyond the approved scenario.
5. Evidence avoids provider tokens, Steam credentials, worker credentials, authorization headers, bearer tokens, cookies, and raw secret-bearing payloads.

**Plans:** 3/3 plans complete

- [x] 46-01-PLAN.md - Approved WebApp provisioning execution and evidence capture.
- [x] 46-02-PLAN.md - Partial-failure, retry, cleanup-risk, and duplicate-resource checks.
- [x] 46-03-PLAN.md - Provisioning evidence redaction and requirement verification.

**UI hint:** yes

### Phase 47: Live Runtime And Visibility Evidence

**Goal:** Operator can prove cloud worker bootstrap and Arma 3 runtime behavior through authenticated views, or record an explicit environment blocker.
**Depends on:** Phase 46
**Requirements:** RUNT-01, RUNT-02
**Implementation boundaries:** Do not mark Steam/Arma runtime as passed unless live install/configure/start/stop/log evidence exists. Runtime cleanup remains separate from provider teardown and cannot be treated as cost stop.
**Success Criteria** (what must be TRUE):

1. Cloud worker bootstrap, registration, heartbeat, and capabilities are verified for the live cloud session.
2. Steam/Arma install, configure, start, stop, and log collection are executed or blocked by a concrete environment prerequisite.
3. Authenticated administrator and server-owner views show lifecycle state, worker health, endpoint, logs, cost, policy, reconciliation, billing owner, template/profile context, and audit history.
4. Runtime evidence distinguishes worker-local cleanup from provider teardown.
5. Redaction checks confirm runtime evidence and screenshots do not expose provider, Steam, worker, bearer, cookie, or raw secret-bearing data.

**Plans:** 3/3 plans complete

- [x] 47-01-PLAN.md - Worker bootstrap, registration, heartbeat, and capability evidence.
- [x] 47-02-PLAN.md - Steam/Arma lifecycle and log evidence or explicit blocker classification.
- [x] 47-03-PLAN.md - Authenticated runtime visibility and redaction verification.

**UI hint:** yes

### Phase 48: Provider Teardown, Cleanup, And Redaction

**Goal:** Operator can prove that provider-side billable resources are deleted or safely classified, and all evidence is redacted before any pass classification.
**Depends on:** Phase 47
**Requirements:** CLN-01, CLN-02
**Implementation boundaries:** Provider teardown is the only cost-stop action. Do not classify live acceptance as passed unless final provider-side billable resource count is `0`.
**Success Criteria** (what must be TRUE):

1. Provider teardown is executed through the control plane for the approved live scenario.
2. Manual cleanup fallback is recorded only when automated teardown fails or leaves billable resources.
3. Provider-side counts for servers, floating IPs, volumes, firewalls, and other billable resources are recorded after cleanup.
4. Final provider-side billable resource count is `0` before any pass status is recorded.
5. Redaction review covers approval records, browser evidence, provider evidence, worker/runtime evidence, logs, screenshots, comments, and exported artifacts.

**Plans:** 3/3 plans complete

### Phase 49: CR Acceptance Classification And Handoff

**Goal:** Operator can classify CR-0001 acceptance criteria against captured evidence and hand off any failed or blocked follow-up work.
**Depends on:** Phase 48
**Requirements:** ACC-01
**Implementation boundaries:** Do not mark criteria as passed without evidence. Do not hide failed, blocked, or deferred items. Do not expand scope into post-CR feature work.
**Success Criteria** (what must be TRUE):

1. Every CR-0001 acceptance criterion is mapped to evidence, failed evidence, blocker evidence, or explicit deferral.
2. Phase 30 and OPS/EVID classifications are updated consistently with the captured evidence.
3. Failed or blocked criteria include concrete follow-up actions and ownership notes.
4. Final milestone evidence distinguishes implementation verification from live operator evidence.
5. The handoff preserves security, cost, cleanup, and provider-teardown-as-cost-stop constraints.

**Plans:** 2/2 plans complete

- [x] 49-02-PLAN.md - Final handoff, follow-up backlog, and milestone verification.
