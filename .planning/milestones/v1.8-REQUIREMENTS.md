# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-19
**Milestone:** v1.8 Cloud Server Creation Experience
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.8 Requirements

Requirements for the cloud server creation experience milestone. Each requirement maps to exactly one roadmap phase.

### Creation

- [x] **CREATE-01**: Authorized user can start a guided Arma 3 cloud server flow from the `/servers` WebApp surface.
- [x] **CREATE-02**: Authorized user can create a new Arma 3 game server or select an existing Arma 3 game server for cloud planning.
- [x] **CREATE-03**: Authorized user must choose an active billing owner and assignment before creating a cloud dry-run plan or provisioning provider resources.
- [x] **CREATE-04**: Authorized user can enter cloud planning inputs for size, location, storage, ports, SSH or administrative CIDR, modpack, and runtime basics.

### Planning

- [x] **PLAN-01**: Authorized user can generate a non-mutating Arma 3 cloud dry-run plan for the selected game server and billing owner.
- [x] **PLAN-02**: Authorized user can review planned resources, assumptions, firewall rules, validation failures, metadata freshness, and hourly or monthly estimates before provider mutation.
- [x] **PLAN-03**: Authorized user is blocked from provisioning stale, invalid, mismatched, superseded, or owner-mismatched cloud dry-run plans.

### Policy

- [x] **POLICY-01**: Authorized user can see allow, warning, approval-required, and denied policy outcomes as actionable workflow states.
- [x] **POLICY-02**: Authorized user can acknowledge warning decisions or follow approval next steps without bypassing policy scope, expiration, or decision identity.
- [x] **POLICY-03**: Authorized approver can approve or deny provisioning and teardown requests from the cloud server workflow with durable audit context.

### Operation

- [x] **OPS-01**: Authorized user can provision provider resources from the reviewed valid cloud dry-run plan and see session, resource, bootstrap, and worker status.
- [x] **OPS-02**: Authorized user can operate cloud runtime lifecycle actions for install, update, start, stop, restart, collect logs, and runtime cleanup.
- [x] **OPS-03**: Authorized user can tear down provider resources as the explicit cost-stop action, separate from runtime stop, runtime cleanup, and local server deletion.
- [x] **OPS-04**: Authorized user can see retryable, cleanup-needed, orphan-risk, partial-failure, and remaining-billable-resource states after provisioning or teardown.

### Cost Responsibility

- [x] **COST-01**: Authorized user can inspect active cloud cost responsibility with owner, assignment, estimated/reconciled/adjusted labels, reconciliation status, and cleanup risk.
- [x] **COST-02**: Authorized user can inspect historical cloud cost responsibility after ownership transfer, provider teardown, runtime cleanup, or local server deletion.
- [x] **COST-03**: User-visible cost, policy, lifecycle, and audit views do not expose provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, bearer tokens, or raw secret-bearing payloads.

### Verification And Handoff

- [x] **VERIFY-01**: Automated or component-level verification covers owner attribution, stale-plan blocking, policy gates, lifecycle boundaries, teardown cost-stop semantics, partial failure visibility, and redaction.
- [x] **VERIFY-02**: v1.8 evidence clearly states that live Hetzner, Steam, and Arma Phase 30 UAT remains deferred unless a separate operator-approved live evidence milestone runs.

## Future Requirements

Deferred to later milestones. Tracked but not in the current roadmap.

### Operational Evidence

- **LIVE-01**: Operator can complete authenticated browser, live Hetzner, live Steam, and live Arma UAT with explicit approval, budget, cleanup window, and final provider billable resource count `0`.
- **LIVE-02**: Operator can complete the Phase 30 live evidence path using the v1.7 evidence template after v1.8 product workflow implementation is ready.

### Advanced Runtime And Cloud Shape

- **RUN-01**: Worker can report dynamic cloud capacity and capabilities for placement.
- **RUN-02**: Cloud workers can optionally support Arma 3 headless clients.
- **RUN-03**: Multiple game sessions can safely run on one worker when billing, ports, storage, and cleanup are proven.
- **RUN-04**: Arma 3 runtime can be packaged with Docker or Compose where networking and BattlEye constraints allow it.
- **RUN-05**: User can resize, snapshot, restore, or back up cloud server resources after ownership, policy, and cost semantics are defined.

### Billing Extensions

- **COST-24**: System can ingest provider billing data through a direct Hetzner billing API adapter if an official supported endpoint becomes available.
- **COST-25**: Administrator can export adjusted internal attribution summaries for treasurer or reporting workflows.

## Out of Scope

Explicitly excluded from v1.8.

| Feature | Reason |
|---------|--------|
| Payment processing, payment-provider billing, customer invoicing, taxes, checkout, or legal invoice generation | CR-0001 defines billing as internal attribution, not payment collection. |
| Live OPS-02/OPS-03 or Phase 30 Hetzner/Steam/Arma UAT closure | Live evidence requires separate operator approval, credentials, provider project, budget, cleanup window, authenticated sessions, and final provider-side billable resource verification. |
| Multi-provider orchestration | Hetzner remains the first real cloud target until runtime and cleanup behavior are proven. |
| Multi-session cloud workers | One server per worker remains the safe billing, firewall, port, storage, and cleanup model. |
| Headless clients, resource resize, snapshots, backups, marketplace templates, or broad cloud-template management | These are useful later features but are not required to productize the first Arma 3 cloud creation path. |
| Generic redesign of all server administration pages | v1.8 is scoped to the cloud creation and operation workflow, not a full WebApp redesign. |
| Full spending policy configuration redesign | v1.8 consumes existing policy gates and approval surfaces rather than rebuilding policy administration. |
| Manual SSH or provider-console workflows as the normal path | CR-0001 targets frontend-driven orchestration through the UTF control plane. |
| Ownerless quick launch | Every billable or hosting session must have an owner from creation until cleanup or transfer completes. |
| Treating runtime stop or runtime cleanup as provider cost stop | Hetzner resources remain billable until provider teardown/deletion succeeds. |
| Raw browser HTTP bridges for cloud actions | WebApp integration should use generated Kiota clients behind repository facades. |
| Persisting raw provider tokens, Steam credentials, worker credentials, worker hashes, authorization headers, or bearer tokens in UI, evidence, logs, or audit displays | Security constraints require redaction and allowlisted projections. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud orchestration is productized. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
