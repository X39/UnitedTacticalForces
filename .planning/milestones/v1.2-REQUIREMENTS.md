# Requirements: United Tactical Forces - Cloud Game Server Orchestration

**Defined:** 2026-06-16
**Milestone:** v1.2 Real Hetzner Provisioning & Cloud Worker Bootstrap
**Core Value:** Authorized users can operate game servers through durable, auditable lifecycle jobs with a clearly assigned billing owner, even when the API process restarts.

## v1.2 Requirements

Requirements for the real provisioning and cloud worker bootstrap milestone. Each requirement maps to exactly one roadmap phase.

### Cloud Provisioning

- [x] **HETZ-05**: Authorized administrator can provision real Hetzner servers, firewalls, IPs, and optional volumes from a valid owner-linked dry-run plan.
- [x] **PROV-01**: Provisioning uses explicit mutating provider methods that are separated from the existing read-only metadata and dry-run provider paths.
- [x] **PROV-02**: Provisioning persists each provider resource identifier, provider operation result, requested shape, and inventory state transition.
- [x] **PROV-03**: Provisioning refuses stale, invalid, ownerless, unsupported, or already-consumed dry-run plans before any mutating provider call is made.
- [x] **PROV-04**: User can see public connection endpoint details after required network resources have been created.

### Ownership And Cleanup

- [x] **BILL-05**: Every provisioned or partially provisioned billable provider resource has exactly one active billing owner snapshot from creation until cleanup or transfer.
- [x] **BILL-06**: Failed provisioning preserves ownership for any created billable resources and marks them cleanup-needed until deletion succeeds.
- [x] **AUDT-04**: Provisioning, partial failure, cleanup, orphan marking, and teardown events are recorded as immutable sanitized audit records.
- [x] **CLN-01**: Administrator can delete a provisioned cloud session and all associated billable provider resources through an explicit teardown operation.
- [x] **CLN-02**: Teardown marks deletion, not power-off, as the cost-stop boundary and records cleanup failure when any billable resource remains.

### Worker Bootstrap

- [x] **HETZ-06**: System can bootstrap a cloud worker on a provisioned Hetzner VM and register it with the API.
- [x] **WORK-05**: API can issue short-lived, secret-safe worker bootstrap credentials scoped to one cloud session or worker identity.
- [x] **WORK-06**: Provisioned VM bootstrap receives only the API endpoint, worker identity, bootstrap credential, and non-secret runtime configuration needed to connect back.
- [x] **WORK-07**: Worker credential material is never exposed through frontend DTOs, generated client models, logs, audit records, lifecycle job errors, or provider status output.

### Worker Registration And Health

- [x] **WORK-08**: Bootstrapped cloud worker can authenticate to the API, register itself, and link to its cloud session and inventory records.
- [x] **WORK-09**: Cloud worker can heartbeat and report static capabilities including game type support, operating system, architecture, region, and one-session worker shape.
- [x] **WORK-10**: API can distinguish local workers from cloud workers in persisted worker state and projections without breaking existing local worker execution.
- [x] **RELY-08**: API restart does not lose provisioned resource state, worker identity, heartbeat state, cleanup-needed state, or bootstrap status.

### Visibility And Controls

- [x] **VIS-07**: Administrator can inspect provisioning, bootstrap, teardown, cleanup-needed, and orphan-candidate states for cloud sessions and resources.
- [x] **VIS-08**: Server owner can see cloud provisioning and worker bootstrap status for their server without seeing provider tokens or worker credential material.
- [x] **VIS-09**: Administrator can retry safe provisioning, bootstrap, and cleanup steps only when the persisted state says the operation is retryable.
- [x] **RELY-09**: Tests cover mutating provider call boundaries, dry-run validation before provisioning, ownership preservation on partial failure, secret redaction, worker registration, and cleanup transitions.

### Operational Hardening

- [x] **OPS-01**: Generated WebApp API clients replace temporary raw cloud admin HTTP calls after OpenAPI/Kiota regeneration is available.

OPS-02 was deferred out of the v1.2 completion scope by accepted operator gate. See
`.planning/v1.2-OPERATOR-GATE-ACCEPTANCE.md`.

## Future Requirements

Deferred to later milestones. Tracked but not in the current roadmap.

### Cloud Runtime

- **HETZ-07**: System can install, configure, start, update, and stop Arma 3 on a cloud worker.
- **RUN-01**: Worker can report dynamic cloud capacity and capabilities for placement.
- **RUN-02**: Cloud workers can optionally support Arma 3 headless clients.
- **RUN-03**: Multiple game sessions can safely run on one worker when billing, ports, storage, and cleanup are proven.
- **RUN-04**: Arma 3 runtime can be packaged with Docker or Compose where networking and BattlEye constraints allow it.

### Cost And Policy

- **COST-05**: User can see running cost snapshots while real cloud resources exist.
- **COST-06**: Administrator can reconcile internal usage records against provider billing data or exports.
- **COST-07**: Administrator can define spending limits, approval thresholds, and automatic shutdown policies.
- **COST-08**: UI labels costs as estimated, reconciled, or adjusted after billing reconciliation exists.

### Operational Hardening

- **OPS-02**: Authenticated Aspire/API browser UAT covers live cloud provisioning, metadata sync, row selection, and server-admin navigation. Deferred from v1.2 by accepted operator gate; requires Steam/Discord admin and server-owner sign-in, representative cloud data, explicit live-provider approval, a safe Hetzner token reference/project, budget, shape, cleanup window, and provider-side final billable resource count `0`.
- **HETZ-08**: Administrator can reconcile known inventory records against real Hetzner resources and identify orphans.

## Out of Scope

Explicitly excluded from v1.2.

| Feature | Reason |
|---------|--------|
| Installing or starting Arma 3 in the cloud | Runtime support follows real provisioning and worker bootstrap. |
| Provider billing reconciliation | Requires real resource lifetime and a chosen authoritative billing source. |
| Running cost dashboard | v1.2 records ownership and cost-stop boundaries; continuous cost display follows after runtime lifetime is proven. |
| Spending limits, approvals, and automatic shutdown | Policy enforcement depends on real resource lifetime and cost snapshots from later milestones. |
| Payment processing | CR-0001 defines billing as attribution, not payment collection. |
| Multi-session cloud workers | One server per worker keeps initial billing, firewalling, ports, and cleanup straightforward. |
| Removing local worker support | Existing local Arma 3 hosting must remain usable while cloud provisioning is added. |
| Kubernetes or generic cluster platform | Explicitly excluded by CR-0001 as an early target. |
