## Phase Details

### Phase 41: Cloud Template Domain And Audit Foundation

**Goal:** Administrators can manage versioned cloud server templates that define the supported Arma 3 cloud shapes users may choose.
**Depends on:** v1.8 Phase 39 and parked Phase 40 guardrails
**Requirements:** TPL-01, TPL-04
**Implementation boundaries:** Do not run live provider UAT. Do not create provider resources as part of template management. Do not expose provider tokens, Steam credentials, worker credentials, cookies, authorization headers, bearer tokens, or raw secret-bearing payloads.
**Success Criteria** (what must be TRUE):

1. Cloud server templates are persisted with stable id, version, game type, provider, enabled state, provider shape defaults, storage/port/runtime bounds, and update history.
2. Template create, update, disable, and inspect operations are permission checked and audited.
3. Disabled or superseded template versions remain available for historical dry-run/provisioning snapshots.
4. Template projections expose only allowlisted fields needed by administrators and authorized creators.
5. Tests cover persistence, versioning, authorization, audit records, and redaction.

**Plans:** 3 plans:
**Wave 1**

- [x] 41-01-PLAN.md - Template entities, migrations, and versioning model.

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 41-02-PLAN.md - Admin APIs, authorization, audit, and projection contracts.

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 41-03-PLAN.md - Template validation, disable/supersede behavior, and focused tests.

**UI hint:** yes

### Phase 42: Arma 3 Runtime Profiles And Mission References

**Goal:** Administrators can define reusable Arma 3 runtime profiles that bind modpack, mission, server configuration, BattlEye/profile/log assumptions, and runtime options without leaking secrets.
**Depends on:** Phase 41
**Requirements:** RUN-01, RUN-02, RUN-03
**Implementation boundaries:** Runtime profiles may reference existing mod-pack, terrain, mission, and configuration records, but must not upload secret-bearing files or expose Steam credentials. Headless clients and Docker packaging stay future scope.
**Success Criteria** (what must be TRUE):

1. Runtime profiles are persisted with versioned references to modpack revision, mission reference, configuration preset, directory assumptions, port policy, and runtime options.
2. Runtime-profile selection validates that referenced modpacks, missions, and configuration data are active and compatible with Arma 3 cloud planning.
3. Dry-run and worker-facing snapshots receive only allowlisted runtime-profile data needed for lifecycle execution.
4. Users can review selected runtime profile and mission context before provisioning without seeing secrets or raw worker payloads.
5. Tests cover profile persistence, reference validation, projection safety, and worker snapshot redaction.

**Plans:** 3 plans:

- [x] 42-01-PLAN.md - Runtime profile entities, mission references, and validation model.
- [x] 42-02-PLAN.md - API projections, profile selection, and dry-run/runtime snapshot integration.
- [x] 42-03-PLAN.md - Secret-safe worker snapshot and profile verification tests.

**UI hint:** yes

### Phase 43: Template-Aware Planning And Provisioning Gates

**Goal:** Guided entry, dry-run review, cost/policy/reconciliation checks, and provider provisioning all enforce selected template and runtime-profile snapshots.
**Depends on:** Phases 41 and 42
**Requirements:** TPL-02, TPL-03, SAFE-01
**Implementation boundaries:** Template use must not bypass existing billing-owner, stale-plan, policy, reconciliation, or provider-teardown boundaries. Live UAT remains deferred.
**Success Criteria** (what must be TRUE):

1. Guided cloud planning can default inputs from an active template and runtime profile while showing user-visible constraints.
2. Dry-run review persists template/runtime-profile snapshots and flags stale, disabled, or constraint-violating inputs before provisioning.
3. Provider provisioning rejects stale or invalid template/profile snapshots before provider token resolution and before mutating provider resources.
4. Cost estimate, policy gate, reconciliation, ownership, and audit projections include template/profile context without secret leakage.
5. Tests cover stale template, disabled template, override bounds, owner/policy/reconciliation enforcement, and provider-mutation ordering.

**Plans:** 3 plans:

- [x] 43-01-PLAN.md - Guided entry defaults and template/profile-aware dry-run input model.
- [x] 43-02-PLAN.md - Review/provisioning blockers and snapshot enforcement.
- [x] 43-03-PLAN.md - Cost, policy, reconciliation, audit, and safety verification.

**UI hint:** yes

### Phase 44: Template/Profile WebApp Experience And Verification

**Goal:** Admins and authorized users can manage and consume templates/runtime profiles through the WebApp without raw HTTP bridges or generated DTO leakage.
**Depends on:** Phase 43
**Requirements:** UI-01
**Implementation boundaries:** Keep `/servers` as the server-owner workflow and `/servers/cloud` as the admin provider/fleet console. Use generated clients and repository facades. Do not add live UAT evidence closure.
**Success Criteria** (what must be TRUE):

1. Admin WebApp surfaces support template/profile listing, detail, create/edit/disable, and validation feedback through repository models.
2. `/servers` cloud creation displays active template/profile choices, applies defaults, shows constraints, and carries selections into dry-run review.
3. Razor components bind hand-written safe models, not generated transport DTOs or raw HTTP responses.
4. UI and API verification cover authorization-sensitive views, stale/disabled template states, redaction, and regression safety for existing creation workflows.
5. Milestone evidence states that live UAT remains deferred until CR-0001 implementation is otherwise complete.

**Plans:** 3 plans:

- [x] 44-01-PLAN.md - Generated-client/repository model refresh for template/profile APIs.
- [x] 44-02-PLAN.md - Admin template/profile management UI.
- [x] 44-03-PLAN.md - `/servers` template/profile creation UX and milestone verification.

**UI hint:** yes
