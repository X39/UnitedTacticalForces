### Phase 21: Spending Policy Model And Evaluation Boundary

**Goal:** Add durable policy configuration and an evaluation boundary that can classify billable cloud actions using v1.4 cost snapshots, owner assignments, and reconciliation risk.

**Requirements:** COST-07, COST-19, RELY-17

**Success Criteria:**

1. Policy entities, enums, EF configuration, migrations, and DTOs store spending limits, warning thresholds, approval thresholds, automatic-action settings, owner/global scope, effective dates, and audit metadata.
2. Policy evaluation service produces allow, warn, approval-required, or deny decisions for a proposed billable action without mutating provider resources.
3. Evaluation consumes current estimated cost, projected cost, billing owner, metadata freshness, reconciliation freshness, cleanup-needed resources, and unknown billable provider-resource risk.
4. Policy decisions, errors, and input snapshots are persisted in a restart-safe way with sanitized failure details.
5. Tests cover policy validation, effective-policy selection, threshold math, stale-data risk handling, and restart-safe idempotency.

### Phase 22: Approval Gates And Exception Workflow

**Goal:** Gate billable provisioning and lifecycle paths with policy evaluation and provide a durable approval/denial workflow for authorized exceptions.

**Requirements:** COST-15, COST-16, COST-17, RELY-18

**Success Criteria:**

1. Provisioning, runtime start/restart/update, teardown-sensitive actions, and future resize extension points evaluate policy before creating or continuing billable cloud usage.
2. Users receive a policy result that explains allowed, warned, blocked, or approval-required decisions before the billable action proceeds.
3. Approval requests persist requested action, owner, server/session/resource scope, projected cost, threshold trigger, requester, expiration, and sanitized reason.
4. Authorized approvers can approve or deny requests, and approved exceptions are scoped, expiring, auditable, and checked again at action execution time.
5. Authorization tests prove direct endpoint calls cannot bypass policy gates or approve exceptions without the required claims.

**Plans:** 3/3 plans complete

### Phase 23: Automated Shutdown And Policy Action Execution

**Goal:** Execute configured policy actions through durable lifecycle/provider jobs while preserving explicit runtime cleanup and provider teardown boundaries.

**Requirements:** COST-18, RELY-19

**Success Criteria:**

1. Automatic policy actions are computed from persisted decisions and current cost/reconciliation state, with idempotency keys that prevent duplicate shutdown or teardown job enqueueing.
2. Runtime stop, runtime cleanup, provider teardown, and notification-only actions remain distinct policy action types with separate authorization and audit semantics.
3. Provider teardown is enqueued only when the effective policy explicitly permits deletion of billable provider resources and the resource owner/scope is known.
4. Policy-triggered jobs snapshot billing owner and policy decision context so historical attribution survives ownership transfer, cleanup failure, retry, and API restart.
5. Tests cover automatic-action idempotency, retry visibility, cleanup failure handling, owner attribution, and deletion-as-cost-stop behavior.

### Phase 24: Policy Visibility And Verification Hardening

**Goal:** Surface policy state and decisions to administrators and affected server owners, refresh generated clients, and close safety verification for spending-policy enforcement.

**Requirements:** VIS-16, VIS-17, VIS-18, RELY-20

**Success Criteria:**

1. API DTOs and endpoints expose effective policy, threshold usage, pending approvals, denials, active exceptions, recent decisions, automatic actions, and required next steps.
2. Administrator cloud operations view shows policy status, owners near or over threshold, pending approval queue, blocked actions, and automatic action history.
3. Server-owner views show relevant warnings, approval requirements, blocked-action reasons, automatic shutdown status, and retry/cleanup guidance only for allowed scopes.
4. Generated Kiota clients and WebApp repository facades are refreshed; no raw browser HTTP bridge is introduced for v1.5 surfaces.
5. Verification covers policy persistence, threshold math, stale-data risk handling, approval expiry, authorization, automatic-action job enqueueing, idempotency, redaction, and OPS-02 remaining operator-gated.
