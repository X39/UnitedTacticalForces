# Phase 12.2 Pattern Map

## Repository And Generated Client Patterns

- `sources/WebApp/Services/RepositoryBase.cs` is the shared wrapper pattern. Repositories should keep using the
  generated `ApiClient` and named `HttpClient("API")`; hand-written behavior belongs in service repositories, not in
  `sources/WebApp/UtfApi/**`.
- `sources/WebApp/Services/EventRepository/EventRepositoryImpl.cs` and
  `sources/WebApp/Services/TerrainRepository/TerrainRepositoryImpl.cs` are the closest examples for normal generated
  Kiota request-builder usage with immutable collection returns.
- `sources/WebApp/Services/GameServerRepository/GameServerRepositoryImpl.cs` shows the mixed current state: generated
  Kiota for older game-server routes, raw `HttpClient` for newer lifecycle/billing/cloud routes, and helper methods for
  required POST responses.
- `sources/WebApp/Services/CloudAdminRepository/CloudAdminRepositoryImpl.cs` is the main temporary raw bridge to
  replace for the audit item.

## API Surface Patterns

- `sources/Api/Controllers/HetznerProviderController.cs` defines admin-only provider status, verification, metadata
  status, metadata read, and metadata sync routes.
- `sources/Api/Controllers/CloudInventoryController.cs` defines admin-only cloud inventory, dry-run details,
  provisioning, teardown, resource, estimate, and session-status routes.
- `sources/Api/Controllers/GameServersController.cs` defines the resource-scoped owner/admin
  `game-servers/{gameServerId}/cloud-status` route.
- `sources/Api/Program.cs` maps OpenAPI in Development via `app.MapOpenApi()` and applies the enum schema transformer.

## Web UI Patterns

- `sources/WebApp/Pages/Servers/Cloud.razor` is a dense operational page for cloud provider, metadata, dry-run,
  inventory, estimate, provisioning, teardown, session, worker, bootstrap, cleanup, and retry visibility.
- `sources/WebApp/Pages/Servers/Index.razor` is the existing server detail surface where owner-visible cloud status is
  rendered.
- Do not redesign these pages in Phase 12.2 unless generated model names force small binding changes. Preserve the
  existing layout and behavior while changing repository plumbing and UAT evidence.

## Test And Verification Patterns

- `tests/Api.Tests/CloudInventory/CloudInventoryVisibilityTests.cs` covers admin/session status, server-scoped status,
  safe projections, and authorization-sensitive visibility.
- Existing API tests use SQLite/in-memory test context helpers and fake provider boundaries; keep live Hetzner calls out
  of automated test runs.
- Prior verification files such as
  `.planning/phases/12-cloud-worker-registration-and-visibility/12-VERIFICATION.md` and
  `.planning/phases/12.1-close-v1-2-milestone-audit-gaps/12.1-VERIFICATION.md` show the expected evidence format.

## Documentation And Audit Patterns

- `.planning/v1.2-MILESTONE-AUDIT.md` is the source of truth for closing the `tech_debt` status.
- `.planning/STATE.md` tracks pending operational hardening and should be updated when the phase is planned and later
  executed.
- `docs/change-requests/CR-0001-cloud-game-server-orchestration.md` is the higher-level cost/security constraint source
  for live Hetzner UAT: no unmanaged provider mutations, provider tokens stay server-side, and deletion is the cost-stop
  boundary.
